 三、MySQL 中 MVCC 是怎么实现的？快照读为什么通常不会阻塞写操作？ 

 InnoDB 的 MVCC 依赖隐藏字段、undo log 和 Read View。每一行记录内部都带有最近一次修改它的事务 ID，同时保存指向 undo log 的回滚指针。旧版本并不是直接存在数据页里，而是沿 undo log 形成版本链。 

 普通 SELECT 做快照读时，会依据当前隔离级别生成或复用 Read View。Read View 中保存活跃事务集合、最小活跃事务 ID 等信息，读取一条记录时根据版本对应的事务 ID 判断该版本对当前事务是否可见；不可见就沿 undo log 向前找旧版本。 

 因此快照读通常不需要给目标记录加共享锁，它读取的是符合可见性规则的历史版本，自然不会因为其他事务正在修改当前版本而阻塞。 

 需要区分当前读。 SELECT ... FOR UPDATE 、 UPDATE 、 DELETE 读取的是最新有效版本，需要加锁，这时就可能与其他事务发生等待甚至死锁。 

 四、线程池大小如何确定 

 线程池大小不能机械地套 CPU 核数 + 1 或 2 × CPU 核数 ，关键是任务到底在消耗 CPU，还是在等待外部资源。 

 纯 CPU 密集任务的目标是减少上下文切换，线程数量一般接近可用 CPU 核数。线程远大于核数并不会提高吞吐量，反而增加调度和缓存失效。 

 I/O 密集型任务存在数据库、Redis、RPC 等等待时间，可以容纳更多线程。可以用近似模型： 

 线程数 ≈ CPU核数 × (1 + 等待时间 / 计算时间)
 
 但线上不会只靠公式。还要看数据库连接池、下游 QPS、接口 P99、CPU 利用率和任务队列长度。比如数据库连接池只有 30 个连接，却配置 300 个数据库工作线程，大量线程最终只是在等待连接。 

 线上调优时我更关注 activeCount、queueSize、rejectCount、任务执行时间以及 CPU。如果队列持续增长而 CPU 并不高，往往意味着线程阻塞在 I/O；如果 CPU 已经接近饱和，再增加线程通常只会恶化延迟。 

 五、缓存一致性如何解决 

 Cache Aside 下读请求通常是先查 Redis，未命中再查数据库，并将结果写回缓存；写请求则先修改数据库，再删除缓存。 

 不建议“更新数据库之后更新缓存”，因为两个并发写请求可能出现数据库更新顺序与缓存更新顺序不一致，例如数据库最终是 B，缓存却因为旧请求后执行而写成 A。 

 “先改数据库再删缓存”仍然不是绝对强一致。典型窗口是数据库已经提交，但删除 Redis 失败，此时缓存会暂时保留旧值。因此工程上通常会配合重试机制、消息队列或 binlog 订阅进行补偿。 

 另一个少见但存在的窗口是缓存失效后，一个读线程查到了旧数据库值，此时写线程完成数据库更新并删除缓存，之前的读线程又把旧值重新写进 Redis。可以通过合理 TTL、延迟双删、基于 binlog 的最终校正等方式降低影响。 

 如果业务必须强一致，就不应该把 Redis 当普通旁路缓存使用，而需要改变数据模型甚至放弃部分缓存收益，因为强一致和极致性能本身存在成本冲突。 

 六、Spring AOP底层原理是什么 

 Spring AOP 的核心是运行期代理，而不是修改业务类源代码。 

 Bean 创建过程中， AnnotationAwareAspectJAutoProxyCreator 这类 BeanPostProcessor 会检查当前 Bean 是否匹配某些 Advisor。如果存在匹配的切面，Spring 不直接把原始 Bean 暴露出去，而是创建代理对象。 

 目标类实现接口时可以使用 JDK 动态代理，本质上通过 InvocationHandler 拦截接口方法；没有合适接口时通常使用 CGLIB，通过动态生成目标类子类覆盖可代理方法完成拦截。 

 一次代理方法调用并不是直接执行切面代码，而是先构建 MethodInterceptor 调用链。事务、日志、权限等 Advice 会转化成拦截器，最终以责任链方式执行。 

 这也解释了 Spring AOP 的经典问题：同一个对象内部 this.method() 调用不会再次经过代理对象。例如： 

 public void a() {
 this.b();
}

@Transactional
public void b() {}
 
 如果 a() 本身没有事务，通过 this.b() 调用时不会触发 b() 上的事务增强，因为调用根本没有经过 Spring 代理。 

 七、Redis 热 Key 和大 Key 会带来什么问题？线上怎么排查和治理？ 

 热 Key 的问题是大量请求集中到 Redis 集群中的某一个节点甚至某一个 key 上。即使整个集群平均负载不高，单节点也可能因为网络带宽、CPU 或单线程命令处理达到瓶颈。 

 如果是极端热点数据，可以在应用进程增加本地缓存，让请求优先命中 Caffeine；对于能够拆分的热点计数，可以通过 key 分片把单点访问扩散到多个 Redis key，再聚合结果。 

 大 Key 的风险不只在内存。删除一个超大 Hash、Set 或 ZSet 可能造成 Redis 主线程长时间阻塞；主从同步和网络传输也会放大延迟。生产环境应该通过 MEMORY USAGE 、 SCAN 配合抽样工具以及 Redis 自带的 bigkeys 分析，而不是直接在线上执行危险的 KEYS * 。 

 治理时通常会拆分结构，例如一个百万成员的大 Hash 按业务维度分桶。删除大对象则优先使用 UNLINK ，让实际内存回收在后台线程完成。 

 八、幂等如何设计 

 幂等不是简单给接口加一把 Redis 锁，而是保证同一个业务请求重复执行多次，最终业务状态和执行一次一致。 

 支付、下单、核销这类接口一般都会定义稳定的业务唯一键，比如 requestId 、订单号或支付流水号。数据库层通过唯一索引建立最终防线： 

 UNIQUE KEY uk_request_id(request_id)
 
 重复请求即使并发进入，也只有一个能真正插入成功。 

 如果业务流程较长，可以维护幂等状态表，把请求状态设计成 PROCESSING / SUCCESS / FAIL ，相同 requestId 再次到达时直接读取已有结果。这里必须考虑第一次请求处理中客户端超时重试的问题，不能简单把“已经存在”当成成功。 

 Redis SET key value NX EX 可以用于快速挡住重复请求，但 Redis 锁本身不是业务最终一致性的保障，因为锁可能过期、Redis 可能故障，真正的底线仍然应该落在数据库状态机或唯一约束上。 

 九、mysql的隔离性 

 MySQL InnoDB 支持 Read Uncommitted、Read Committed、Repeatable Read 和 Serializable 四种隔离级别。 

 RC 和 RR 的重要区别不仅是名字上的“不可重复读”。InnoDB 中普通快照读依赖 MVCC：RC 基本上每条快照读语句都会生成新的 Read View，因此同一事务中两次查询可能看到其他事务刚提交的数据；RR 通常在事务第一次快照读时创建 Read View，之后复用，所以多次快照读取到的视图相对稳定。 

 幻读要进一步区分快照读和当前读。RR 下快照读依靠 MVCC 避免大多数幻读现象；对于 SELECT ... FOR UPDATE 、UPDATE 这种当前读，InnoDB 会结合记录锁和 Gap Lock / Next-Key Lock 锁住索引区间，阻止其他事务在范围中插入新记录。 

 隔离级别越高并不意味着一定越好。锁范围扩大后，并发写入能力会下降，所以很多互联网业务会使用 RC，并通过业务约束解决部分一致性问题。 

 十、Kafka 为什么吞吐量高？生产环境出现消息积压时怎么排查？ 

 Kafka 的高吞吐建立在顺序追加、批量传输和减少数据拷贝之上。消息写入 partition 时主要是追加日志文件，不需要像 B+Tree 那样频繁做随机页修改。Producer 会把多条消息组成 batch，Consumer 也通过批量拉取减少网络往返。 

 文件读取场景还能充分利用 Linux Page Cache，数据发送过程中可以利用 sendfile 等机制降低用户态和内核态之间的数据复制成本。 

 出现积压时，不能看到 lag 增长就直接增加 Consumer。需要先看 partition 数，因为一个 Consumer Group 内同一个 partition 在同一时间只能由一个 consumer 实例消费。比如 Topic 只有 8 个 partition，把消费者从 8 个扩到 30 个并不能获得 30 倍并发。 

 还需要看单条消息处理耗时。如果 Consumer 每条消息都同步调用一个 500ms 的 RPC，瓶颈其实在下游；盲目扩消费者还可能把下游直接打挂。 

 生产排查通常结合 lag 增长速度、消费 TPS、partition 分布、rebalance 频率、GC 和下游 RT 判断真正瓶颈。

 3. Linux 中如何定位某个端口被哪个进程占用？ 

 可以使用 ss 、 lsof 或 netstat 查询监听端口对应的进程。 

 ss -lntp | grep 8080
lsof -iTCP:8080 -sTCP:LISTEN
 
 如果只知道进程号，可以继续查看进程启动命令、工作目录和打开的文件： 

 ps -fp 
readlink -f /proc/ /exe
ls -l /proc/ /fd
 
 如果端口显示被占用，但进程状态不明显，还需要确认是否存在 IPv4、IPv6 或容器网络映射。容器场景下要同时检查宿主机端口和容器内部端口，不能只看宿主机进程。 

 4. Linux 环境变量、Shell 变量和进程环境之间有什么区别？ 

 Shell 变量只存在于当前 Shell。使用 export 后，变量才会进入当前 Shell 启动的子进程环境。 

 APP_MODE=prod
export APP_MODE
java -jar service.jar
 
 对于临时配置，可以直接在命令前声明： 

 APP_MODE=prod java -jar service.jar
 
 这种方式只影响本次启动的进程。系统级配置可以放在 /etc/profile 、用户 Shell 配置文件或 systemd 的 Environment 配置中，但需要注意不同启动方式加载的环境文件可能不同。 

 排查服务环境变量时，不能只看当前终端： 

 tr '\0' '\n' /environ
 
 还要确认变量是否被启动脚本、容器配置或 systemd 覆盖。 

 5. MySQL 的聚簇索引和二级索引在查询路径上有什么区别？ 

 InnoDB 的聚簇索引通常以主键组织数据，叶子节点中保存完整行记录。二级索引的叶子节点通常保存索引列和主键值。 

 通过二级索引查询时，如果需要返回二级索引中没有的字段，数据库还要根据主键回到聚簇索引查找，这个过程叫回表。 

 CREATE INDEX idx_user_status_time
ON user_event(user_id, status, created_at);
 
 如果查询： 

 SELECT user_id, status, created_at
FROM user_event
WHERE user_id = ?
 AND status = ?;
 
 查询字段都在索引中，可能直接完成覆盖索引扫描。如果再查询一个不在索引中的大字段，就可能产生大量回表。 

 索引设计不能只看查询条件，还要考虑返回字段、数据分布、写入成本和索引占用空间。 

 6. 哪些情况下索引可能无法有效使用？ 

 常见情况包括： 

 
 对索引列进行函数或表达式运算； 

 对索引列进行隐式类型转换； 

 使用前导通配符； 

 联合索引没有使用最左侧列； 

 查询条件选择性很低； 

 使用 OR 导致优化器选择全表扫描； 

 数据量过小，优化器认为全表扫描更快； 

 范围条件后面的联合索引列利用率下降。 

 
 例如： 

 SELECT *
FROM user_info
WHERE DATE(create_time) = '2026-09-21';
 
 可以改成范围查询： 

 SELECT *
FROM user_info
WHERE create_time >= '2026-09-21 00:00:00'
 AND create_time ?
ORDER BY id
LIMIT 20;
 
 如果排序条件不是唯一字段，需要使用组合游标： 

 WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20;
 
 游标分页要求排序字段稳定、索引匹配，并且需要明确数据在翻页过程中发生新增或删除时的语义。 

 10. MySQL 的隔离级别分别解决什么问题？为什么可重复读仍然可能出现复杂并发现象？ 

 常见隔离级别包括读未提交、读已提交、可重复读和串行化。 

 读未提交可能读到其他事务未提交的数据；读已提交避免脏读，但同一事务内两次查询可能结果不同；可重复读保证普通一致性读在事务内看到相对稳定的快照；串行化通过更强的并发限制换取更高一致性。 

 InnoDB 的可重复读通常通过 MVCC 和 Next-Key Lock 共同实现。普通 SELECT 可能读取快照，而加锁读会读取当前版本并参与锁竞争。 

 SELECT *
FROM inventory
WHERE product_id = ?
FOR UPDATE;
 
 隔离级别不能脱离具体 SQL 判断。需要结合快照读、当前读、索引结构和锁范围分析。 

 11. Redis 适合保存哪些数据？哪些内容不应该直接放入 Redis？ 

 Redis 适合保存访问频繁、结构明确、允许通过过期或重建恢复的数据，例如： 

 
 热点查询结果； 

 Session； 

 分布式锁状态； 

 排行榜； 

 计数器； 

 短期任务状态； 

 限流令牌。 

 
 不适合把 Redis 当作所有业务数据的永久数据库，尤其是不能恢复的核心账务数据、没有持久化策略的大对象以及无限增长的日志。

 # 给定一组非负整数 nums，重新排列每个数的顺序（每个数不可拆分），使之组成一个最大的整数
# 输入：nums = [3,30,34,5,9]
# 输出：9534330

# 解题答案仅供参考
def cmp(s1: str, s2: str):
 # 将较短的字符串用字符串的第一位填充至相同长度
 l1, l2 = len(s1), len(s2)
 if l1 > l2:
 s2 = s2 + s2[0]*(l1-l2)
 else:
 s1 = s1 + s1[0]*(l2-l1)
 # 如果s1 > s2，说明s1应该放到s2前面。比如s1=2，s2=1应该为21，比如s1=23，s2=2应该为232
 # 如果s1 == s2，长度大的在前面。比如s1=212，s2=21，则应该21221而不是21212
 return s1 > s2 or (s1 == s2 and l1 > l2)

def solution(nums: list):
 length = len(nums)
 # 选择排序，每次选择出一个“最大”的元素放到前面。关于最大的定义请阅读上面的函数cmp
 for i in range(length):
 max_idx = i
 for j in range(i+1, length):
 # 如果元素nums[j]比当前标记的最大元素更大，则更新最大元素的下标
 if cmp(str(nums[j]), str(nums[max_idx])) is True:
 max_idx = j 
 nums[i], nums[max_idx] = nums[max_idx], nums[i]
 return "".join(map(str, nums))

print(solution([3, 30, 34, 5, 9])) # 9534330
print(solution([92, 922, 929, 21, 211, 213])) # 9299292221321211
