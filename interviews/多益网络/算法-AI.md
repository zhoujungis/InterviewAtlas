## 多益网络 AI应用开发 一面

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-08-17 ｜ [原文链接](https://www.nowcoder.com/discuss/918819769548038144)

1. 请做一下自我介绍 

 2. 你实习时候有什么产出,遇到过哪些困难,怎么解决的 

 3. 一次成本异常可能横跨多个云账号，如何保证证据不会串租户 

 租户隔离不能依赖提示词，也不能让模型自由填写账号 ID。任务创建时，后端根据登录身份生成不可修改的授权上下文，其中包含租户、云账号、资源范围和字段脱敏策略。 

 工具调用时，模型只负责生成时间范围、产品类型和查询条件，账号范围由网关从授权上下文中注入。工具返回的数据还要携带租户和账号标签，写入证据库前再次校验。 

 public ToolRequest authorize(
 ModelArguments args,
 SecurityContext context
) {
 if (!context.allowedProducts().contains(args.product())) {
 throw new SecurityException("product is not authorized");
 }

 return new ToolRequest(
 context.tenantId(),
 context.allowedAccountIds(),
 args.product(),
 args.startTime(),
 args.endTime()
 );
}
 
 即使模型在文档或用户输入中看到其他账号，也不能改变后端注入的资源范围。 

 4. RAG 的召回结果很多，但关键证据总是排在后面，如何定位问题 

 先区分问题发生在召回阶段还是排序阶段。可以检查关键证据是否进入初始候选集：如果没有进入，问题通常来自查询表达、分块、索引字段或过滤条件；如果已经进入但排名很低，问题主要在融合和重排。 

 成本归因场景不能只根据文本相关性排序，还需要加入时间重合度、资源匹配度、账号范围、变更距离和数据可信度。最终分数可以写成： 

 score =
 semantic_relevance
 + resource_match
 + temporal_overlap
 + source_reliability
 - stale_version_penalty
 
 还要检查负向条件。例如用户问“没有发布但费用上涨”，如果重排模型忽略“没有”，就可能把发布记录排在最前面。对于数字、资源 ID 和时间条件，应增加确定性特征，不能完全交给语义模型。 

 5. KV Cache 为什么能够加速自回归生成，前缀缓存为什么可能产生错误命中 

 自回归模型生成下一个 Token 时，需要使用之前所有 Token 的 Key 和 Value。没有 KV Cache 时，每生成一个新 Token 都要重复计算完整历史；使用缓存后，只需要计算当前 Token，并读取之前保存的 Key 和 Value。 

 前缀缓存会进一步复用多个请求相同的 Prompt 前缀，但缓存键必须包含模型、Tokenizer、位置编码配置、Prompt 内容和推理参数。只根据文本哈希复用缓存可能在模型热更新、LoRA 切换或 RoPE Scaling 配置变化后产生错误结果。 

 cache_key = hash(
 model_revision,
 tokenizer_revision,
 adapter_id,
 rope_config,
 prefix_token_ids
)
 
 多租户场景还要考虑缓存侧信道。即使两个租户的前缀文本相同，也不应默认共享包含敏感业务内容的缓存块。 

 6. 多 Agent 同时修改共享状态时，如何避免后完成的旧结果覆盖新结果 

 共享状态不能使用普通的最后写入覆盖。每个节点读取状态时记录版本号，提交结果时使用 Compare-And-Set。只有数据库中的版本仍然等于读取版本，更新才允许成功。 

 UPDATE agent_task
SET state_json = :new_state,
 version = version + 1
WHERE task_id = :task_id
 AND version = :expected_version;
 
 如果更新失败，节点需要重新读取状态，判断自己的结果是否仍然有效。对于可以合并的字段，例如证据集合，可以按证据 ID 做集合合并；对于不可合并的字段，例如最终归因结论，需要进入冲突解决节点。 

 不能简单增加分布式锁包住整个 Agent 任务，因为外部工具和模型调用可能持续数十秒，会造成锁续期、故障恢复和吞吐问题。 

 7. Agent 的规划结果如何持久化，才能在服务重启后继续执行 

 任务不能只保存当前节点名称，还要保存节点输入、输出、依赖版本、尝试次数、工具调用 ID 和等待原因。每次状态转换先写入数据库，再发送下一步执行事件。 

 task_id
node_id
node_state
input_version
output_uri
attempt_id
tool_call_id
retry_count
next_run_time
 
 执行节点必须是幂等的。服务重启后，调度器扫描 RUNNING 但租约已经过期的节点，将其重新放入队列。若节点已经调用外部工具，恢复时应先查询工具调用状态，不能直接重复执行。 

 对于模型推理节点，可以选择重新推理，也可以保存原始输出后继续后续流程。是否重新推理取决于任务是否要求严格复现。 

 8. 数据库已经提交成功，但消息没有发送出去，如何保证任务不会丢失 

 使用 Transactional Outbox。业务状态更新和待发送事件写入同一个本地数据库事务，后台发布器再将 Outbox 事件发送到消息队列。 

 BEGIN;

UPDATE agent_task
SET state = 'WAITING_ANALYSIS'
WHERE task_id = :task_id;

INSERT INTO outbox_event(
 event_id,
 aggregate_id,
 event_type,
 payload,
 status
) VALUES (
 :event_id,
 :task_id,
 'ANALYSIS_REQUESTED',
 :payload,
 'PENDING'
);

COMMIT;
 
 发布器可能在发送成功但更新 Outbox 状态前崩溃，因此消息仍可能重复。消费者必须根据 event_id 去重，系统最终提供的是至少一次投递和业务幂等，而不是依赖消息队列实现不可证明的“绝对只消费一次”。 

 9. 模型工具调用耗时很长，HTTP 请求应该同步等待还是转异步任务 

 如果完整任务可能超过网关、负载均衡器或客户端的超时时间，就不应让 HTTP 请求同步等待。创建任务后立即返回 task_id ，后台通过消息队列执行，客户端使用轮询、SSE 或 WebSocket 获取进度。 

 POST /analysis-tasks
202 Accepted

{
 "task_id": "task_8392",
 "status": "PENDING"
}
 
 任务状态查询接口需要区分排队、执行、等待人工、重试、成功和失败。SSE 只负责推送进度，不作为唯一事实来源；客户端断线重连后，应根据事件序号补拉缺失状态。 

 对几十毫秒即可完成的只读工具仍可同步执行，没有必要把所有调用都转换成异步任务。 

 10. MySQL B+ 树索引发生页分裂时会造成什么影响，如何降低写放大 

 当目标叶子页没有足够空间插入新记录时，InnoDB 需要申请新页，将部分记录移动过去并更新父节点。页分裂会增加随机 I/O、Redo、Buffer Pool 压力和索引碎片，严重时还会向上递归分裂。 

 随机 UUID 作为聚簇索引会让插入分散到大量叶子页，更容易产生页分裂。可以使用趋势递增且全局唯一的 ID，但也要避免所有写入集中在最右侧页面形成热点。 

 二级索引数量也会放大写成本。每插入一行，不仅要更新聚簇索引，还要更新所有二级索引。索引设计需要根据查询收益决定，不能把每个可能的条件都建立成独立索引。 

 11. MySQL 的 Next-Key Lock 如何解决幻读，为什么仍然可能引发死锁 

 Next-Key Lock 是记录锁与间隙锁的组合，不仅锁住已经存在的索引记录，还锁住记录之前的索引区间，从而阻止其他事务在查询范围中插入新记录。 

 例如： 

 SELECT *
FROM resource_bill
WHERE amount BETWEEN 1000 AND 2000
FOR UPDATE;
 
 如果 amount 有索引，InnoDB 会锁住扫描到的索引记录及其间隙。两个事务以不同顺序锁定重叠区间时，仍然可能
