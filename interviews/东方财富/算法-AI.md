## 东方财富 AI应用开发(暑期) 一面凉经

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-07-10 ｜ [原文链接](https://www.nowcoder.com/discuss/905232325024174080)

1. 请做一下自我介绍 

 2. 介绍一下项目的整体架构 

 3. MySQL 的联合索引在什么情况下会失效？如何判断是“没用上”还是“用了但收益低”？ 

 答案： 

 联合索引常见问题包括跳过最左列、对索引列执行函数或隐式类型转换、范围条件截断后续列的有序利用、 LIKE '%xxx' 、字符集或排序规则不一致，以及优化器判断全表扫描成本更低。 

 “失效”不能只看 key 。应结合 EXPLAIN ANALYZE 查看实际扫描行数、回表次数、过滤比例和执行时间。 key 非空只说明选择了索引，不代表效率高；例如低选择性字段可能扫描大量二级索引并频繁回表，反而比顺序扫描更慢。 Using index condition 表示使用了 ICP， Using index 通常表示覆盖索引，但仍需看实际 rows。 

 EXPLAIN ANALYZE
SELECT id, status
FROM review_task
WHERE tenant_id = 42
 AND created_at >= '2026-01-01'
ORDER BY created_at DESC
LIMIT 100;
 
 适合的索引可以设计为 (tenant_id, created_at, id, status) ，但是否把 status 放进去要根据写放大、索引体积和覆盖收益权衡。 

 4. RAG 的索引更新如何做到可见性一致，又不影响在线查询？ 

 答案： 

 不能原地覆盖一整批索引，否则向量库、关键词索引和元数据可能短暂指向不同版本。我会给每次摄取生成 index_version ，新版本在影子空间完成解析、索引和校验，通过抽样查询及数量校验后，再原子切换租户级别的版本指针。 

 查询请求进入时读取一次版本并贯穿整条链路，避免 BM25 使用 V2、向量检索却使用 V1。旧版本暂时保留，等待在途请求结束后异步回收。单文档更新使用 outbox 事件和幂等消费，删除采用 tombstone，防止消息乱序导致旧内容复活。 

 UPDATE tenant_index_pointer
SET active_version = 'v20260710'
WHERE tenant_id = 42
 AND active_version = 'v20260701';
 
 条件更新失败说明切换期间版本已变化，需要重新校验而不是强行覆盖。 

 5. Java 中 HashMap 在并发环境下会出现什么问题？为什么 ConcurrentHashMap 仍不保证复合操作原子性？ 

 答案： 

 HashMap 没有并发安全保证。并发写入可能出现更新丢失、读取不可见、内部结构处于瞬时不一致状态；JDK 7 扩容时还存在链表成环风险。JDK 8 改变了扩容方式，但依旧不能并发使用。 

 ConcurrentHashMap 通过 volatile、CAS 和桶级同步保证单次操作安全，但“先判断再执行”是两个操作，中间可被其他线程插入。例如 containsKey 后 put 不是原子的，应使用 putIfAbsent 、 compute 或 merge 。 

 cache.compute(key, (k, oldValue) -> {
 if (oldValue == null || oldValue.expired()) {
 return loadFromRemote(k);
 }
 return oldValue;
});
 
 还要注意 compute 的回调不宜执行长时间阻塞操作，否则会扩大桶竞争，实际工程中可缓存 CompletableFuture 合并并发加载。 

 6. 混合检索中的 BM25 与向量召回如何融合？为什么不能直接相加分数？ 

 答案： 

 BM25 分数受词频、文档长度和索引分布影响，向量相似度则受模型、距离函数和归一化方式影响，两者不在同一量纲，直接相加会使某一路长期占优。 

 常用方法是 RRF，只依赖候选排名： 

 RRF(d) = Σ 1 / (k + rank_i(d))
 
 它对分数尺度不敏感，适合作为稳定基线。进一步可以训练 Learning to Rank，把 BM25 分、向量分、标题命中、文档时效、权限等级、问题类型等作为特征。训练时必须按时间或文档版本切分数据，避免同一文档片段同时进入训练集和测试集造成泄漏。 

 在财报场景中，精确指标名、法规编号偏向 BM25，语义解释偏向向量检索，因此还可由查询分类器动态调整召回配额。 

 7. InnoDB 为什么选择 B+ 树？页分裂对性能有什么影响？ 

 答案： 

 B+ 树非叶子节点只保存键和子页指针，单页能容纳更多分支，树高更低；叶子节点按键有序并通过双向链表连接，既适合等值查询，也适合范围扫描。哈希结构虽然等值查询理论复杂度低，但不支持范围、前缀和排序，同时扩容成本高。 

 随机插入会使目标页空间不足并触发页分裂：申请新页、搬迁记录、修改父节点，极端情况下向上传播。它会造成额外 I/O、日志量增加、缓存命中率下降和空间碎片。随机 UUID 作为聚簇主键尤其明显。 

 但顺序主键也不是绝对最优，高并发插入可能集中竞争最右叶子页。可使用趋势递增且低碰撞的 ID、批量写入、合理填充因子，并根据写入并发评估热点页问题。 

 8. 如何设计大模型输出的结构化约束？仅依赖 Prompt 有什么风险？ 

 答案： 

 仅在 Prompt 中要求“输出 JSON”属于软约束，模型仍可能输出 Markdown、缺字段、错误枚举或非法转义。可靠方案是在推理层使用 JSON Schema、CFG/受限解码或模型原生 tool calling，使下一 Token 只能落在合法语法范围内。 

 应用层仍需做语义校验，例如金额不能为负、引用页码必须真实存在、工具名必须在白名单内。校验失败可进行有限次数的修复重试，但不能无限重试；涉及资金或权限的操作还要经过确定性规则引擎。 

 {
 "type": "object",
 "required": ["riskLevel", "evidenceIds"],
 "properties": {
 "riskLevel": {"enum": ["LOW", "MEDIUM", "HIGH"]},
 "evidenceIds": {
 "type": "array",
 "items": {"type": "string"},
 "minItems": 1
 }
 },
 "additionalProperties": false
}
 
 9. Redis Cluster 中为什么会出现热点 Key？如何在不破坏一致性的前提下治理？ 

 答案： 

 Redis Cluster 按 hash slot 分片，同一个 Key 永远落到单节点。热点 Key 即使容量很小，也可能把某个分片的 CPU、网卡或事件循环打满。治理前应结合 command latency、带宽、访问频次和慢日志确认是读热点、写热点还是大 Key。 

 只读热点可使用 JVM 本地缓存并增加短 TTL，通过版本号或订阅失效消息控制陈旧窗口；允许近似的计数可拆成多个逻辑分片后聚合；强一致库存不能随意拆读，应把扣减放在单一主状态机中，再异步派生读模型。 

 热点治理不是简单给 Key 加随机后缀，因为那会改变原子性和一致性边界。是否能拆分，取决于业务是否满足可交换、可结合或最终一致。 

 10. 为什么数据库分库分表后分页越来越慢？如何实现稳定的深分页？ 

 答案： 

 LIMIT offset, size 必须先扫描并丢弃 offset 条记录。分片后，每个分片还可能各取 offset + size 条，再由聚合层归并，数据传输和排序成本被放大。 

 更稳定的方式是 Keyset Pagination，使用唯一且有序的游标，例如 (created_at, id) 。下一页查询从上一页最后一条记录继续，复杂度与页码无关。 

 SELECT id, created_at, status
FROM review_task
WHERE tenant_id = 42
 AND (created_at, id) 'READY';
COMMIT;
 
 Kafka EOS 只能解决 Kafka 内部读写事务，不能自动让外部数据库和远程 API 获得端到端 exactly-once。 

 13. 大模型幻觉应该怎样定义和分层治理？ 

 答案： 

 幻觉不只是“答案错误”，还包括无证据归因、引用与结论不一致、错误调用工具、把过期数据当成最新数据，以及在证据不足时过度确定。 

 治理要分层：数据侧保证解析与元数据正确；检索侧提高召回并识别证据冲突；生成侧要求逐结论引用并限制模型只根据证据回答；工具侧采用白名单、参数校验和最小权限；输出侧执行事实一致性检查；产品侧提供拒答和人工复核。 

 对高风险财务结论，系统不能让另一个 LLM 的“主观打分”成为唯一防线，应把金额计算、阈值比较、权限和合规规则交给确定性程序。 

 14. JVM 中一次 Young GC 后对象一定会进入老年代吗？晋升失败如何处理？ 

 答案： 

 对象通常在 Eden 分配，Young GC 后存活对象进入 Survivor，并随年龄增长。达到晋升阈值、动态年龄判断成立、Survivor 空间不足，或者大对象策略触发时，才可能进入老年代。 

 晋升前 JVM 会评估老年代是否有足够空间。不同收集器处理不同：Parallel/CMS 时代可能触发担保与 Full GC；G1 会根据 Region 和回收集合处理，若疏散失败可能保留对象并进入更重的回收；ZGC、Shenandoah 则采用并发转移和染色指针等不同机制。 

 排查不能只盯 -Xmx ，还要查看对象分配速率、晋升速率、存活集大小、TLAB、Humongous Object、停顿分位数和 GC 日志中的 evacuation failure。 

 15. Agent 执行工具时如何防止 Prompt Injection 和越权调用？ 

 答案： 

 外部文档、网页和工具返回值都属于不可信数据，不能与系统指令处于同一信任级别。模型提出工具调用只能视为“执行建议”，真正执行前必须经过策略引擎。 

 策略引擎校验调用主体、租户、工具白名单、参数 Schema、资源范围和风险等级；读取类工
