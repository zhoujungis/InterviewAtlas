## vivo Agent 开发工程师 二面

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-11-21 ｜ [原文链接](https://www.nowcoder.com/discuss/953777276263333888)

1、用户说“找出下周三场复盘，优先把最长的挪到周四，别和客户会撞”。如果你来设计这个 Agent，第一轮给模型哪些工具，哪些步骤要等结果回来？

 先提供能查事件和忙闲的只读工具。第一步查下周的复盘，取回事件标识、起止时间和可见日历。排序可以由程序完成，模型负责理解“最长”和“优先”在这句话中的含义。如果实际只查到两场，就说明覆盖范围；若两场并列最长，要请用户区分，或者给出两个方案。不能让模型凭标题猜时长。

 确定目标后才知道周四要找多长的空档，再查客户会所在的授权日历。确定新旧时间以后生成变更草稿，只改被选中的会议。“优先”也值得留意：最长的一场挪不开时，可以提议改挪第二场，但这个替换需要用户决定。这样每一步拿到的对象和约束都有来处。

 2、有依赖关系的一串工具调用，用有向无环图和状态机分别擅长表达什么？用户中途改主意怎么表示？

 依赖图适合描述一轮计划内哪些结果要先得到。一个节点要用事件标识和候选时间，就必须等待这两份输入；没有依赖的只读查询可以并行。状态机适合描述任务处于查找、待选择、待确认还是已终止，以及哪些事件能触发转换。等待用户后回到查找，在状态机里是自然的循环。

 两者可以组合起来。把当前任务状态和计划版本保存下来，在一个状态里执行一小段依赖图。用户更正目标时进入新的计划版本，保留仍然有效的观察，作废依赖旧条件的节点。否则强行沿原图走到底，图上的每个节点也许都成功执行了，最终却完成了用户已经放弃的目标。

 3、正在查周四空档时，用户说“等等，改周五，客户会照样避开”。旧查询慢了两秒才返回。你会保留哪些结果？

 三场复盘的排序取决于原始会议和时长，改目标日期不会自动改变它。如果事件版本仍有效，可以保留排序、选中的会议和“避开客户会”这一约束。周四忙闲和依赖它生成的建议全部失效。我会让周五查询携带新的计划版本，工具返回时检查结果对应的版本与条件。

 取消旧请求可以省一些算力，但即使取消失败、周四结果最后才到，它也只能进入旧计划的记录。验证方法是控制返回顺序：先让周五产生候选，再让周四返回，检查预览和后续工具参数里都只有周五。若原会议此时也被改长，则从时长这个依赖点重算，不能仅把日期替换一下。

 4、两个执行者都读取了版本7。一个先写入版本8，另一个随后也要更新。比较并交换能保证什么，不能保证什么？

 原子条件更新会把“当前版本仍是7”作为写入前提，并在成功时推进版本。先提交的一方成功，后一方的条件不成立，因而可以发现基于旧数据的覆盖。若把检查版本和写入拆成两个独立操作，两者之间仍有被别人抢先修改的窗口。

 这个保证只覆盖参与比较的那项资源。检查草稿版本，不能证明外部日历仍然空闲，也不能证明用户批准了后来变化的内容。冲突以后要重新读取状态，判断哪些假设失效。若直接换成最新版号把同一个旧动作重试，比较并交换本来要保护的更改就会被应用自己覆盖。

 5、回到那场复盘。用户看到“周五三点到四点”的草稿并点了确认，原会议却刚被组织者延长到90分钟。你的 Agent 怎么办？

 先看确认覆盖了什么。用户确认的是一个具体会议及一小时的改动方案。提交前重新读取后发现会议已经变长，原来的确认并没有包含占用额外半小时这件事。我会标记旧草稿失效，核查周五15:00到16:30是否可行，然后告诉用户时长发生了变化。即便多出的半小时恰好有空，也要让用户看到新方案。

 如果目标系统支持条件写入，可以把预期事件版本带入工具，让执行时发生的更新也能被发现。本项目的默认交付只到草稿，助手能可靠报告的是“变更草稿已准备好”。扩展接入真实改期工具时，才按其权限、条件更新能力和返回结果报告是否生效。

 6、评测 Agent 时，逐条比对标准工具调用序列，和检查环境最终状态，各会漏掉什么？

 逐条比对轨迹很适合检查有先后要求的动作，例如在确认之后才能发起写入。但合法路径可能有多条。一个助手一次批量取回三场会议，另一个先列出标识再读详情，两者完全可能得到同一个正确草稿。硬性匹配唯一轨迹会把后一种实现误判为失败。

 最终状态检查允许合理的路径差异，可它会漏掉过程中的越界动作：先改错一场再改回来，最终表面上也能一致。我的做法是给结果写可验证条件，给过程写少量必须满足的约束，另外记录步数和成本。评分时能区分“完成了任务”“违反了确认要求”和“正确但绕了远路”，排查方向也不同。

 7、你会怎么把“组织者中途改了时长”做成一个能反复跑的 Agent 测试？录一段标准对话够吗？

 我会建一个可重置的小日历环境，预置三场会议和周五忙闲。在助手展示一小时草稿后，测试驱动器用组织者身份把目标会议改成90分钟，再让用户确认旧预览。触发点取决于任务事件，不依赖脚本规定的“第六句话”，这样两个用不同工具顺序的助手都能遇到同一冲突。

 验收检查三项：旧确认没有提交，新建议覆盖90分钟，其他会议保持原值。若周五只剩60分钟，说明冲突并请求新选择也算通过。这个设计借鉴了 τ²-Bench 在电信场景中让用户与 Agent 都能改变共享环境的思路。项目方在2026年10月19日发布的 2.0.0 还调整了评分口径，明确提示与1.x的分数不可直接比较。自己的回归集也应把环境、任务和评分器的版本一起固定。

 8、把任务分成查空档、多轮更正、冲突恢复三类。微平均和宏平均的成功率有什么差别？什么情况下排名会反过来？

 微平均把全部成功任务数除以全部任务数，样本多的类别权重大。宏平均先分别计算三个类别的成功率，再让三类各占三分之一。两者都要求先定义成功，比如冲突题的正确结果可能是停下来澄清；如果一律把“生成了草稿”记成功，平均方式再精细也无济于事。

 当系统A擅长高频查询、系统B擅长低频冲突时，大量查询样本可能把A推到微平均第一，等权计类时则可能是B领先。还要报告每类分母。只测两道冲突题，答对一道就会让该类跳动50个百分点，这种宏平均不适合独自承担发布决策。

 9、给你一组同批测试结果。80道查空档、10道更正、10道冲突恢复，旧版分别做对76、7、6道，新版做对79、8、3道。你会怎么解读？

 旧版微平均89%，新版90%；宏平均从75%降到约69.6%。多做对的查询和更正掩盖了冲突恢复从6/10降到3/10。我的第一步是找出两版结果不同的冲突样本，区分新版是多问了一句、暂未完成，还是拿着过期确认继续提议写入。三者对用户的影响差别很大。

 如果发现旧草稿被当成有效确认，我会挡住新版的改期路径，保留只读查询作为独立候选。随后增加“改时长、改对象、撤回授权”等明确触发的测试，固定模型和工具桩回放。十个样本不足以估计线上出错概率，但一个可以稳定复现的确认失效，就足以说明这条路径需要修正。

 10、最后让你接手这个退化。新版同时换了模型和工具描述。你只有一次小规模回归预算，怎么找出该改哪里，并给出放行依据？

 我先选少量能稳定体现差异的冲突题，再配上表述相近、无需重规划的正常题。固定用户、环境变化、解码设置和评分器，把旧新模型与旧新工具描述交叉成四组，同一任务在各组使用相同起始快照。这样既能看单项变化，也能发现只有两者组合时才出现的退化。若模型服务仍有随机性，把有限的重复次数优先给结果摇摆的样本。

 诊断时找轨迹中第一个有意义的分歧。若模型在工具失败后继续执行，先看描述和返回值有没有区分“过期”与“成功”；若工具明确报过期、模型仍复用旧确认，就由执行器把旧版本彻底置为不可提交。修好后，用未参与定位的会议和不同措辞再跑，检查过期确认被拦住、用户重新确认的新方案能通过、正常查询没有普遍多问。小规模回归能给出是否恢复受限试用的依据，真实完成率还要靠后续试用数据。

## vivo Agent 开发工程师 一面

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-11-20 ｜ [原文链接](https://www.nowcoder.com/discuss/953318284886122496)

1、用户说“帮我看看下周哪天下午有空，我想约个复盘”。你的 Agent 第一步会做什么？

 我会先查用户下周下午的忙闲。“看看”授权了查询，“想约”说明查询的目的，具体哪天、要不要建草稿还没决定。这个区分会直接影响工具选择。如果这时就打开一张填满默认值的日程卡，用户还得从里面猜哪部分是自己说过的。

 我会让模型提出查询范围，由程序按用户所在时区展开“下周”，调用已授权的忙闲工具。如果有空，就报出一两段连续空闲以及各自的时长。用户没有指定会议时长，也可以先做这一步。等他说“周二那个，留半小时”，再把选中的时段转成草稿。

 2、意图分类、槽位抽取和工具选择有什么联系？前两项都预测对了，工具还可能选错吗？

 意图描述用户希望达成的目标，槽位保存对象、时间、时长等参数。工具选择还取决于当前掌握了哪些事实、用户允许做到哪一步。同样是安排复盘，知道具体时间时可以准备草稿，只有一个大致范围时，可以先查空档。

 举个反例：“看看周二三点那场复盘是谁组织的。”模型能正确识别查询意图，也能抽出时间和标题，但忙闲工具只返回占用区间，用它回答不了组织者是谁。需要先理解每个工具能观察什么。所有可用工具都读不到组织者时，正确动作也可能是一句能力范围说明。

 3、假设用户改说“帮我把下周那场复盘挪到下午”。你准备先问他哪一天，还是先查？

 如果已经获准按标题查询日程，我会先在下周范围内查“复盘”。用户说“那场”时，最先要确定的是被修改的对象。直接追问日期，可能让用户去查一件助手自己就查得到的事。反过来，只用忙闲工具也不够，因为两个占用区间可能来自完全不同的会议。

 如果只找到一场，就用它原来的日期和时长做条件，继续找当天下午的空档，并把“按原日期查”展示出来。如果找到周二的项目复盘和周四的客户复盘，我只问“你指周二的项目复盘，还是周四的客户复盘？”先解决会改变后续查询结果的歧义。查不到时，我会报告已经查过的范围，再请用户补一个线索。

 4、模型返回一个符合 Schema 的对象，和发出一次工具调用，有什么区别？两者都能表示成功吗？

 结构化结果规定输出的数据形状。例如一个对象要求有候选日期、时长和标题，解析器可以检查字段是否齐全。工具调用还表达了一项待执行的操作，应用需要按名字找到工具、校验参数和权限，再把执行结果交回模型。两者可以共用结构约束，但表达的是不同阶段。

 即使接口严格保证参数类型，一个字符串仍可能指向已经删除的会议，一个合法时间也可能落在用户拒绝的日期。模型给出调用只说明它提出了动作。工具返回的状态及结果才能说明动作发生到了哪一步，例如“查到两个候选”或“草稿已保存”。

 5、如果项目里 search_events 和 find_free_time 经常互相选错，你会怎么改？怎么知道改动起作用了？

 先看错例的目标。“周二几点有复盘”需要找到已有事件，“周二几点能开复盘”需要找可用时段。两句话共享大部分词，如果工具描述都只写“查询日历”，模型很难凭名字补出区别。我会在描述中写明输入、返回值和适用条件：前者返回匹配事件及标识，后者按窗口和时长返回候选空档。

 验证时保留这类只差一两个字的成对样本，再加一句“先找出原来的复盘，再看看能挪到几点”，期望依次选两种工具。固定模型、输入和工具实现，仅替换描述，分别记录首步选对率和最终草稿是否正确。只有第一项变好，往往说明入口修好了，下一步仍没有用对查询结果。

 6、ReAct 式循环里的 observation 起什么作用？完整计划已经写出来了，为什么还要在两步之间等工具结果？

 计划中的步骤可以依赖尚未知道的事实。一次行动产生的观察会缩小下一步可选动作的范围。例如先查会议，观察里可能是唯一匹配、多个匹配、空结果或读取失败，这四种情况需要的下一步各不相同。提前把后续工具参数全部填好，等于替这些未知事实选了一个答案。

 实现这样的循环只需要让下一次决策看到当前目标、已执行动作、工具结果和剩余预算。对排障最有用的也是这些可记录的证据。还要由程序定义终止条件，例如目标已完成、等待用户选择、工具不可用，或预算已耗尽。循环次数用完时应把进度说明白。

 7、忙闲工具只查到了个人日历，工作日历超时。它返回周二三点没有占用，你会怎么答？

 先看“没有占用”的范围。个人日历成功返回空记录，是一条有效观察；工作日历超时，则没有提供忙闲证据。我会让工具分别返回每个日历的读取状态和覆盖时段，把两条事实都交给决策层。否则，把两个结果拼成一个空列表之后，模型再强也猜不回哪一路超时了。

 我会答“个人日历周二15:00有半小时空档，工作日历暂时查不到。要我再查一次工作日历，还是先按这个时间做一份待核对草稿？”如果用户要求避开所有工作会议，就等缺失的结果。如果他只关心个人安排，可以按缩小后的范围继续。

 8、对话历史和结构化任务状态各适合存什么？把旧消息压缩成一段摘要，最容易丢哪类信息？

 历史消息保留原话，适合回查指代和解释歧义。任务状态保存下一次决策真正需要的值，例如选定对象、硬约束、偏好、仍待回答的问题，以及每个值从哪一轮得到。摘要可以压缩背景，但“周三尽量别排”和“周三绝对不行”写成同一句“避开周三”，就丢失了约束强度。

 更正和撤回也容易丢。用户先选A，随后说“算了，选B”，状态里要能表达A已失效。若摘要只列出A和B两个候选，模型下一轮可能把旧选择重新拿回来。短历史负责保留原话，结构化状态负责把这种覆盖关系明确传下去。

 9、助手刚报了周二和周四两个空档，用户说“第二个吧，改成一小时，地点照旧”。你的下一次工具调用是什么？

 我会先把“第二个”绑定到用户实际看到的那一版候选列表，得到周四那个具体时段。旧查询按半小时找空档，现在要一小时，先用新的时长重新核对周四该时段。开始时间有空并不能推出随后一小时都有空。地点从已选定的原复盘记录继承。原记录没填地点时，就保留待定。

 如果周四15:00到15:30空闲，15:30以后已占用，我会解释为什么刚才的推荐不能直接保存，再查周四下午最近的连续一小时。若连“第二个”对应的列表都恢复不出来，我会把两项重新列给用户选。不能重新搜索一遍，拿新列表第二行冒充他点过的那一项。

 10、最后加个条件。用户坚持周四下午、必须满一小时，查到的最长空档只有45分钟。Agent 连查三次都给出了同样结果，怎么让它停在一个有用的答案上？

 我会让执行器比较此次查询的窗口、时长、日历范围和数据版本。在输入和数据都没变、上次查询又完整成功的情况下，再请求一遍没有新的信息来源。可以在第一次确定无解时就结束搜索。这里跟超时不同，结果已经告诉我们，约束组合没有可行解。

 回复时说出冲突：“周四下午最长的空档是45分钟。要保留一小时的话，我可以查周五；如果周四更重要，我可以按45分钟做草稿。”若用户坚持两项都保留，就记录未排成的原因，不创建草稿。我会用两个紧邻的用例验证这段逻辑：同条件重复查询应停住；用户随后把时长改成40分钟，则允许重新查。这样既挡住空转，也不会把真正的新指令当成重复。

 自我介绍 介绍觉得做的最好的的一个项目 算法题：如何判断单链表中是否有环？ 

 是个很经典的面试题，可惜没有答出来，面完后同学说了思路：用快慢指针或者哈希表。对于快慢指针方法，如果单链表存在环，快、慢指针必定会在环中的某个结点相遇；对于哈希表方法，可以使用STL的map将链表结点指针映射成map下标，每访问过一个结点p，就将m[p]赋为1(m[p]初始为0)，若在访问某个结点时其m[p[已经被设为1，说明已被访问过，即有环
 参见： https://blog.csdn.net/cyuyanenen/article/details/51712420 

 机器学习中L1和L2范数各有什么特点以及相应的原因？
 L1范数更容易产生稀疏的权重，L2范数更容易产生分散的权重，原因一般从公式角度或者几何空间角度去解释
 从 公式 角度解释：深度学习花书7.1节（202页左右）。带L1正则化的最优参数w=sign(w星) max{|w星|- a/H , 0}，其中w星代表未正则化的目标函数的最优参数，H代表海森矩阵，a是正则化系数，只要a足够大，w 星就会在更大区间范围内使w变为0，而带L2正则化的最优参数w=H/(H+a)▪w星,只要w星不为0，w也不为0.
 从 几何空间 角度解释：绿色等高线代表未施加正则化的代价函数，菱形和圆形分别代表L1和L2正则化约束，L1-ball 与L2-ball的不同就在于L1在和每个坐标轴相交的地方都有“角”出现，而目标函数的"等高线"除非位置摆得非常好，大部分时候都会在角的地方相交。注意到在角的位置就会产生稀疏性。相比之下，L2-ball 就没有这样的性质，因为没有角，所以第一次相交的地方出现在具有稀疏性的位置的概率就变得非常小
 
 ps:其实L1和L2范数的问题感觉解释的还不是很清楚，如果有朋友有更好的解释，欢迎留言交流~ 二面：几天后意外收到hr面，感谢vivo给的机会，这里也简单记录一下
