 三、MyBatis 的一级缓存和二级缓存有什么区别？实际开发中会使用吗？ 

 MyBatis 的一级缓存默认开启，作用范围是 SqlSession。简单来说，同一个 SqlSession 中，如果执行相同的查询，并且缓存没有失效，就可能直接从本地缓存取数据，不需要再次访问数据库。 

 但一级缓存也有局限，比如执行更新操作或者提交、回滚事务时，相关缓存会被清理，而且不同 SqlSession 之间不能共享。 

 二级缓存作用于 Mapper 的命名空间，可以在不同 SqlSession 之间共享，不过需要显式配置，并且要注意缓存失效和数据一致性问题。 

 我们实际开发中一般不会特别依赖 MyBatis 二级缓存，因为业务系统经常存在多个服务同时修改数据的情况，这时候缓存同步比较麻烦。对于访问频繁的数据，通常更倾向于使用 Redis，并配合过期时间和更新策略进行管理。 

 四、如果 Redis 缓存和 MySQL 数据不一致，你一般怎么处理？ 

 其实缓存和数据库不一致，在实际开发中挺常见的，尤其是多个请求同时读写同一条数据的时候。 

 比较常用的方案是 Cache Aside，也就是查询时先读缓存，缓存不存在再查数据库并回填；更新时先修改数据库，成功之后再删除对应的缓存，而不是直接同时更新两份数据。 

 但这里还有一个并发问题，比如线程 A 删除缓存后，线程 B 查询数据库并准备回填旧数据，随后可能把过期数据重新写进缓存。所以对一致性要求比较高的场景，还需要考虑并发控制、版本号或者基于消息队列的补偿机制。 

 另外，缓存通常会设置合理的 TTL，让异常情况下产生的不一致数据有机会自动过期。具体采用哪种方案，还得看业务能够容忍多长时间的数据延迟。 

 五、用户反馈某个业务提交页面非常卡顿，你会怎么排查？ 

 遇到这种问题，我一般不会直接认定是数据库慢，因为用户感觉页面卡顿，背后可能涉及浏览器、网络、后端接口甚至第三方服务。 

 可以先用浏览器开发者工具查看 Network，重点看提交请求有没有正常发送、接口耗时多少，以及具体卡在请求建立、等待响应还是数据下载阶段。如果接口耗时确实很长，再结合服务端日志和链路追踪定位。 

 比如之前排查过一个工单提交接口，发现主业务写库其实很快，真正耗时的是接口里同步调用了外部通知服务，而且没有合理设置超时时间。 

 后来把非核心通知逻辑改成异步处理，同时补上超时控制和失败重试，接口响应就稳定了很多。当然，异步化还得考虑消息丢失和重复消费，不能只顾着让接口返回得快。 

 六、MySQL 的 Explain 里面，type 字段有哪些常见值？有什么区别？ 

 Explain 里面的 type 反映的是 MySQL 访问数据的大致方式，常见的有 system、const、eq_ref、ref、range、index 和 ALL。 

 比如通过主键或者唯一索引进行等值查询，可能出现 const；关联查询中，如果被驱动表通过唯一索引匹配单条记录，可能出现 eq_ref；普通索引的等值查询通常可能出现 ref，而使用索引完成范围查找时则可能出现 range。 

 需要特别注意的是 index 和 ALL，前者通常意味着扫描整个索引，后者通常是全表扫描，两者都可能读取大量记录，只不过扫描的数据结构不同。 

 实际优化 SQL 时，不能单纯认为 type 越靠前就一定越快，还要结合 rows、filtered、Extra 和实际执行耗时判断，因为优化器选择的执行计划还受到数据分布、统计信息和查询成本影响。 

 七、如果一个接口被用户连续点击多次，导致重复提交数据，你会怎么解决？ 

 这种情况在订单提交、工单创建或者支付回调里面都比较常见，本质上要解决的是接口幂等性，也就是同一个业务请求重复执行，不应该产生重复的业务结果。
