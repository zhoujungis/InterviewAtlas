 3. 音乐播放资源如果放在本地，如何处理资源上限、打包分发和跨平台问题？ 

 音频资源不应全部无条件加载到内存，可以按照播放模式选择策略： 

 
 短音效直接加载到内存。 

 长音频采用流式读取。 

 高频访问资源使用有限容量的 LRU 缓存。 

 大文件使用异步预加载，避免阻塞 UI 线程。 

 资源文件通过版本号和哈希值校验完整性。 

 
 Qt 资源系统适合打包少量静态资源： 

 RESOURCES += resources.qrc
 
 如果音频较多或需要动态更新，可以将资源放在外部目录，通过安装器或更新器管理。跨平台时要注意： 

 
 路径分隔符不能手动拼接。 

 音频编码格式需要确认平台支持情况。 

 Windows、Linux、macOS 的音频输出设备处理不同。 

 发布包中要携带对应插件和动态库。 

 Qt 的插件搜索路径要经过验证。 

 
 4. 项目如果部署在服务端，如何设计部署架构？ 

 可以拆成网关、房间服务、匹配服务、状态存储和数据持久化几个部分。 

 网关负责连接管理、身份验证和协议转换；匹配服务负责将用户分配到房间；房间服务负责棋局状态、落子校验和超时判定。每个房间应尽量由单个逻辑线程或单个协程负责，避免多个线程同时修改棋盘。 

 棋局状态可以使用内存保存，并定期写入 Redis 或数据库。对于关键操作，需要保存落子日志，服务崩溃后可以通过日志恢复棋局。 

 部署时可以采用： 

 客户端
 -> 负载均衡
 -> WebSocket 网关
 -> 房间服务
 -> Redis / MySQL
 
 房间迁移是难点。不能简单地把请求随机转发给任意实例，可以通过一致性哈希、房间归属表或网关路由保证同一个房间的请求进入同一个服务实例。 

 5. 平时主要写 C++，有没有使用过 Python？掌握到什么程度？ 

 6. 函数式编程和面向对象编程有什么区别？ 

 面向对象编程围绕对象、状态和行为组织代码，通过封装、继承和多态表达复杂业务关系。函数式编程强调纯函数、不可变数据和函数组合，尽量减少共享状态和副作用。 

 C++ 支持两种风格的混合使用。例如，可以用类封装资源和生命周期，用纯函数完成数据转换： 

 std::vector transform(const std::vector & values) {
 std::vector result;
 result.reserve(values.size());

 for (int value : values) {
 result.push_back(value * value);
 }
 return result;
}
 
 在并发代码中，不可变数据和纯函数可以减少锁竞争。但完全避免状态并不现实，工程上通常根据模块特点选择合适的组织方式。 

 7. C++ 多态是如何实现的？虚函数表什么时候创建？ 

 C++ 多态主要分为编译期多态和运行时多态。 

 编译期多态包括函数重载、模板和运算符重载；运行时多态通常通过虚函数实现。当一个类包含虚函数时，编译器一般会为对象增加虚函数表指针，对象通过该指针找到对应的虚函数表，再根据实际类型调用目标函数。 

 class Parser {
public:
 virtual ~Parser() = default;
 virtual void parse() = 0;
};

class JsonParser : public Parser {
public:
 void parse() override {}
};
 
 标准并没有规定虚函数表必须以某种形式实现，但主流编译器通常采用类似机制。构造函数和析构函数期间，虚函数调用不会按照最终派生类的多态行为执行，因为对象此时尚未完成或已经开始销毁。 

 8. 函数重载和函数重写有什么区别？编译器如何处理重载？ 

 函数重载发生在同一个作用域或相关作用域内，函数名相同但参数列表不同，属于编译期多态。返回值不同不能单独构成重载。 

 函数重写发生在派生类中，派生类重新实现基类的虚函数，属于运行时多态。建议使用 override 明确告诉编译器这是一次重写： 

 class Base {
public:
 virtual void run(int value);
};

class Derived : public Base {
public:
 void run(int value) override;
};
 
 编译器会根据函数名、参数类型、参数数量和限定符生成重载决议结果。 const 、引用限定符等也可能影响函数签名匹配。 

 9. 栈和堆的区别是什么？局部变量一定在栈上吗？ 

 栈通常由线程自动管理，分配和释放速度快，但空间有限，适合函数调用帧和生命周期明确的局部对象。堆由动态内存分配器管理，生命周期更灵活，但需要承担分配、释放和碎片管理成本。 

 局部变量通常放在栈上，但并非绝对： 

 
 编译器可能进行寄存器分配。 

 逃逸分析可能改变对象存储位置。 

 优化后对象可能被消除。 

 全局和静态变量通常位于静态存储区。 

 new 创建的对象位于动态存储区。 

 
 void example() {
 int value = 10;
 int* ptr = new int(20);
 delete ptr;
}
 
 实际开发中应优先使用自动对象和智能指针，避免裸指针承担所有权。 

 10. 如何判断一个类是否适合使用移动语义？ 

 如果类管理独占资源，例如文件描述符、锁、缓冲区或动态内存，移动语义通常可以避免深拷贝。 

 移动构造和移动赋值应当： 

 
 转移资源所有权。 

 将源对象置于有效但未指定状态。 

 保证不会重复释放资源。 

 尽量声明为 noexcept 。 

 
 class Buffer {
public:
 Buffer(Buffer&& other) noexcept
 : data_(other.data_), size_(other.size_) {
 other.data_ = nullptr;
 other.size_ = 0;
 }

private:
 char* data_ = nullptr;
 std::size_t size_ = 0;
};
 
 如果类中包含互斥量、引用成员或不可移动成员，就不能简单地默认生成移动操作。还要遵循五法则或零法则，避免拷贝、移动和析构行为互相矛盾。 

 11. 四种智能指针分别解决什么问题？ 

 unique_ptr 表示独占所有权，不能拷贝，只能移动，适合对象由一个管理者负责释放的场景。 

 shared_ptr 表示共享所有权，通过引用计数管理对象生命周期，适合多个对象共同持有资源的场景，但存在控制块开销和循环引用风险。 

 weak_ptr 不拥有对象，不增加强引用计数，通常用于观察对象或打破 shared_ptr 循环引用。 

 auto_ptr 已经被 C++11 弃用并在 C++17 移除，因为复制时会转移所有权，容易导致源对象状态异常。 

 auto owner = std::make_unique (10);
auto shared = std::make_shared (20);
std::weak_ptr observer = shared;
 
 智能指针并不意味着自动线程安全。多个线程同时操作同一个 shared_ptr 变量仍需要同步，只是不同 shared_ptr 实例共同管理同一控制块时，引用计数操作通常是线程安全的。 

 12. map 和 unordered_map 的底层结构有什么区别？红黑树如何维持平衡？ 

 map 通常基于红黑树，元素按键有序，查找、插入和删除复杂度为 O(log n) 。 unordered_map 通常基于哈希表，平均查找复杂度为 O(1) ，但最坏情况可能退化到 O(n) 。 

 红黑树通过颜色约束保证最长路径不会超过最短路径的两倍，主要规则包括： 

 
 每个节点只能是红色或黑色。 

 根节点是黑色。 

 空节点视为黑色。 

 红色节点不能有红色子节点。 

 从任意节点到其所有后代空节点的黑节点数相同。 

 
 插入和删除后可能通过旋转和重新着色恢复约束。红黑树不追求严格平衡，但可以在维护成本和树高之间取得平衡。 

 13. unordered_map 的负载因子过高会发生什么？ 

 负载因子通常定义为： 

 load_factor = 元素数量 / 桶数量
 
 负载因子过高会导致冲突增加，查找和插入的平均复杂度恶化。容器可能触发 rehash，重新分配桶并重新计算元素位置。 

 std::unordered_map table;
table.reserve(100000);
table.max_load_factor(0.7f);
 
 rehash 会使迭代器失效，因此不能在持有迭代器期间进行可能触发扩容的操作。对于攻击者可控的 Key，还需要关注哈希碰撞攻击，可以使用更安全的哈希函数或限制输入规模。 

 14. Qt 中线程安全的信号槽连接是如何工作的？ 

 跨线程连接通常使用队列连接。发送信号的线程不会直接执行接收槽函数，而是将调用封装成事件投递到接收对象所属线程的事件队列中。 

 connect(worker, &Worker::finished,
 widget, &Widget::onFinished,
 Qt::QueuedConnection);
 
 接收对象必须有正确的线程归属，并且目标线程需要运行事件循环。跨线程传递的自定义类型要注册元类型： 

 Q_DECLARE_METATYPE(DeviceState)
qRegisterMetaType ("DeviceState");
 
 如果使用 DirectConnection ，槽函数会在发送线程执行，容易造成线程安全问题。使用队列连接时，参数通常会被复制或移动到事件中，因此要避免传递悬空引用和生命周期不明确的裸指针。 

 15. Qt 如何创建线程？ QThread 本身和工作对象分别运行在哪个线程？ 

 常见方式是创建 QThread ，再将工作对象通过 moveToThread 移动到目标线程： 

 QThread* thread = new QThread;
Worker* worker = new Worker;

worker->moveToThread(thread);

QObject::connect(thread, &QThread::started,
 worker, &Worker::run);
QObject::connect(worker, &Worker::finished,
 thread, &QThread::quit);
QObject::connect(thread, &QThread::finished,
 worker, &QObject::deleteLater);

thread->start();
 
 QThread 对象本身属于创建它的线程，真正执行工作的是它管理的线程。直接继承 QThread 并重写 run 也可以，但容易把线程控制和业务逻辑混在一起。 

 如果工作对象需要接收队列信号，目标线程必须有事件循环。停止线程时应采用协作式退出，不应直接强制终止，否则可能造成锁未释放、资源状态不完整和数据损坏。 

 16. 多线程资源竞争如何保证数据安全？ 

 首先要明确共享数据的所有权和访问边界，再选择同步工具： 

 
 std::mutex ：保护一般共享状态。 

 std::shared_mutex ：读多写少。 

 std::atomic ：简单独立变量。 

 std::condition_variable ：等待状态变化。 

 Qt 的 QMutex 、 QReadWriteLock ：Qt 工程中的对应工具。 

 
 std::mutex mutex;
std::condition_variable condition;
std::queue queue;

void push(int value) {
 {
 std::lock_guard lock(mutex);
 queue.push(value);
 }
 condition.notify_one();
}

int pop() {
 std::unique_lock lock(mutex);
 condition.wait(lock, [] {
 return !queue.empty();
 });

 int value = queue.front();

 3. 这个项目为什么使用 WebSocket，而不是普通 HTTP？ 

 HTTP 更适合请求—响应模型，例如查询设备列表、提交配置和获取历史记录。实时监控场景中，服务端需要主动把状态变化推送给客户端，如果只使用 HTTP，就需要客户端轮询，轮询间隔过短会增加请求量，过长又会造成状态延迟。 

 WebSocket 在完成握手后会建立全双工长连接： 

 HTTP Upgrade 请求
 ↓
WebSocket 握手成功
 ↓
客户端和服务端双向发送消息
 
 选择 WebSocket 主要是因为： 

 
 服务端可以主动推送。 

 不需要频繁建立 HTTP 请求。 

 支持双向通信。 

 适合状态变化、告警和任务进度推送。 

 
 但 WebSocket 不代表连接永远可靠，还需要设计心跳、超时、重连、消息序号和断线补偿机制。连接恢复后，客户端不能只等待下一条消息，而应该携带最后一次收到的序列号，让服务端补发缺失事件。 

 4. WebSocket 长连接建立时如何控制机器资源？如何避免连接泄漏？ 

 服务端需要对连接数、握手超时、空闲时间、单连接缓存和消息大小进行限制。 

 可以设置： 

 
 最大连接数。 

 单 IP 连接数。 

 握手超时时间。 

 心跳间隔和响应超时时间。 

 单帧最大长度。 

 单连接待发送队列长度。 

 每个用户允许的最大连接数。 

 
 连接对象应由明确的所有者管理，关闭流程需要保证从事件循环、连接表、用户会话表和待发送队列中全部移除。 

 class Connection : public std::enable_shared_from_this {
public:
 void close() {
 if (closed_) return;
 closed_ = true;

 stopHeartbeat();
 removeFromConnectionTable();
 socket_.shutdown();
 }

private:
 bool closed_ = false;
};
 
 如果服务端只关闭 Socket，却没有删除连接管理表中的对象，可能造成逻辑连接泄漏。反过来，如果先释放对象，再有异步回调访问它，则会出现 Use-After-Free。因此异步回调通常应使用弱引用或带生命周期管理的上下文对象。 

 5. WebSocket 前端使用原生 JavaScript 还是第三方方案？如果要修改，如何保证兼容？ 

 如果功能简单，可以使用浏览器原生 WebSocket；如果项目需要统一重连、消息分发、心跳、鉴权和状态管理，可以在原生 API 外封装一层连接管理器。 

 class SocketClient {
 constructor(url) {
 this.url = url;
 this.retry = 0;
 this.connect();
 }

 connect() {
 this.socket = new WebSocket(this.url);

 this.socket.onopen = () => {
 this.retry = 0;
 this.send({type: "resume", seq: this.lastSeq || 0});
 };

 this.socket.onmessage = event => {
 const message = JSON.parse(event.data);
 this.lastSeq = message.seq;
 this.dispatch(message);
 };

 this.socket.onclose = () => {
 const delay = Math.min(30000, 1000 * 2 ** this.retry++);
 setTimeout(() => this.connect(), delay);
 };
 }

 send(data) {
 if (this.socket.readyState === WebSocket.OPEN) {
 this.socket.send(JSON.stringify(data));
 }
 }

 dispatch(message) {}
}
 
 修改协议时要增加版本号，不能直接改变旧字段的含义。新增字段应尽量保持向后兼容，服务端需要兼容旧客户端一段时间。对于无法兼容的变更，应通过 URL、协议头或消息版本进行区分。 

 6. 音乐播放器中，音频播放线程、解码线程和 UI 线程应该如何协作？ 

 UI 线程只负责控制操作和展示状态，例如播放、暂停、进度条和音量调整。解码线程负责读取文件、解析音频数据并生成 PCM，播放线程负责将 PCM 数据写入音频设备。 

 线程之间不能直接共享一个不断变化的缓冲区而不加同步。通常可以设计环形缓冲区： 

 解码线程 -> PCM 环形缓冲区 -> 播放线程 -> 音频设备
 
 解码线程写入数据时检查剩余空间，播放线程读取数据时检查可读数量。缓冲区为空时，播放线程等待；缓冲区过满时，解码线程暂时阻塞或降低读取速度。 

 Qt 中可以通过信号槽将播放进度发送给 UI： 

 emit positionChanged(currentPosition);
 
 信号只负责通知，不应在 UI 槽函数中执行解码、文件扫描或音频格式转换。 

 7. Qt 中的线程安全规范应该如何制定？ 

 首先需要规定对象归属：一个 QObject 通常只能由所属线程访问，跨线程调用应使用队列连接或明确的同步机制。 

 常见规范包括： 

 
 UI 控件只能在主线程操作。 

 业务对象只在所属线程访问。 

 不在线程之间传递裸引用。 

 共享容器必须明确加锁或改为消息传递。 

 不在析构函数中阻塞等待不确定的异步任务。 

 线程退出前停止定时器、Socket 和后台任务。 

 通过 deleteLater 在对象所属线程销毁 QObject。 

 
 connect(worker, &Worker::finished,
 worker, &QObject::deleteLater,
 Qt::QueuedConnection);

connect(thread, &QThread::finished,
 thread, &QObject::deleteLater);
 
 线程安全不只是给代码加一把锁，还包括对象生命周期、事件循环、退出顺序和异常传播。 

 8. 如何设计一个可靠的 TCP 二进制协议？ 

 协议头中至少应该包含魔数、版本号、消息类型、序列号、负载长度和校验信息。 

 魔数 | 版本 | 类型 | 序列号 | Payload长度 | Payload | CRC
 
 解析过程不能假设一次 recv 就能拿到完整消息，应维护连接级缓冲区： 

 
 缓冲区长度不足固定头时继续读取。 

 解析 Payload 长度。 

 对长度做上限校验。 

 缓冲区未达到完整消息长度时继续等待。 

 收到完整消息后校验 CRC。 

 解析并移除已处理字节。 

 
 协议字段要明确大小端，不能直接把 C++ 结构体强制转换为字节流，因为可能存在内存对齐、填充、字节序和 ABI 差异。 

 std::uint32_t readUint32BE(const std::uint8_t* data) {
 return (static_cast (data[0]) (data[1]) (data[2]) (data[3]);
}
 
 9. HTTP GET 和 POST 在协议、语义和数据结构上有哪些差异？ 

 GET 通常用于获取资源，参数经常放在 URL 查询字符串中；POST 通常用于提交数据，数据放在请求体中。 

 区别不只是参数位置： 

 
 GET 通常具有更强的幂等性。 

 GET 请求可能被浏览器、代理或缓存系统缓存。 

 POST 通常用于创建、提交或触发业务操作。 

 GET URL 长度受客户端和服务器限制。 

 POST 请求体可以承载更复杂的数据。 

 两者都可以携带请求头和请求体，但语义不同。 

 
 如果 POST 操作可能被重试，就需要引入幂等键，否则网络超时后客户端无法判断服务端是否已经成功执行，重复重试可能产生重复订单、重复任务等问题。 

 10. C++ 项目中如何设计错误处理机制？ 

 错误处理应区分可恢复错误、业务错误、系统错误和程序缺陷。 

 常见方式包括： 

 
 返回错误码。 

 使用 std::optional 表示结果可能不存在。 

 使用 std::expected 风格类型携带错误信息。 

 对真正异常的情况使用异常。 

 对不可恢复错误记录上下文并终止或隔离。 

 
 错误信息不能只写“failed”，应包含请求 ID、模块、错误码、底层原因和关键参数。 

 enum class ErrorCode
