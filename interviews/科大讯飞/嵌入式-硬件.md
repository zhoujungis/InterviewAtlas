 2. 项目中 MCU 是如何选型的？你会重点考虑哪些指标？CPU 主频和 RAM/Flash 是不是越大越好？

 回答思路：

 
 按照：功能需求 → 性能 → 外设 → 内存 → 功耗 → 成本 → 生态与供应链几个方面综合考虑。

 
 首先看功能和外设资源，比如项目需要多少路 UART、SPI、I2C、CAN、ADC、PWM，以及是否需要 USB、Ethernet、DMA 等。实际选型时，外设资源是否满足需求往往比单纯看主频更加重要。

然后看 CPU 性能。根据任务复杂度判断需要什么级别的内核、主频以及是否需要 FPU、DSP 等。如果只是简单的传感器采集和控制，没有必要为了高主频选择性能过剩的 MCU。

接下来是 RAM 和 Flash：
Flash 主要看代码、常量、升级分区等是否放得下；
RAM 要考虑全局变量、Buffer、任务栈、堆、DMA 缓存等；
还要预留一定余量，不能刚好够用。
RAM 也不是越大越好，而是满足需求并留出合理余量。

然后是功耗。如果是电池供电设备，就要重点考虑运行电流、睡眠电流、低功耗模式、唤醒时间等。主频提高通常也会带来更高的动态功耗，因此性能和功耗需要做权衡。

最后还要考虑：
成本
封装和 IO 数量
工作温度
开发工具和 SDK
芯片供货稳定性
团队已有技术积累

 6. 你项目里面创建了哪些任务？为什么要这么划分？

 回答思路： 可以根据自己的项目实际想一想这个问题。 

 划分原则：

 实时性要求不同的功能尽量分开；
阻塞操作不要放在高实时性任务里面；
一个任务尽量负责一个相对独立的功能；
任务之间通过队列、通知、信号量等机制通信，而不是大量共享全局变量。

 
 7. 项目中任务之间是怎么通信的？讲一讲用过哪些 API？

 回答思路：根据不同场景选择不同机制。队列：传递数据。 xQueueCreate() xQueueSend() xQueueReceive() xQueueSendFromISR() 比如采集任务把传感器数据放进队列，数据处理任务再取出来。

 信号量：同步事件。 xSemaphoreCreateBinary() xSemaphoreGive() xSemaphoreTake() xSemaphoreGiveFromISR() 例如 DMA 完成以后通知处理任务。

 Mutex：保护共享资源。 xSemaphoreCreateMutex() xSemaphoreTake() xSemaphoreGive() 比如多个任务需要访问同一个 UART/SPI 设备。

 Task Notification：轻量级任务通知。 xTaskNotify() xTaskNotifyFromISR() xTaskNotifyWait() ulTaskNotifyTake() 如果只是 “通知某个任务有事件发生”，Task Notification 通常比专门创建一个队列更加轻量。

 ① FreeRTOS 默认是什么调度方式？

 最常见的是：

 #define configUSE_PREEMPTION 1
#define configUSE_TIME_SLICING 1

 
 也就是：

 
 抢占式调度 + 时间片轮转。 在这种配置下，调度器优先选择 最高优先级的 Ready 任务 运行；如果最高优先级下存在多个 Ready 任务，则默认会通过时间片在同优先级任务之间轮转。

 
 ② configUSE_PREEMPTION 有什么作用？

 它控制是否开启 抢占式调度 。

 #define configUSE_PREEMPTION 1

 
 表示开启抢占。例如：

 Task A：优先级 2，正在运行

 ↓
 B变成Ready
 ↓
 B抢占A

 #define configUSE_PREEMPTION 0

→ 高优先级Ready任务可以抢占当前任务
PREEMPTION = 0
→ 当前任务主动让出CPU为主

## 科大讯飞嵌入式软件开发二面 面经

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-09-14 ｜ [原文链接](https://www.nowcoder.com/discuss/928916509336797184)

1. 面试官指出你项目里某段实现不合理，你会怎么回应，并举例说明你后来会怎么改？

 
 先确认他指出的具体问题：正确性、实时性、可维护性，还是资源占用。

 如果当时是权衡取舍，就讲清楚约束：deadline、芯片资源、联调时间。

 承认不合理点时直接说影响面，例如无超时、无背压、临界区过长。

 给出改进方案：加超时与重试上限、队列限流、把重活移出中断、补单测和压测。

 补充验证标准：异常注入后能否恢复、最坏延迟、长时间跑是否稳定。

 
 2. TCP通信里，服务端被动打开和客户端主动连接的调用顺序分别是什么？中间失败怎么处理？

 
 服务端： socket → bind → listen → accept → recv/send → close 。

 客户端： socket → connect → send/recv → close 。

 bind 失败常见端口占用或权限问题； listen 后要设合理 backlog。

 connect 失败要区分超时、拒绝、路由不可达，并做有限次退避重试。

 accept 后每个连接独立处理，注意 EINTR 、半关闭和 close 前排空数据。

 
 3. memmove 和 memcpy 怎么选？自己实现拷贝时如何判断重叠？

 
 确定不重叠用 memcpy ，可能重叠用 memmove 。

 重叠判断看区间关系：若 dst 落在 src 到 src+n 内，从前往后拷会破坏未读数据。

 重叠且 dst > src 时应从尾到头拷； dst < src 时可从头到尾。

 还要注意空指针、长度为0、对齐和字宽优化，但正确性优先于炫技优化。

 业务里对用户输入长度要先校验，避免越界把相邻对象踩坏。

 
 4. 你做过最难啃的一个技术问题是什么？卡点、突破口和结果分别是什么？

 
 卡点通常不是语法，而是偶现问题：时序竞争、缓存一致性、资源寿命管理。

 我的做法是先稳定复现：最小用例、日志时间戳、示波器/逻辑分析仪对照。

 突破口往往来自缩小变量：单任务跑、关优化、固定输入、对比好坏版本 diff。

 解决后会补防护：断言、看门狗、超时、状态机非法迁移检测。

 最后沉淀文档，避免同类问题再次靠“感觉”排查。

 
 5. 在Linux上做过最头疼的一次环境/权限/设备节点问题是什么，你怎么定位？

 
 常见是设备节点权限、驱动未加载、设备树不匹配导致 /dev 不出现。

 先看 dmesg 和驱动加载日志，确认探针是否成功。

 再用 ls -l /dev 、 udevadm 、组权限确认应用能否打开设备。

 若偶现，查电源时序、复位脚、时钟是否在打开前就绪。

 最终把依赖写进启动脚本或 systemd 单元，并加上失败可观测日志。

1. 简单做一下自我介绍，并说明为什么投嵌入式软件开发？

 
 我是XX学校计算机/电子相关专业，主力方向是嵌入式软件，熟悉C、STM32、RTOS和基础驱动。

 实习/项目里做过板级bring-up、外设驱动和业务联调，能独立把需求落到可运行固件。

 投嵌入式是因为更喜欢贴近硬件的问题定位：寄存器、时序、中断和资源约束都能直接验证。

 也关注语音/IoT类产品，希望在科大讯飞这类场景里把稳定性和功耗做得更好。

 
 2. 实习里印象最深的一次排障是什么？你怎么定位并闭环的？

 
 现象是某模块偶发卡死，复现不稳定，日志也不完整。

 先缩小范围：确认是任务饿死、死锁，还是外设中断异常；用LED/GPIO打点和串口时间戳分段。

 再抓关键证据：看任务栈水位、互斥锁持有关系、中断开关配对、DMA完成标志是否丢失。

 根因通常落在超时策略缺失或中断里做了过重操作；修完后补压力测试和看门狗保护。

 最后沉淀成checklist：异常路径必有超时、关键路径必可观测。

 
 3. 挑一个你最熟的项目，讲整体架构，以及你负责模块和其他模块怎么协作？

 
 项目按层拆：板级启动/驱动层、中间件（队列/协议）、业务应用层。

 我负责的模块对外只暴露少量接口，例如 init、start、push_data、get_status，隐藏寄存器细节。

 与其他模块通过消息队列或环形缓冲交互，避免直接共享大量全局变量。

 关键共享资源用互斥或关中断保护，并规定谁是生产者、谁是消费者、超时怎么处理。

 联调时先单模块自测，再做端到端：上电、通信、异常断电、长时间跑稳。

 
 4. 下面写法有什么问题？ uint8_t mask = ~0x01; 在不同平台上可能怎样？更稳妥怎么写？

 
 0x01 默认是有符号 int ， ~0x01 先按整型取反，再赋给 uint8_t 时会发生截断，结果依赖整型宽度和符号规则，可读性差。

 目标如果是“只清最低位对应的8位掩码”，应明确宽度： uint8_t mask = (uint8_t)~((uint8_t)0x01); 或 uint8_t mask = 0xFEu; 。

 做位操作时优先统一无符号类型，并写清位宽意图，避免隐式整型提升带来歧义。

 代码评审里这类问题常表现为“本机能过、换MCU位宽后行为怪异”。

 
 5. 实现一个安全一点的交换宏 SWAP(a,b) ，并说明常见坑。

 
 朴素写法 #define SWAP(a,b) do{ typeof(a) t=(a); (a)=(b); (b)=t; }while(0) （或C用临时变量函数）可避免 if 悬挂问题。

 若写成 #define SWAP(a,b) {int t=a; a=b; b=t;} ，类型写死、作用域和分号场景都容易踩坑。

 参数有副作用时，如 SWAP(arr[i++], arr[j++]) ，宏展开会重复求值，结果未定义或逻辑错误。

 面试里更稳妥的回答是：简单场景可用宏，复杂/有副作用场景用 static inline 函数。

 还要注意类型是否兼容、是否需要 volatile 访问语义。

 
 6. 给定 uint32_t reg ，如何把 bit2~bit4 改成 0b101 ，同时不影响其他位？

 
 先清除目标域： reg &= ~(0x7u << 2); 

 再写入新值： reg |= (0x5u << 2); 

 合并写成： reg = (reg & ~(0x7u << 2)) | (0x5u << 2); 

 移位和掩码用无符号常量，避免有符号右移/整型提升问题。

 若对应硬件寄存器，通常用读改写，并确认该域是否有写1清0等特殊语义。
