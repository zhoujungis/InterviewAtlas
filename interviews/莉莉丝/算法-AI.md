## 简历中写了RAG/Agent项目，如何更能体现出自己的优势

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-06-21 ｜ [原文链接](https://www.nowcoder.com/discuss/898117229852585984)

大家好，我是阿不达。

 先介绍一下自己，我来自郑州大学，28届研究生在读，从去年初开始把主要精力都放在Agent相关的项目上，近半年陆续参加了美团、字节、莉莉丝等公司的面试，目前已拿到字节的日常offer。这篇文章想和大家聊聊我在简历优化上踩过的坑和总结的经验。

 最近有不少同学和牛牛发私信给我，想让我帮他们看看简历。看了十几份之后，我发现一个特别普遍的问题：大家简历上虽然都写了RAG或Agent项目，但很多情况下只是在平铺直叙，并没有真正展示出该有的技术深度。换句话说，就是没让人眼前一亮的感觉。

 

 其实很多时候不是大家的能力不行，而是写简历的时候没把自己的优势体现出来。今天结合我自己的经验，给大家分享几个建议。

 问题一：技术亮点没有前置，埋在细节里

 很多同学写项目经历时，习惯按时间线平铺：项目背景 → 技术栈 → 实现过程 → 最后成果。

 可是面试官在筛选简历的时候有时候可能只有几十秒的时间，就像高考阅卷一样，如果核心技术能力没有在第一时间展示出来，很可能就直接被pass掉了。

 

 我们距离来说：

 不好的写法

 
 智能客服系统（2024.03 - 2024.06） 

 项目背景：为公司开发了一个基于大模型的智能客服系统，支持多轮对话和知识库问答。

 技术栈：Spring Boot、Vue、DeepSeek、Elasticsearch

 实现内容：实现了文档上传、向量检索、对话生成等功能，支持用户自定义知识库。

 
 面试官看完：这不就是调个API吗？

 更好的写法

 RAG智能客服系统（2024.03 - 2024.06） | 核心开发

 项目描述 ：基于大模型的企业级智能客服系统，完整实现检索增强生成（RAG）链路和ReAct Agent工具调用能力

 技术实现 ：

 
 文档处理链路：Apache Tika多格式解析（PDF/Word/Excel等10+种）→ 语义分块（512 tokens/块，50 tokens重叠）→ BGE-M3向量化

 混合检索优化：向量检索 + BM25全文检索 + RRF融合算法，Recall@5从0.42优化至0.68（提升62%）

 Agent工具调用：实现ReAct模式（Reasoning → Action → Observation循环），集成知识库检索、订单查询、工单创建等5个工具

 评估体系：建立200条Golden Set，TopK参数调优（5→10），MRR指标提升15%

 
 技术栈 ：Spring Boot、DeepSeek V3、Elasticsearch、MinIO、Apache Tika、BGE-M3

 项目成果 ：知识库问答准确率85%+，工具调用成功率92%，日均处理咨询2000+次，人工客服工作量降低60%

 对比一下：标题直接点明“完整实现检索增强生成链路”，第一眼就能看到RAG、ReAct、混合检索这些关键词。用Recall@5、MRR、TopK这些RAG领域的标准评估指标说话。从文档解析 → 分块 → 检索 → 生成，每个环节都有技术细节。

 

 面试官一看就能判断：你是真的懂RAG，而不是简单的在套壳。

 问题二：泛泛而谈，缺乏技术深度

 第二个常见问题：只写做了什么，不写怎么做的。

 比如“实现了Agent工具调用”、“优化了检索效果”，这些其实都是结果，但面试官更想知道你的技术思路和实现细节。

 举个例子：Agent记忆系统

 泛泛而谈的写法：

 
 实现了Agent的记忆功能，支持多轮对话上下文管理。

 
 更好的写法（就拿我这两天学习二哥的PaiCli项目为例，如果你凑巧阅读了源码，然后又凑巧写出了下面这段话，我相信即使面对面试官追问拷打，你也可以完全不怵）：

 Agent记忆系统设计与实现 

 架构设计 ：三层记忆 + 上下文压缩 + 智能检索

 技术实现 ：

 
 短期记忆管理：实现4种记忆类型（对话/事实/摘要/工具结果），超出token阈值时自动淘汰最旧条目，保留压缩摘要待重新注入上下文

 长期记忆持久化：JSON文件存储 + Agent启动自动加载，实现内容去重和关键词检索，跨会话保留用户偏好和项目信息

 上下文压缩优化：采用Map-Reduce策略分片摘要后合并，保留最近3轮完整消息不参与压缩，支持自动提取关键事实到长期记忆

 智能检索排序：基于IKAnalyzer分词 + 关键词匹配 + 时间衰减 + 来源加权的检索算法

 
 技术栈 ：Java、Jackson（JSON处理）、IKAnalyzer（中文分词）、LLM API

 成果 ：上下文压缩率60%+，长期记忆召回准确率85%+，多轮对话质量提升40%

 第二种写法的优势很明显：三层记忆的设计思路清晰，自动压缩、JSON文件持久化、检索注入这些都是可以深入聊的技术点，而且考虑了token预算、质量保证这些工程化问题。

 

 再举个例子：RAG分块策略

 泛泛而谈：

 
 实现了文档分块功能，支持多种文档格式。

 
 更好的写法：

 RAG代码分块与检索优化 

 能力设计 ：多粒度代码分块 + 关系图谱构建 + 混合检索策略

 技术实现 ：

 
 智能分块：基于JavaParser进行AST解析，支持文件/类/方法三种粒度，平均块大小512 tokens，类级别块包含方法签名但不含方法体（避免单块过大）

 关系图谱：提取extends/implements/imports/calls关系，存储在SQLite，支持依赖追踪和关联检索

 混合检索：精确检索（grep）+ 语义检索（search_code）结合，长上下文模式下topK动态调整至20

 向量化：使用BGE-M3模型进行代码embedding，支持跨语言语义理解

 
 技术栈 ：JavaParser、SQLite（关系图谱）、Elasticsearch（向量检索）、BGE-M3

 成果 ：代码检索准确率78%+，检索响应时间 < 200ms，支持10万+代码文件索引

 技术选型有理有据：JavaParser、AST解析，不是简单的文本切分。而且考虑了实际问题：类级别块太大怎么办？关系图谱有什么用？精确定位优先，语义检索辅助，这是真正用过RAG的人才会总结出来的经验。

 问题三：只写单点功能，缺乏完整技术链

 第三个问题：写了一堆技术点，但看不出完整的技术链路。

 面试官想看的不是你会多少个技术，而是你能不能把这些技术串起来，解决一个完整的问题。

 举个例子：Multi-Agent协作系统

 很多同学会写“实现了多智能体协作”，但如果你学过PaiCLI的Multi-Agent设计，就会知道这不是简单的“多个Agent一起工作”。

 只写单点功能：

 
 实现了多智能体协作，包括任务规划、任务执行、结果审查等功能。

 
 展示完整技术链：

 Multi-Agent协作系统设计 

 协作架构 ：用户输入 → Planner拆解（DAG依赖图）→ AgentOrchestrator分配 → Worker并行执行 → Reviewer质量审查 → 返回结果

 实现细节 ：

 
 Planner（规划者）：任务拆解 + 拓扑排序生成执行计划，支持依赖关系识别

 Worker（执行者）：共享工具集（文件操作/代码检索/测试执行），独立任务按批次并行

 Reviewer（审查者）：质量审查 + 问题反馈，未通过时自动重试（最多2次）

 
 工程化设计 ：

 
 主从架构（AgentOrchestrator主控），冲突自动解决（文件级锁）

 DAG并行调度：独立任务并行，依赖任务串行，平均执行时间减少50%

 
 技术栈 ：Java 17、Spring Boot、LLM API（GLM-5/DeepSeek V4）、SQLite

 项目成果 ：复杂任务完成质量提升40%，错误率降低35%，单任务平均耗时从8分钟降至4分钟

 从任务拆解 → 并行执行 → 质量检查，每个环节都清晰。三角色分工、主从架构、DAG依赖，展示了系统设计思维。冲突解决、并行优化、质量保证，这些都是实际落地需要考虑的问题。

 再举个例子：Plan-and-Execute模式

 只写功能点：

 
 实现了任务规划功能，支持复杂任务的自动拆解和执行。

 
 展示完整技术链：

 Plan-and-Execute任务编排系统 

 项目描述 ：基于DAG的智能任务规划与并行执行系统，支持复杂多步骤任务的自动拆解和依赖管理

 设计思路 ：先整体规划，再按依赖顺序执行（对比ReAct的“边走边看”模式）

 技术实现 ：

 
 智能规划：Planner调用LLM进行任务拆解，生成DAG依赖图并使用拓扑排序确定执行顺序，避免无关步骤扩展

 并行执行：独立任务按批次并行执行（复用工具层的并行能力），有依赖关系的任务串行处理，平均执行效率提升55%

 动态调整：支持用户确认前补充要求并重新规划，执行完成后自动切回ReAct模式保持灵活性

 任务编排：PlanExecuteAgent负责批次调度，支持任务失败回滚和重试机制

 
 技术栈 ：Java、Spring Boot、LLM API（GLM-5/DeepSeek V4）、拓扑排序算法

 适用场景 ：多步骤、有依赖关系的复杂任务（如模块迁移、系统重构）

 成果 ：复杂任务拆解准确率90%+，并行执行效率提升55%，任务失败率降低40%

 明确技术选型的理由：Plan-and-Execute vs ReAct，什么时候用哪个。DAG依赖、拓扑排序、并行执行，每个技术点都能展开聊。避免无关步骤、自动切换模式，展示了对Agent设计的理解。

 

 问题四：缺乏安全和工程化考虑

 很多同学写Agent项目时，只关注功能实现，忽略了安全性和工程化。

 但实际上，一个真正落地的Agent系统，安全控制和工程化能力是面试官非常看重的。

 举个例子：Agent安全控制

 如果你学过PaiCLI的HITL（Human-in-the-Loop）设计，就会知道Agent的安全不仅仅是“弹个框确认”。

 只提功能：

 
 实现了工具调用审批功能，危险操作需要用户确认。

 
 展示完整安全架构：

 Agent安全控制系统（HITL + 多层防护） 

 项目描述 ：企业级Agent安全控制体系，实现从审批、拦截到审计的完整安全链路

 四层防护架构 ：

 
 
 HITL审批机制

 
 危险操作静态规则识别（write_file/execute_command/create_project/revert_turn）

 三级危险等级分类：高危（execute_command）、中危（write_file）、安全

 审批决策支持：批准/全部放行/拒绝/跳过/修改参数后执行

 

 
 路径围栏（PathGuard）

 
 文件类工具强制限定在项目根目录内，拦截绝对路径外逃、 .. 穿越、符号链接逃逸

 基于白名单机制，支持配置化路径规则

 

 
 命令黑名单（CommandGuard）

 
 HITL之前的fast-fail拦截层，拦截高危命令：sudo、rm -rf /*、mkfs、dd of=/dev、fork bomb、curl|sh等

 支持正则匹配和动态更新

 

 
 审计日志（AuditLog）

 
 危险工具调用按天写入JSONL格式到~/.paicli/audit/

 记录outcome（allow/deny/error）和approver（hitl/policy/none）

 审计参数自动脱敏（token/key/password/Authorization）

 

 
 

 工程化设计 ：

 
 MCP动态工具默认走HITL审批和审计流程

 路径校验和命令拒绝在HITL之前执行，减少无效审批次数70%+

 支持审批策略配置化和热更新

 
 技术栈 ：Java、Jackson（日志序列化）、正则引擎、文件系统API

 成果 ：成功拦截95%+高危操作，审计日志覆盖率100%，误拦率 < 2%

 四层防护，不是简单的弹窗确认。审计日志、参数脱敏、快速拒绝，考虑了实际落地的细节。分层设计，每层有明确职责。

 总结：如何让简历体现技术优势

 回到最开始的问题：

 
 简历上写了RAG/Agent项目，如何更能体现出自己的优势？

 
 我总结了四个建议：

 
 
 技术亮点前置，让面试官秒懂你的深度 

 别按时间线平铺流水账。把技术细节放在标题和前三行，用专业术语（RAG、ReAct、DAG、HITL、混合检索）直接说明你做了什么。

 
 用技术细节替代泛泛而谈 

 不要只写“实现了XXX功能”。写清楚“使用XXX技术实现YYY，解决了ZZZ问题，指标提升了多少”。架构设计、技术选型、工程化考虑、量化成果，这些才是面试官想看的。

 
 展示完整技术链，不是单点功能堆砌 

 别只列举技术栈：Spring Boot、Vue、DeepSeek、Elasticsearch。串起完整链路：文档解析 → 分块 → embedding → 检索 → 重排 → 生成 → 评估优化。让面试官看到你能端到端解决问题，不只是调API。

 
 体现安全和工程化能力 

 不要只写功能实现。写安全控制（HITL、路径围栏、审计日志）、性能优化（并行执行、上下文压缩）、可扩展性（MCP协议、Skill系统）。

 

 最后

 如果你正在准备秋招，或者简历上有RAG/Agent项目，建议：

 
 拿出你的简历，对照上面的建议，逐条优化。

 去学一个完整的开源项目（比如PaiCLI、LangChain、PaiAgent），理解真正的技术实现。

 建立自己的技术深度：不只是调API，而是理解为什么这样设计、有哪些坑、如何优化。

 
 简历不是流水账，是高效的自我推荐。把你的优势、技术深度、工程化能力用最直接的方式展示出来，面试官才能看到你的价值。
