2. 实习期间最核心的三件事

 Q：你在实习期间做的最核心的三件事是什么？ 

 我的回答： 

 第一是编写各种运维小工具。例如以前需要手工录入客户档案，我写了工具采集客户机器信息，并通过语雀 API 自动生成和录入客户档案。

 第二是处理生产环境中的各种故障排查。

 第三是把排障经验整理成文档，在公司内部分享，也会把部分内容写到个人博客。

 AI 补充/点评： 

 内容比较实在，体现了自动化、排障和知识沉淀三方面能力。可以进一步补充工具带来的量化效果，例如节省多少时间、减少多少重复操作。

 3. 故障排查文档如何组织

 Q：你写故障排查文档时，有没有固定的目录结构？ 

 我的回答： 

 我通常会按照叙事结构来写：

 先说明故障现象；

 再一步一步展示排查过程；

 最后说明问题根因和解决方式。

 我认为排查过程比单纯展示问题本身更重要。

 AI 补充/点评： 

 回答不错，符合技术复盘文档的基本结构。还可以补充影响范围、时间线、临时止损、长期改进和预防措施。

 4. etcd 异常导致 Kubernetes 系统组件无法启动

 Q：详细讲一下你博客里 etcd 出问题后的排查过程。 

 我的回答： 

 当时在练习 Kubernetes 时，发现 API Server、CoreDNS 等多个系统组件都无法启动。

 一开始怀疑是组件没有安装好，于是重新安装了部分组件，但问题仍然存在。后来注意到这些都是 kube-system 下的系统组件，并且都会依赖 etcd，于是开始检查 etcd。

 使用 etcd 相关工具测试后发现无法正常连接，最终判断是 etcd 数据异常。我清理了其 WAL 等数据，相当于重建 etcd，之后集群恢复正常。

 机器当时直接在公网开放了 6443 端口，因此怀疑异常和外部攻击有关，但没有进一步确认攻击来源。

 AI 补充/点评： 

 从多个系统组件同时异常推断到 etcd，思路是合理的。但“被攻击”缺少日志、审计记录或网络证据，不能直接定性。清理 WAL、重建 etcd 也属于破坏性操作，生产环境应优先备份、检查日志并尝试从快照恢复。

 5. CPU 不高，但接口访问很慢

 Q：一台 Linux 服务器 CPU 占用不高，但访问接口很慢，你会怎么排查？ 

 我的回答： 

 我会先从请求链路开始排查。

 如果是网页请求，会先通过浏览器 F12 查看静态资源和接口的加载时间、失败请求及状态码。如果出现 502 等错误，就继续检查后端服务。

 如果后端服务本身没有明显问题，还会检查数据库是否存在慢查询。

 AI 补充/点评： 

 回答覆盖了前端、后端和数据库，但题目重点是服务器接口慢，应该更系统地检查网络延迟、磁盘 I/O、负载、连接数、线程池、依赖服务和 DNS 等因素。CPU 不高不代表机器没有瓶颈。

 6. 安装时报 Permission denied 

 Q：客户现场安装产品时出现 Permission denied ，一般是什么问题？怎么定位？ 

 我的回答： 

 通常是文件或目录权限不足。

 我会使用 ls -lah 查看文件所属用户、用户组和权限，再根据情况使用 chmod 修改权限，或者调整运行用户所属的用户组。

 AI 补充/点评： 

 基本方向正确，但不应简单地把普通用户加入 root 组。还需要检查父目录执行权限、文件系统是否以 noexec 挂载、SELinux、ACL、脚本解释器和文件格式等。

 7. 目录的执行权限代表什么

 Q：如果要让普通用户访问某个子目录，所有父目录都要有权限吗？目录的执行权限代表什么？ 

 我的回答： 

 当时没有回答出来。

 AI 补充/点评： 

 目录的 x 权限表示可以进入或穿过该目录，并访问其中已知名称的文件。要访问深层子目录，路径上的每一级父目录通常都需要具备执行权限； r 权限主要决定能否列出目录内容。

 8. 私有化交付为什么使用 k3s

 Q：你们什么场景会使用 k3s？为什么单机部署不直接使用 Docker Compose？ 

 我的回答： 

 我们的产品组件比较多，包括 Spark、前端、后端和 AI 相关服务，基本都拆成不同 Pod。

 使用 k3s 可以配合 Helm 管理模板和配置，整体维护更方便。k3s 本身也比较轻量，即使是单机环境也适合使用。客户规模更大时会部署多节点 Kubernetes。

 AI 补充/点评： 

 能够说明 Helm、配置管理和多组件编排的优势。还可以补充滚动升级、自愈、服务发现和统一交付方式，但也要承认单机使用 Kubernetes 会增加复杂度。

 9. 私有化交付的环境检查

 Q：私有化部署前有没有环境检查清单？ 

 我的回答： 

 有，主要检查：

 磁盘容量；

 内存大小；

 Linux 发行版和 CPU 架构；

 是否已经安装 Docker；

 磁盘性能是否达标；

 是否属于麒麟等需要额外适配的环境。

 如果客户已经安装了新版 Docker，可能会和 k3s 自带的 containerd 产生冲突。

 AI 补充/点评： 

 回答比较贴近实际交付。还可以加入 CPU、内核版本、端口、时间同步、DNS、主机名、网络连通性、防火墙、SELinux、磁盘挂载参数和系统限制等检查项。

 10. 麒麟与 ARM 环境适配

 Q：麒麟等国产化系统通常需要适配哪些内容？ 

 我的回答： 

 我接触的部分麒麟客户使用 ARM 架构，因此主要需要准备 ARM 架构镜像。

 实际适配工作做得不多，更多只是使用过麒麟环境。

 AI 补充/点评： 

 能够坦诚说明经验边界。除架构外，还可能涉及内核、glibc、系统库、驱动、包管理器、中间件兼容性和安全策略。

 11. 在线与离线镜像交付

 Q：你们的镜像怎么管理？客户纯离线环境怎么部署？ 

 我的回答： 

 镜像主要存放在阿里云镜像仓库。

 对于离线环境，会通过内部机器人把所有镜像统一打包，再把镜像包传到客户服务器并导入。

 AI 补充/点评： 

 这是常见的离线交付方案。还可补充镜像版本清单、校验值、签名、依赖一致性以及导入失败后的重试机制。

 12. 达梦数据库部署经验

 Q：部署达梦数据库时遇到过什么问题？部署的是几节点？ 

 我的回答： 

 部署的是单节点。

 主要问题是大小写兼容。业务里有些表名或字段名大小写混合，而达梦默认的大小写处理方式和业务预期不一致，因此初始化时调整了大小写敏感相关配置。

 AI 补充/点评： 

 抓住了真实兼容问题，但表述中“默认大小写敏感还是不敏感”有些混乱。面试前最好明确达梦标识符大小写、引号和兼容模式的具体规则。

 13. Pod 之间网络不通的排查案例

 Q：讲一下你博客中底层网络问题的排查流程。 

 我的回答： 

 客户是三节点集群。宿主机上可以访问 Spark Web UI，但其他 Pod 无法访问 Spark Pod。

 我由此判断宿主机到容器和容器到容器的通信路径不同，于是研究了 Flannel VXLAN 和 iptables，并对 Pod 间流量抓包。

 抓包发现 TCP SYN 能到达 Spark Pod，但返回的 SYN+ACK 在回程中丢失。最后怀疑是老版本 CentOS 7、3.10 内核的兼容问题，迁移到 AlmaLinux 并升级内核后恢复。（其实排查过程也有涉及到conntrack还有内核checksum错误那些，不过当时有点忘记了没说出来）

 AI 补充/点评： 

 这是本场面试中较有价值的案例，现象和抓包结果比较具体。但“内核兼容问题”仍需要更多证据，例如路由、反向路径过滤、conntrack、iptables 规则和内核日志。最终通过更换发行版解决，不等于完全定位了根因。

 14. 常见 CNI 及其特点

 Q：除了 Flannel，你还知道哪些 CNI？各有什么特点？ 

 我的回答： 

 知道 Calico 和 Cilium。

 Calico 可以使用 BGP，适合跨网段通信；Cilium 使用 eBPF，属于比较新的方案，性能和可观测性较强。

 AI 补充/点评： 

 大方向基本正确，但“Flannel 只能同网段、Calico 才能跨网段”过于绝对。跨网段能力取决于具体后端、路由和网络设计。

 17. SNAT 与 DNAT

 Q：SNAT 和 DNAT 分别是做什么的？ 

 我的回答： 

 DNAT 修改目标地址，SNAT 修改源地址。

 例如原本请求某个地址，经过规则转换成实际服务地址，属于 DNAT；修改请求的源地址则属于 SNAT。

 AI 补充/点评： 

 核心概念回答正确。Kubernetes 中 Service 转发常涉及 DNAT，而跨节点访问、Pod 出网等场景可能涉及 SNAT 或 MASQUERADE。

 18. conntrack 的作用

 Q：conntrack 是用来做什么的？记录维护在哪里？ 

 我的回答： 

 conntrack 用来记录网络连接状态，包括协议、源地址、目标地址和连接链路等信息。

 对于具体由内核哪里维护，当时回答得不够准确。

 AI 补充/点评： 

 连接跟踪表由 Linux 内核 Netfilter 子系统维护，可通过 conntrack 工具或 /proc/net/nf_conntrack 等方式查看。它是 NAT、状态防火墙和 Kubernetes Service 转发的重要基础。

 19. 容器镜像大小优化

 Q：构建镜像时，如何优化镜像体积和构建速度？ 

 我的回答： 

 可以使用更小的基础镜像，例如 Debian Slim 或 Alpine。

 安装依赖后及时清理缓存，也可以减少镜像大小。构建时还应尽量减少无用文件。

 AI 补充/点评： 

 基础方向正确。还可以提多阶段构建、合理安排层缓存、 .dockerignore 、固定依赖版本和合并安装清理命令。

 20. BusyBox 和 Alpine 为什么小

 Q：BusyBox 是什么？为什么它构建出来的镜像很小？ 

 我的回答： 

 BusyBox 是一个轻量级工具集，常用于嵌入式或 IoT 场景。Alpine 也会使用更轻量的 shell，例如 ash ，因此整体体积更小。

 AI 补充/点评： 

 BusyBox 把大量常用 Unix 命令集成在一个可执行文件里，通过不同调用名称实现不同功能，因此体积很小。Alpine 还使用 musl libc 和 BusyBox，不只是把 Bash 换成 ash。

 21. Kubernetes 节点 NotReady 如何排查

 Q：一个 Kubernetes 节点处于 NotReady ，怎么排查？ 

 我的回答： 

 一开始把节点健康和 Pod 的 liveness/readiness 探针混淆了。

 后来补充说，节点问题应检查 kubelet 状态。

 AI 补充/点评： 

 这是明显失分点。常见步骤包括：

 kubectl describe node 查看 Conditions 和 Events；

 检查 kubelet、容器运行时和 k3s-agent 服务；

 检查磁盘、内存、PID 压力；

 检查节点到 API Server 的网络和证书；

 查看 CNI 是否正常。

 22. 常见 Kubernetes 资源

 Q：Kubernetes 中常见的资源有哪些？分别做什么？ 

 我的回答： 

 Deployment：无状态应用；

 StatefulSet：有状态应用；

 CronJob：定时任务；

 DaemonSet：每个节点运行一个 Pod，监控 Agent 经常使用；

 Service：为服务提供稳定的访问入口。

 AI 补充/点评： 

 回答覆盖了主要工作负载类型。还可以补充 Job、ConfigMap、Secret、Ingress、PersistentVolume 和 PersistentVolumeClaim。

 23. Service 类型和临时访问方式

 Q：ClusterIP、NodePort 等 Service 有什么区别？如何从本地临时访问 ClusterIP 服务？ 

 我的回答： 

 ClusterIP 用于集群内部访问，NodePort 可以通过节点端口对外暴露。

 临时测试 ClusterIP 服务时，可以使用：

 
kubectl port-forward
 AI 补充/点评： 

 最终回答正确。完整类型还包括 LoadBalancer 和 ExternalName。 port-forward 常用于本地调试 Pod 或 Service，不适合作为生产流量入口。

 24. 多架构镜像迁移

 Q：你做过的多架构镜像迁移主要有哪些工作？ 

 我的回答： 

 通过镜像仓库相关接口，在源仓库和目标仓库之间直接迁移镜像，避免先拉到本地再推送。

 同时把 ARM64 和 AMD64 镜像合并到同一个多架构 Manifest 中，客户端拉取时会根据机器架构选择对应镜像。

 AI 补充/点评： 

 项目价值比较明确。面试中把接口说成 OCI 或 CRI 有些混乱，更准确地说通常是基于 Registry API 或工具操作 Manifest List / OCI Image Index。

 25. 单架构与多架构 Manifest 的差异

 Q：单架构镜像和多架构镜像的 Manifest 有什么区别？ 

 我的回答： 

 多架构 Manifest 里会包含架构相关信息，并引用不同架构镜像的摘要。

 AI 补充/点评： 

 基本正确。多架构镜像本身通常是一个索引，包含多个平台条目，每个条目指向对应架构的 Manifest，因此不会要求客户端把所有架构镜像都拉下来。

 26. 设计服务器统一监控工具

 Q：如果让你设计一个机房服务器统一监控工具，你会采集哪些指标？怎么实现？ 

 我的回答： 

 会关注：

 CPU、内存、磁盘容量；

 磁盘 I/O；

 网络流量；

 长时间高占用机器；

 存储池、LVM、Ceph 状态；

 RAID 卡和硬盘状态。

 还需要统一看板和 Alertmanager 一类的告警系统。

 如果服务器运行在 PVE 中，也可以通过 PVE API 或 Guest Agent 采集信息。

 AI 补充/点评： 

 覆盖面较广，能结合 PVE、RAID、Ceph 等实践。设计层面还可以明确 Agent、时序数据库、告警规则、标签体系、权限和高可用架构。

 27. RAID 卡状态如何采集

 Q：RAID 卡状态能否通过软件采集？ 

 我的回答： 

 一般可以使用厂商提供的管理工具采集，部分设备也支持通用协议。

 AI 补充/点评： 

 回答正确。常见工具包括 StorCLI、MegaCLI、ssacli 等，也可以将结果转换成 Prometheus 指标。

 28. 如何使用 AI Agent 开发复杂项目

 Q：如果项目包含前后端和产品设计，你会怎么使用 AI Agent？ 

 我的回答： 

 我通常先让 AI 进行头脑风暴，通过提问明确需求，再生成产品原型或 PRD，并把项目拆解成阶段性任务。

 开发过程中不会让 AI 一直自行循环，而是保持 Human in the Loop，定期检查和纠正它的设计与代码。

 AI 补充/点评： 

 回答比较有实践感，说明不是单纯“让 AI 写代码”。如果能补充版本控制、测试、代码审查和验收标准，会更加完整。

 29. 上下文窗口满了会发生什么

 Q：和 AI Agent 对话时，上下文窗口满了会发生什么？ 

 我的回答： 

 Codex 一类工具通常会进行 compact，把已有上下文压缩成摘要，再继续对话。具体实现可能是调用专门的模型或接口完成摘要压缩。

 AI 补充/点评： 

 方向基本合理。压缩后通常会损失细节，因此重要约束应放进项目文档、规则文件或可检索的持久化记录中，而不能完全依赖会话上下文。

 30. Subagent 和并行 Agent

 Q：用过并行 Agent 或 Subagent 模式吗？ 

 我的回答： 

 用过。复杂任务可以交给能力更强的模型，简单修改则交给速度更快、成本更低的模型。

 并行 Agent 的 Token 消耗比较快，因此需要根据任务复杂度选择模型。

 AI 补充/点评： 

 回答体现了成本和任务分层意识。还应注意多个 Agent 之间的上下文一致性、重复劳动和最终合并质量。

 31. 推理强度对模型执行的影响

 Q：不同推理强度会对 AI 执行产生什么影响？ 

 我的回答： 

 更高推理强度会给模型更多思考时间，适合复杂问题。但思考时间过长也可能导致过度设计、反复否定自己，反而得到较差的答案。

 AI 补充/点评： 

 观点比较实际。可以进一步说明，应根据任务难度动态选择推理强度，而不是所有任务都开最高档。

 2. 如何理解 SRE

 Q：你怎么理解 SRE？它可以分成哪些部分？ 

 我的回答： 

 SRE 是 Site Reliability Engineer，核心目标是保证服务的可靠性和可用性。

 最终目标是持续提升系统可用性。

 AI 补充/点评： 

 提到了自动化、测试、高可用和技术债，但整体回答仍偏宽泛。可以从 SLI/SLO、错误预算、监控告警、容量规划、变更管理、故障响应和自动化几个方面展开。

 3. SRE 是否等同于后期运维

 Q：不结合具体岗位，怎样做才能真正保证可靠性？ 

 我的回答： 

 不能只在故障发生后处理问题，而应尽可能减少日常运维步骤、消除技术债、增加测试，并在架构层面实现高可用。

 例如 Kubernetes 控制面要考虑多节点部署，而不是只依赖单节点。

 AI 补充/点评： 

 方向正确。面试官后续也强调，可靠性应在早期设计阶段介入，而不是上线后靠“救火”实现。

 4. 最近关注的技术方向

 Q：最近在关注哪些开源项目、社区或技术博客？ 

 我的回答： 

 最近关注 AI Agent 的记忆能力。

 目前一些 Agent 会在回答问题前检索过去的会话记录，把其他 Session 中的信息作为上下文。我认为这方面仍处于探索阶段，当前的记忆能力还比较粗糙。

 AI 补充/点评： 

 回答比较新颖，但与 SRE 岗位关联略弱。可以同时准备一个基础设施相关方向，例如 eBPF、Cilium、OpenTelemetry、Kubernetes 或可观测性。

 5. 常用的 AI Coding 工具

 Q：Codex、Claude Code 等工具中，你觉得哪个更好用？ 

 我的回答： 

 我使用 Codex 较多，通常会选择最新模型，并根据任务开启较高推理强度。

 AI 补充/点评： 

 答案偏简略。可以从代码检索、终端操作、上下文管理、补丁质量、速度和成本等维度比较，而不只是说使用哪个。

 6. 使用 Codex 解决实际问题

 Q：举一个使用 Codex 解决问题的实际案例。 

 我的回答： 

 在分析故障时，我会把大量日志放到一个目录，让 Codex 在目录中使用 grep 、 ripgrep 等工具筛选和分析日志。

 AI Agent 处理大量重复日志的效率比较高，可以和我一起完成故障排查。如果环境允许，有时也会让它通过 SSH 在服务器上执行只读检查。

 AI 补充/点评： 

 案例真实，体现了 Agent 在海量日志分析中的价值。需要强调权限控制、只读操作、命令审核和敏感数据处理，尤其不能让 Agent 无限制操作生产服务器。

 7. 如何判断 AI 有没有“忽悠”

 Q：使用 AI 时，你怎么判断它有没有编造或误导你？ 

 我的回答： 

 主要依赖自己的经验检查它输出的内容和代码。

 现在模型出现明显错误的情况比以前少，但如果自己也不了解某个领域，就很难判断。

 AI 补充/点评： 

 回答比较坦诚，但可以更方法化：

 要求提供证据或命令输出；

 通过多种方式交叉验证；

 先在测试环境复现；

 检查官方文档和源码；

 对高风险操作设置人工确认。

 8. 大学四大基础课程学得最好的是哪门

 Q：计算机四大基础课中，你哪一门学得最好？ 

 我的回答： 

 没有觉得哪一门学得特别好，更多知识是在实际工作中学到的。

 AI 补充/点评： 

 这种回答比较吃亏。即使理论成绩一般，也最好选一门相对熟悉的课程，并结合工作场景说明，例如计算机网络与实际抓包排障的联系。

 9. 私有化部署全流程

 Q：从研发输出制品，到客户现场完成私有化部署，整个流程是什么？ 

 我的回答： 

 研发提交代码并打 Tag 后，由 Jenkins 自动构建镜像。

 产品包含前端、后端、Spark 和多个 BI 组件。所有镜像会被统一打包并放到专用下载服务器。

 客户现场执行一键安装脚本后，会：

 下载或导入镜像；

 创建并初始化 PostgreSQL 数据库；

 启动后端服务并完成数据库初始化；

 启动 Spark 和其他业务组件；

 最后启动前端服务。

 整个组件编排使用 k3s。

 AI 补充/点评： 

 流程讲得比较完整。还可以补充版本清单、配置生成、环境预检、回滚、验收和部署后的健康检查。

 10. k3s 离线部署和定制

 Q：你们使用的是 k3s 离线版本吗？做过哪些修改？ 

 我的回答： 

 使用离线版本，k3s 二进制和离线镜像包都会跟随安装包一起下发。

 公司对 k3s 做过一些定制，例如延长证书有效期，减少客户环境中证书过期带来的维护问题。

 AI 补充/点评： 

 能说明实际交付特点。不过把证书直接改成 99 年存在明显安全和合规风险，更合理的方式是建立证书轮换、升级和告警机制。

 11. k3s 本身如何安装

 Q：k3s 自己具体是怎么安装起来的？ 

 我的回答： 

 知道会把二进制文件和离线镜像包下载到服务器，并把二进制放到系统路径中。

 对于更深层的安装过程、systemd 服务和组件启动方式，当时了解不够。

 AI 补充/点评： 

 这是需要补课的内容。至少应掌握 k3s 二进制、systemd 服务、配置文件、数据目录、token、离线镜像目录和 server/agent 启动参数。

 12. Static Pod 是什么

 Q：你了解 Static Pod 吗？ 

 我的回答： 

 不了解。

 AI 补充/点评： 

 Static Pod 由节点上的 kubelet 直接管理，而不是由 API Server 调度。Pod 清单通常位于指定目录，控制面组件在 kubeadm 集群中经常以 Static Pod 运行。

 13. 客户已有 Docker 导致 containerd 冲突

 Q：部署 k3s 时遇到过什么问题？ 

 我的回答： 

 有客户机器已经安装了较新的 Docker，其中也包含 containerd，可能与 k3s 自带的 containerd 冲突。

 最后通过修改 k3s 自带 containerd 的路径等方式绕开客户现有环境。

 AI 补充/点评： 

 是比较典型的私有化环境兼容问题。还应明确冲突究竟发生在 socket、目录、端口还是配置层面，避免只描述为“两个 containerd 冲突”。

 14. PostgreSQL 初始化

 Q：PostgreSQL 密码和数据库初始化是怎么做的？ 

 我的回答： 

 通过脚本自动生成 PostgreSQL 密码，并自动完成建库、用户和初始化数据等操作。

 实际客户大多数使用单节点 PostgreSQL，多节点数据库经验较少。

 AI 补充/点评： 

 回答符合实习经历。还可以补充脚本的幂等性、失败重试、密码保存位置和初始化日志。

 15. 数据库密码轮换如何设计

 Q：如果要设计数据库密码轮换机制，你会怎么做？ 

 我的回答： 

 可以把 PostgreSQL 密码放到 Kubernetes Secret 中，轮换时修改 Secret，让应用读取新密码。

 但 Secret 并不绝对安全，拥有集群权限的人可以直接导出其内容。

 AI 补充/点评： 

 意识到了 Secret 的安全边界，但只修改 Secret 并不意味着数据库密码和应用连接会自动同步。

 完整流程需要协调数据库修改、Secret 更新、应用滚动重启、连接验证和失败回滚。还可以接入 Vault 或云密钥管理系统，并启用 etcd 静态加密和 RBAC。

 16. 自动录入客户机器信息

 Q：你写过哪些自动化工具？解决了什么问题？ 

 我的回答： 

 我写过自动采集客户机器信息并录入语雀的工具。

 工具会采集机器配置，然后调用语雀 API 自动生成客户档案，替代原来的手工录入。

 AI 补充/点评： 

 项目目标清晰，适合在面试中讲。最好补充采集字段、异常处理、鉴权方式和实际节省的人力。

 17. 镜像仓库之间直接迁移

 Q：还做过哪些镜像相关工具？ 

 我的回答： 

 以前迁移镜像时需要先从源仓库拉到本地，再推到客户仓库。

 后来我写了工具，通过镜像仓库接口直接完成仓库间迁移，不需要把完整镜像落到本地。

 同时还支持把 ARM64 和 AMD64 镜像合并成一个多架构镜像。

 AI 补充/点评： 

 这个项目比普通脚本更有亮点，能体现对镜像仓库和多架构交付的理解。回答时应准确区分 OCI、Registry API、CRI 和 Docker API。

 18. 为什么学习 Go

 Q：你为什么学习 Go？ 

 我的回答： 

 因为 Kubernetes 等很多基础设施项目都使用 Go。

 我比较喜欢 Go 接近 C 的语法和简洁的工程体验。相比 Python，Go 的依赖和打包方式更统一，而且可以直接编译成二进制文件，运行速度也较快。

 AI 补充/点评： 

 动机合理，也符合 SRE 方向。可以补充并发模型、静态类型、跨平台编译和部署方便等特点。

 19. Go 是否进行过系统学习

 Q：你系统学习过 Go 吗？现在还能手写吗？ 

 我的回答： 

 以前系统学过一段时间，但遗忘较多。现在不少代码会借助 AI Agent 完成，纯手写会比较困难。

 AI 补充/点评： 

 回答过于诚实，容易让面试官怀疑基础能力。更好的表达是：基础语法和代码阅读没有问题，复杂实现会借助文档和 AI 提升效率，同时会自己审核和测试代码。

 20. Home Lab 和个人项目

 Q：平时会搭建个人网站或做自己的项目吗？ 

 我的回答： 

 主要是在 Home Lab 中折腾 PVE、服务器和各种自托管服务，也会搭建游戏服务器。

 暂时没有特别完整的公开项目。

 AI 补充/点评： 

 对 SRE 岗位来说，Home Lab 本身就是不错的实践。可以提前整理成一个结构化项目：架构图、监控、备份、网络、自动化和故障案例。

 21. 面试官对 SRE 岗位的介绍

 面试官观点： 

 SRE 不应只在系统上线后负责维护和救火。

 可靠性、高可用和可维护性应该在产品早期设计阶段就被考虑。SRE 可以覆盖整个生命周期，包括前期设计、中期改进、后期运营和故障处理。

 P99、SLA 等指标只是最终结果，不能靠上线后不断填坑实现。

 该公司每年需要交付大量私有化生产环境，因此岗位的核心任务是不断提高基础设施的可靠性、自动化程度和环境适应能力，从而降低交付成本。

 个人复盘： 

 第二场面试相比第一场更重视对 SRE 岗位本身的理解，而不是单纯考命令和组件知识。

 主要问题有三点：

 对 SRE 的回答仍然偏传统运维视角；

 Kubernetes 和 k3s 的底层安装机制掌握不深；

 一些项目实际做过，但接口名称和技术概念容易说混。

 面试官给出的建议是阅读《Google SRE》，并把可靠性理解为从设计阶段开始贯穿整个系统生命周期的工程能力。

 总结

 两场面试整体都围绕以下几类能力展开：

 Linux 权限、网络和系统排障；

 Kubernetes/k3s 的使用及底层原理；

 私有化部署和离线交付；

 容器镜像、多架构镜像和仓库迁移；

 SRE 对可靠性、自动化和高可用的理解；

 AI Agent 在日志分析和开发中的实际使用。

## 云计算方向秋招总结

来源：牛客网 ｜ 类型：面经 ｜ 发布：2022-09-18 ｜ [原文链接](https://www.nowcoder.com/discuss/401038251895648256)

9/22补档： 

 阿里云：由于实习面过，有一个直达终面的机会，HR比较nice，问的也是职业发展，对云原生技术、社区的关注，总的来说面试官和HR都挺nice 蚂蚁：一面电话面30min，开场聊项目，围绕项目聊容器、K8s没有很生硬的八股和发问，所有问题都是结合项目问出来的（阿里系好像都这样） 

 

 9/27补档： 

 阿里云：团队的技术人员电话了一下，聊了下组内的业务和后续流程的问题 Momenta：VP面，第一次接触这么高职级的面试官，果然大佬都很Nice！ 

 
 

 秋招两个月以来一直在牛客上看大家的面经和经验帖子，非常感激各位牛友的无私分享，由于秋招一直不是很顺利，所以没有心情记录面经，只能靠回忆总结一下秋招以来的心得体会，主要还是面 向云计算、云原生方向，不过我的知识理解和写作笔力有限，有讲的不对的地方请大家不吝斧正，我也可以进一步学习了解一下 ，如果大家觉得感兴趣，也欢迎和我讨论。 

 背景 

 

 由于我一直在做云计算（主要是云原生）方向，所以主要的技术栈是kubernetes、容器、golang为主，附带os、虚拟化、安全容器的少量知识。一开始觉得容器编排的发展方向不错，计划以后扎根容器编排这个比较有前景领域，做Kubernetes的深度开发，但是在实际的秋招过程中发现以前太理想化了，今年行情大环境不好，基础架构部门不属于直接盈利的组，HC情况非常不乐观，不过云原生方向的开发人员还是有很多可以去的方向。 

 哪些行业、岗位适合云原生开发的同学？ 

 在实际的面试时和各个部门主管、实验室师兄聊的过程，发现做云的同学在很多公司都有相应的部门可以去 

 最直观、最匹配的 

 各个互联网大厂的基础架构、基础平台、云原生部门：如头部大厂的阿里云云原生、字节基架paas团队，美团的基础平台等，区别无非是有的主要是面向内部的业务，不过这类部门今年的HC普遍不乐观（不然我也想去.jpg）。 

 传统云计算 

 最近在面试过程中越来越感觉到，Kubernetes只是云计算的一个容器编排的工具，虽然容器市场的前景还算不错，但是很多云厂商还要传统的虚拟机、边缘计算、CDN业务支撑，这些业务今年的HC明显会更多，实际的场景也梗丰富。从未来的职业发展来看，个人觉得去这些部门也很好：一方面从技术上，linux容器可以考虑成进程的虚拟化，但是在安全性、网络性能等方面有很多优化的空间，所以不论是做安全容器、还是内存、IO的优化，以后有很多需要从虚拟机的优化技术获取idea，如SRIOV、OVS网络等；从业务方面来看，以Kubernetes为主的容器编排拓展性是很好，但是它毕竟只是一个开源框架，但是更多的还是要考虑业务本身做什么和自己的职业规划，需要面向具体业务定制化。
 

 自动驾驶——计算任务调度 

 自动驾驶公司面试过蔚来自动驾驶pnc和momenta的基础架构，由于这些公司都是自动驾驶方向，他们更多的需要点在于：需要海量数据来进行计算、仿真、控制的诸多领域，要完成车端到云的双向数据链路，所以在业务上以数据驱动为指导。具体到 云原生技术，前述的计算任务可能会用容器承载（不一定是spark on k8s、flink on k8s那种意义的大数据平台云化），他们需要容器编排框架来做计算任务的分配，可以理解为自动驾驶产品+云原生技术。 

 量化、AI公司——GPU算力平台 

 这部分比较直观，量化公司如幻方、九坤，还有旷视、商汤这些公司需要大量的GPU资源，他们搭建的云平台主要用来跑深度学习模型，这一层需要任务调度、资源分配、甚至可能需要GPU虚拟化（这个比较难搞），也会需要云原生技术栈的开发人员。不过目前我没有面试这类公司，后续如果有面试之后再补充吧。
 

 
 

 面试分享 

 云原生方向的面试、个人理解包括几个部分： 

 CS基础：OS、网络 golang：runtime层面的 gc、调度、对内存管理等；常用的interface、mutex、闭包、channel等的底层实现 容器\运行时：cgroup，linux namespace， UnionFS（经典三件套）， LXC，runc，安全容器(runv、gvisor、kata) Kubernetes：各个组件底层 （最好过一下源码的主要逻辑） ，主要是 scheduler的流程、打分算法；kubelet会结合CRI问；kube-proxy会结合CNI问；controller会结合client-go问，最好有client-go使用经验，需要看一下源码 了解CNCF社区动向：kubevela、volcano、kubecruise、istio、p rometheus 之类的可以了解下设计思想积累业内的最优实践 各个公司面试官风格&遇到的有趣问题：
