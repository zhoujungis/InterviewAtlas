 1. KV Cache是什么？为什么能加速大模型推理？

 面试官： 有了解过KV Cache吗？它是什么作用，为什么能加速大模型推理？

 面试官追问： 那KV Cache的代价是什么？长序列推理时显存怎么估算？

 回答： 

 KV Cache 的本质，是用显存换取自回归解码阶段的重复计算。在 Transformer 的每一层注意力中，历史 Token 对应的 Key 和 Value 一旦计算完成，在后续生成步骤中通常不会改变，因此可以缓存下来。生成第 个 Token 时，只需要计算当前 Token 的 Query、Key、Value，再让当前 Query 与前 个位置的 Key、Value 做注意力，而不必重新计算全部历史 Token 的 Key、Value 投影。

 Prefill 阶段。 一次输入整段 Prompt，普通全注意力的计算量仍近似为 。KV Cache 不会消除这部分完整上下文注意力计算。

 2. Agent上下文超限了怎么处理？

 面试官： Agent执行多步任务时，对话历史加工具返回结果很容易超限，你有什么处理方案？

 面试官追问： 三种策略分别在什么场景下用？

 回答： 

 Agent 上下文治理的核心不是“把旧消息删掉”，而是在有限 Token 预算内，持续保留完成当前任务所必需的状态、证据和约束。一个成熟方案通常分为五层。

 第一层是 预算与优先级管理 。先为 System Instruction、工具 Schema、当前用户请求、近期对话、任务状态、检索证据和输出预留独立预算。System 约束、权限边界和当前目标不能被普通历史消息挤出上下文。

 第二层是 近期窗口 。保留最近若干轮原始消息，适合强依赖局部指代、短期状态快速变化的实时对话。但窗口不应只按“轮数”截断，而应按 Token、消息类型和任务依赖截断。机械丢弃最早消息可能删掉长期有效的用户约束。

 第三层是 结构化状态与摘要 。把历史对话压缩成任务状态，例如目标、已确认事实、未完成子任务、约束、决策及证据引用。摘要应支持版本号、更新时间和可追溯来源；发生冲突时，新事实不能静默覆盖旧事实，而应记录“旧值、当前值、变更依据”。

 第四层是 外部记忆检索 。把长期历史、文档和经验存入可检索存储，按语义、关键词、时间、实体、会话和权限联合召回。向量相似度只表示“像”，不表示“当前有效”，因此还要考虑新鲜度、来源可信度、用户归属和业务权限。

 第五层是 工具结果压缩 。Agent 最容易被日志、网页全文、数据库大结果集和代码构建输出撑爆。应在工具层先做分页、字段投影、去重、统计聚合、错误摘要和 Artifact 引用，只把决策所需片段送回模型，而不是把原始输出全部塞回上下文。

 场景选择可以这样回答：

 
 短对话和低风险客服：近期窗口加少量结构化槽位即可。

 长周期任务：近期窗口、任务状态、阶段摘要和 Artifact 引用组合使用。

 跨会话个性化：使用权限隔离的长期记忆检索，并设置过期、确认和删除机制。

 知识问答：重点是检索外部证据，而不是把所有历史对话永久保留。

 高风险操作：关键参数、用户确认、审批结果和工具回执必须保留为不可丢失的结构化状态。

 
 摘要模型不一定越小越好。小模型成本低，但数字、否定关系、权限条件和未完成事项一旦压错，后续所有步骤都会在错误状态上继续。应使用专门评测集比较事实保真率、未完成任务召回率、压缩率和下游成功率，再决定模型与策略。 上下文压缩的目标不是最短，而是让 Agent 在更少 Token 中仍然保持任务连续性、事实一致性和可恢复性。 

 3. Agent取消机制怎么做？

 面试官： 一个Agent任务耗时很长，用户等不及了，怎样停止这个任务？这个机制你实际尝试过吗？

 回答： 

 Agent 取消机制的本质是 可传播的协作式取消 + 资源级强制终止 + 状态一致性恢复 。只在主循环里放一个布尔标记，只能停止下一步调度，不能保证当前网络请求、子进程、数据库事务或外部工具真正停下来。

 完整设计可以分为六层：

 
 任务状态机。 每个任务具有 task_id 、 RUNNING/CANCELLING/CANCELLED/SUCCEEDED/FAILED 状态、截止时间和父子任务关系。取消请求必须幂等，多次取消返回同一个最终状态。

 取消令牌传播。 从 HTTP 请求或交互层生成 Cancellation Token，向 Planner、Agent Loop、模型流式请求、工具调用和子任务逐层传播。每个耗时阶段都在安全点检查，而不是只在循环开头检查。

 Deadline 与超时。 将剩余时间预算传给下游，区分连接超时、首 Token 超时、空闲读取超时和总耗时。超时本质上是由系统发起的取消，也必须走同一条清理链路。

 底层中止。 对支持取消的 HTTP 客户端主动关闭请求或流；对子进程先发送优雅终止信号，超时后再强制终止进程组；对容器或沙箱可以直接回收执行单元。 Future.cancel() 或 Thread.interrupt() 只是发出信号，目标代码不响应时并不等于任务已经停止。

 副作用治理。 已执行的发邮件、扣款、写文件等动作不能靠取消“回滚”。工具应支持幂等键、事务、预提交、补偿动作和操作日志。取消时停止未来动作，并对已提交副作用执行明确的补偿或人工确认。

 资源清理与观测。 在 finally 、 whenComplete 或上下文管理器中释放连接、文件句柄、锁、临时目录和 GPU Session；记录取消来源、传播延迟、未能中止的子任务和最终一致性结果。

 
 Java 中 CompletableFuture.orTimeout() 只会让 Future 以超时异常完成，通常不会自动停止已经运行的底层任务；丢弃 Future 更不会释放连接。正确做法是让执行函数显式接收取消令牌或 Deadline，并使用能够中止请求的客户端 API。对于不可协作的第三方 SDK，应把调用隔离到独立进程、容器或受控 Worker，通过终止执行单元形成最后一道边界。

 实际项目回答应给出可验证证据，例如“取消请求 P95 多久生效”“正在进行的工具是否真正停止”“已产生副作用如何恢复”，而不是只说自己使用了某个并发类。面试式结论是： 取消不是线程 API 问题，而是从用户请求一直传播到资源和副作用的一条系统契约。 

 4. MCP是什么？Agent通过MCP调用工具的流程是什么？

 面试官： MCP是什么？Agent通过MCP调用工具的流程是什么？

 面试官追问： 你觉得MCP能成为标准吗？

 回答： 

 MCP，即 Model Context Protocol，是一种面向 AI 应用与外部能力之间连接的开放协议。它解决的不是模型“会不会决定调用工具”，而是 Host、Client 与 Server 之间如何发现能力、协商版本、传输请求、返回内容并管理连接生命周期。Tools、Resources、Prompts 是常见的 Server 能力；较新的协议还在能力协商下支持日志、Sampling、Elicitation、Tasks 等扩展。

 更准确的角色关系是：

 
 Host 是承载 Agent 的应用，例如 IDE、桌面客户端或业务服务，负责权限、上下文、模型调用和用户交互。

 MCP Client 运行在 Host 内部，通常与一个 MCP Server 建立一个逻辑连接。

 MCP Server 暴露工具、资源或提示模板，并连接本地文件、数据库、SaaS 或企业系统。

 
 典型调用流程如下：

 
 Client 通过 initialize 与 Server 协议握手，协商协议版本和双方能力，然后发送 initialized 通知。

 Host 根据需要通过 tools/list 等方法发现能力，将经过权限过滤的工具 Schema 提供给模型。

 模型基于用户请求生成结构化工具调用意图。注意，这一步通常属于模型 API 或 Agent Runtime，而不是 MCP 协议替模型做决策。

 Host 校验工具名、参数 Schema、用户权限、风险级别和是否需要人工批准。

 Client 通过 JSON-RPC 2.0 向 Server 发起 tools/call 。本地常见传输是 stdio，远程常见传输是 Streamable HTTP。

 Server 执行能力并返回结构化内容、错误状态或资源引用。Host 对结果做大小限制、脱敏、可信度标记和 Prompt Injection 防护。

 Host 将工具结果关联到原始调用，再交回模型继续推理，直到产生最终回答或触发下一次工具调用。

 
 关于“能否成为标准”，到当前阶段已经不能再回答“OpenAI 和 Google 是否跟进还不确定”。OpenAI Agents SDK 与 Google ADK 均已提供 MCP 集成，主流开发工具和 Agent 生态也在广泛接入。更合理的判断是： MCP 已经成为 Agent 工具与上下文连接层最有影响力的开放协议之一，但“广泛采用”不等于所有系统都必须统一成一个运行时。 

 它仍有三类边界：第一，协议统一接口，不统一工具语义、数据质量和业务事务；第二，远程 Server 带来授权、Token 转发、供应链和 Prompt Injection 风险；第三，低延迟、强事务、超高吞吐的内部调用仍可能直接使用 gRPC、HTTP 或消息系统。MCP 的长期价值更像 Agent 世界的连接协议，而不是替代所有服务协议。

 5. RAG中的父子索引是什么？解决了什么问题？

 面试官： RAG为什么需要设计父子索引？检索小文本块、返回大父文档能解决什么问题？

 面试官追问： 这样设计有什么代价？

 回答： 

 父子索引解决的是 RAG 中一个非常核心的矛盾： 用于匹配的文本块希望足够小，用于回答的上下文又希望足够完整。 

 如果 Chunk 太大，一个向量同时混入多个主题，查询信号容易被稀释，精确术语也可能匹配不出来；如果 Chunk 太小，虽然局部语义更纯，但标题、定义、前提、表格上下文和跨段逻辑会被切断。父子索引把这两个粒度拆开：

 
 以较小的子块建立向量或关键词索引，每个子块记录 parent_id 、位置、版本和权限元数据。

 查询时检索子块，可先混合 BM25 与向量召回，再做 Rerank。

 将命中的子块映射回父块或相邻窗口，按父文档去重、合并和控制总 Token。

 把更完整的父级上下文交给生成模型，并保留子块命中位置用于引用和可解释性。

 
 这里的“父”不一定是整篇文档，也可以是一个章节、一个表格加说明、一个函数或一个带标题的语义段落。父块过大仍会引入噪声，因此父子尺寸不能只凭经验固定为 256/1024 Token，应根据文档结构、查询类型和下游评测调优。

 它的代价主要包括：

 
 索引与文档存储更复杂，需要维护子块到父块的映射、版本和权限一致性。

 多个命中子块可能指向同一个父块，若不去重会重复占用上下文。

 返回父块会放大 Token 和延迟，甚至把未授权的兄弟内容一起带出，因此权限应至少落实到可返回的父级粒度。

 子块的 Rerank 分数不能直接等同于父块分数，需要设计 Max、Top-N 聚合或覆盖度评分。

 文档更新后，父块与子索引必须原子换版，否则会出现旧索引指向新正文或反过来的不一致。

 
 验证时应比较 Recall@K、MRR/nDCG、答案正确率、引用命中率、上下文利用率、Token 成本和延迟，并对普通小块、滑动窗口、父子索引和层级检索做消融。 父子索引不是简单多存一份文本，而是把“在哪里命中”和“带什么上下文回答”拆成两个可分别优化的阶段。 

 6. ReAct模式和Plan模式有什么区别？

 面试官： ReAct模式和Plan模式有什么区别？分别适合什么场景？

 回答： 

 ReAct 与 Plan 模式的本质区别，是“决策与执行交错进行”还是“先形成显式计划，再由执行器推进”。二者不是互斥框架，也不能简单等同于“ReAct 灵活但慢、Plan 一定高效”。

 ReAct 通常按 Observation -> Reason/Decision -> Action -> New Observation 循环。每一步都根据最新环境反馈决定下一步，适合信息不完整、需要搜索、工具结果不确定或错误恢复频繁的任务。优势是反馈闭环短；缺点是模型可能局部贪心、重复调用、路径漂移，而且每一步都要重新推理，成本和延迟较高。

 Plan-and-Execute 先把目标拆成子任务、依赖和验收条件，再由执行器逐步完成。计划可以是线性列表，也可以是 DAG，但“Plan 模式必然一次性生成完整 DAG”并不准确。优势是全局目标更清晰、任务可并行、便于预算和审计；缺点是环境变化后原计划会过时，错误计划如果不允许重规划，执行越认真可能偏得越远。

 场景上可以这样选择：

 
 开放式检索、故障排查、网页操作、代码探索：更适合 ReAct，因为下一步依赖刚获得的观察。

 固定审批流、批处理、可预测的数据流水线：更适合显式 Plan 或 Workflow。

 长周期复杂任务：通常采用分层混合模式，Planner 生成里程碑和依赖，每个子任务内部使用 ReAct，遇到关键假设失效时触发 Replan。

 
 工程实现中，计划不应只是一段自然语言。至少要有 step_id 、依赖、输入、工具权限、预算、完成条件和状态；执行器则要维护最大步数、重试策略、幂等键、Checkpoint 和取消信号。每一步完成后由确定性 Verifier 或环境状态判断是否达标，不能只让同一个模型口头宣布成功。

 一个成熟系统还要支持“不要用 Agent”的判断。如果流程稳定、风险高且规则明确，状态机或工作流引擎通常比自主 ReAct 更可靠。 ReAct 解决动态探索，Plan 解决全局分解，生产系统真正重要的是反馈、验证和重规划，而不是给循环贴哪一个模式标签。 

 7. 工具返回结果的消息结构怎么设计？为什么需要单独的Tool Message？

 面试官： Agent调用工具后，工具返回结果的消息结构怎么设计？为什么需要单独的Tool Message？

 回答： 

 Tool Message 的核心作用，是把“模型提出的工具调用”和“外部系统返回的观察结果”建立明确、可机器验证的关联。它不是普通用户消息，也不是系统指令。如果把工具输出拼成用户文本，模型、编排器和审计系统都很难判断这段内容来自谁、对应哪次调用、是否执行成功，以及能否被信任。

 "attempt": 1,
 "truncated": false,
 "artifact_id": null
 }
}
 
 具体字段要服从所使用的模型 API 或协议，不能假设所有厂商都接受自定义 status 和 metadata 。通常必须保证： tool_call_id 与模型发出的调用一一对应；结果内容类型明确；业务失败与协议失败可区分；大结果通过 Artifact、分页或引用返回；敏感字段在进入模型前完成脱敏。

 单独设计 Tool Message 有五个价值：

 
 关联性。 并行调用多个工具时，可把每个结果精确绑定到原始调用。

 角色边界。 模型知道这是一条外部观察，而不是用户的新指令。

 可恢复性。 编排器可以根据超时、可重试错误、参数错误或权限错误采用不同策略。

 可观测性。 调用链能够记录工具、参数摘要、延迟、重试和结果大小。

 安全性。 工具内容可被标记为不可信数据，避免网页或文档中的恶意文本越权成为高优先级指令。

 
 需要特别强调：Tool Message 虽然角色独立，但并不会自动消除 Prompt Injection。网页、邮件和数据库文本仍可能包含“忽略之前指令”之类内容。Host 必须限制工具权限、隔离数据与指令、对高风险动作二次验证，并避免把原始 HTML、系统密钥或超长日志直接交给模型。

 Tool Message 的本质不是多一个 role 字段，而是把工具调用从自然语言聊天提升为可关联、可审计、可恢复的执行协议。 

 8. 多个Agent同时修改同一个文件，如何避免冲突？

 面试官： 多个Agent同时修改同一个文件，如何避免冲突？

 回答： 

 最优先的原则不是“给同一个文件加一把更大的锁”，而是尽量减少共享可变状态。可以先按模块、目录、函数或任务所有权拆分，让多个 Agent 在独立 Workspace、分支或 Git Worktree 中工作，最后通过 Patch 合并。只有确实需要修改同一逻辑区域时，才进入冲突控制。

 一种可靠的工程链路是：

 
 每个 Agent 从同一个基线提交或文件哈希开始，在隔离工作区产生结构化 Patch。

 提交前执行 Compare-And-Swap：确认目标文件当前哈希仍等于读取时的基线哈希。

 若基线未变化，原子应用 Patch；若已变化，使用三方合并，即 Base、Current、Agent Result，而不是覆盖写入。

 只在“检查版本 + 应用 Patch + 更新版本”的短临界区加锁，避免把模型思考和工具执行时间放进锁内。

 合并后运行解析器、格式化、类型检查、测试和领域不变量校验。文本无冲突不代表语义无冲突。

 
 乐观并发控制适合冲突概率低、Agent 任务较长的场景；悲观锁适合短事务和高冲突热点，但必须设置租约、持有者 Token、超时和 Fencing Token，避免锁过期后旧持有者继续写入。仅使用 Redis SET NX PX 而没有 Fencing，无法完全防止暂停进程恢复后的陈旧写。

 对于代码仓库，Git 的 Patch 和三方合并通常优于直接共享文件锁；对于结构化文档，可以按 AST、JSON Patch 或数据库行级版本合并。所谓“让 LLM 仲裁冲突”只能作为生成候选合并结果，最终仍要由确定性校验和测试验证。

 还要处理原子落盘：先写临时文件、 fsync ，再原子重命名，避免进程崩溃留下半个文件。写操作应带 operation_id ，重试时保持幂等。

 多 Agent 协同的关键是隔离、版本、Patch、短临界区和验证闭环；锁只是其中一个工具，不能替代语义合并。 

 9. Agent陷入死循环或重复调用，怎么兜底？

 面试官： Agent陷入死循环或重复调用同一个工具，你们的系统有什么兜底机制？

 回答： 

 死循环治理要同时限制资源消耗和识别“没有进展”。固定最大 15 步、同一工具每分钟 5 次可以作为某个业务的配置，但不能当成普适答案。搜索任务、代码任务和高风险交易的合理预算完全不同。

 可以设计六层保护：

 
 硬预算。 限制总步骤、模型 Token、工具次数、总耗时、金额、外部请求数和并行度。任何一个预算耗尽都进入受控终止，而不是继续请求模型“再试一次”。

 调用指纹。 对 tool_name + 规范化参数 + 关键环境版本 做哈希。连续重复相同调用且环境未变化时，不再次执行副作用工具，而是返回缓存结果或明确告知重复。

 进展不变量。 观察已解决子目标数、错误类型、文件哈希、数据库状态、测试通过数或检索到的新证据。若若干步后状态没有增量，即使工具参数略有变化，也可能是循环。

 错误分类与重试策略。 仅对瞬时错误重试，并采用指数退避和随机抖动；参数错误、权限错误和确定性业务拒绝不应盲目重试。

 熔断与降级。 某工具持续失败时打开 Circuit Breaker，切换备用工具、回退到只读模式、请求用户补充信息或转人工。

 可恢复终止。 退出前保存 Checkpoint、已完成事项、失败原因和下一步建议，使用户或人工能够从断点继续。

 
 不建议依赖“最近几轮 Thought 语义相似度”作为主要检测手段。一方面模型的隐式推理未必可见或适合持久化，另一方面语言表述可以变化但行为仍然重复。应优先基于可观察的 Action、参数、环境状态和任务进度检测。

 副作用工具还必须使用幂等键和执行前置条件。即使 Agent 重复调用，支付、发信、发布和删除操作也不能重复生效。高风险动作应采用准备、确认、提交的两阶段交互，并在提交前再次校验用户授权和当前状态。

 真正的兜底不是“发现循环后报错”，而是让系统在任何重复、超时和失败路径下都能控制成本、阻止重复副作用，并留下可恢复状态。 

 10. 多Agent之间通信方式是什么？如何做任务分发和结果合并？

 面试官： 多Agent之间怎么通信？如何做任务分发和结果合并？

 回答： 

 多 Agent 通信首先要选择协作拓扑，而不是先选择 Redis 还是 gRPC。常见结构包括 Supervisor-Worker、Planner-Executor、黑板系统、事件驱动协作和点对点会话。生产中通常优先采用中心编排或共享任务状态，因为它更容易控制权限、预算、重试和审计。

 通信方式可按可靠性需求选择：

 
 同进程低延迟协作：内存队列、Channel、 asyncio.Queue ，但进程退出后状态会丢失。

 同集群同步调用：gRPC/HTTP，适合短请求和明确响应，不适合把长任务可靠性全部压在连接上。

 异步可靠任务：Kafka、RabbitMQ、Redis Streams 或云消息队列，支持确认、重试、消费组和死信。Redis Pub/Sub 不保存消息，消费者离线时会丢失，不能直接作为关键任务总线。

 长周期工作流：使用持久化工作流引擎或事件溯源状态机，支持 Checkpoint、补偿和恢复。

 
 任务分发时，Planner 应输出结构化任务： task_id 、父任务、依赖、输入 Artifact、能力标签、优先级、Deadline、预算、权限和验收条件。Router 根据 Agent 能力、负载、数据位置、风险等级和历史质量调度。Worker 通过租约领取任务，使用幂等键执行，并通过 Heartbeat 防止任务永久卡死；租约到期后可以重派，但必须用 Fencing Token 防止旧 Worker 迟到写入。

 结果合并不能只依赖“多数投票”。多个 Agent 可能共享同一模型和同一错误，因此错误高度相关。更可靠的方法是按任务类型选择 Verifier：代码用测试和静态分析，检索用证据覆盖与引用，计算用程序复算，业务操作用环境状态和事务回执。对可拼接结果按 Schema 合并；对互斥结论保留证据、置信度和冲突原因，再由独立 Judge 或人工决策。

 所有消息应至少带有 trace_id 、 task_id 、 attempt 、 schema_version 、 producer 、时间、幂等键和 Artifact 引用，并限制 Agent 只能访问完成任务所需的工具与数据。

 多 Agent 系统的价值不在于“Agent 数量更多”，而在于能否把任务分解、隔离执行、可靠传递和可验证合并做成一条闭环。 

 11. 上下文压缩保留什么信息？如何判断哪些内容可以丢弃？

 面试官： 上下文压缩时保留什么信息？怎么判断哪些内容可以丢弃？

 追问： 压缩任务交给小模型还是大模型？

 回答： 

 上下文压缩应围绕“未来决策还依赖什么”来做，而不是围绕“哪些句子看起来重要”。建议保留以下几类信息：

 
 当前目标与完成标准。 用户到底要什么，什么状态才算完成。

 硬约束与授权。 时间、预算、格式、禁止项、权限范围、人工确认和安全规则。

 任务状态。 已完成步骤、未完成步骤、阻塞原因、重试次数和下一步。

 关键事实与实体。 明确确认的人、对象、数字、版本、路径、时间和业务状态。

 决策及依据。 为什么选择某方案，哪些方案被排除，依据来自哪个证据或工具回执。

 可恢复引用。 大型工具结果不必全文保留，但要保留 Artifact ID、查询条件、版本、摘要和关键片段。

 用户稳定偏好。 只保留经用户确认、与后续任务相关且在隐私策略允许范围内的偏好。

 
 通常可以压缩或丢弃的是：已被确定性结果取代的探索过程、重复日志、无新增信息的寒暄、已成功消费的大型中间输出，以及不影响后续行为的语言修辞。但不能简单删除所有“中间推理”。系统不需要保存模型私有 Chain-of-Thought，却需要保存可审计的决策摘要、证据和行动结果。

 判断是否可丢弃，可以对每条信息做四个问题：后续步骤是否直接依赖它；删除后能否从外部 Artifact 可靠恢复；它是否属于安全或合规证据；它是否已被更新且旧值只需进入变更历史。压缩后应执行一致性校验，例如实体、数字、否定关系、未完成任务和权限条件是否仍然完整。

 小模型还是大模型没有统一答案。结构化抽取、去重和日志归并可由规则或小模型完成；跨文档冲突、复杂计划和高风险事实压缩需要更强模型或双模型复核。选择标准应是压缩成本与下游错误成本，而不是模型价格本身。可以用事实保真率、约束召回率、未完成任务召回率、压缩率和最终任务成功率做评测。

 优秀的上下文压缩不是写一段更短的摘要，而是构造一个可追溯、可更新、足以驱动下一步行动的最小任务状态。 

 12. LLM调用失败怎么排查？

 面试官： 调用大模型API失败，你的排查流程是什么？

 回答： 

 排查 LLM 调用失败应先回答三个问题：请求是否到达服务端，服务端是否开始生成，失败是否可以安全重试。推荐按调用链分层，而不是一上来只看 CPU 和内存。

 
 确定影响范围。 是单请求、单模型、单地域、单租户还是全量失败；记录开始时间、错误率、P95/P99 延迟和最近变更。

 建立关联。 用 trace_id/request_id 串起网关、应用、模型服务和工具日志。记录模型、版本、区域、流式与否、输入/输出 Token、参数摘要和 HTTP 状态，但不得记录密钥或未脱敏的敏感 Prompt。

 定位网络阶段。 分别检查 DNS、TCP、TLS、代理、连接池、连接超时、首字节/首 Token 超时、流式空闲超时和总 Deadline。能够建连不代表流式响应没有中途断开。

 按状态码分类。 400 多为参数、Schema 或上下文问题； 401/403 是认证、权限或项目配置； 404 可能是模型名或 Endpoint； 409 常见于状态冲突； 429 是速率或配额限制； 5xx 表示服务端、上游依赖或容量异常。仍应以具体供应商错误码为准。

 检查请求内容。 计算真实 Token，验证模型上下文限制、Tool Schema、JSON 格式、图片大小、停止条件和内容安全策略。不要只按字符数猜 Token。

 最小化复现。 使用相同模型和认证发送最小请求，再逐项恢复参数、工具和上下文，找出触发差异。对比最近成功样本与失败样本，但先做脱敏。

 检查服务端资源。 若是自部署模型，再看队列长度、Batch、GPU OOM、KV Cache、显存碎片、推理引擎日志、模型权重、NCCL 和节点健康。

 
 重试必须服从错误语义。连接重置、部分 429/5xx 可采用指数退避、随机抖动和 Retry-After ；参数错误与权限错误不应重试。对有副作用的工具链要带幂等键，避免模型请求重试导致动作重复。流式调用中断后，不能默认把半截输出当成完整答案，应标记不完整并决定续写、重放或降级。

 生产系统还需要熔断、备用模型、区域切换、队列削峰、请求限流和质量降级，并监控成功率、首 Token 延迟、生成吞吐、Token 使用、取消率和降级率。 排障的关键是按层定位并保留请求关联，而不是把所有失败都归因于“网络波动”。 

 13. 分布式唯一ID怎么生成？要求自增怎么办？

 面试官： 多台机器如何生成唯一ID？如果要求自增呢？

 回答： 

 先要澄清“自增”的语义，因为唯一、趋势递增、单调递增、严格连续和按真实时间排序是不同要求，成本也完全不同。

 
 只要求全局唯一：UUIDv4、随机 128 位 ID 等最简单，但索引局部性较差。

 要求大致按时间排序：UUIDv7、ULID、Snowflake 类 ID 更适合数据库索引和日志排序。

 要求每个业务分区单调递增：可以为租户、订单域或分片分别维护 Sequence。

 要求全局严格递增：必须经过某个线性化的排序点，吞吐和可用性会受到约束。

 要求无空洞连续：分布式系统中代价最高，事务回滚、预取和故障都会造成 Gap，通常不应把它作为普通主键需求。

 
 Snowflake 一般由时间戳、节点 ID 和毫秒内序列组成，吞吐高、趋势递增且无需每次访问中心服务。风险包括时钟回拨、节点 ID 冲突、同毫秒序列耗尽和时间位溢出，因此需要时钟监控、回拨等待或逻辑时钟、节点租约与唯一分配。

 如果要求全局严格递增，可以使用数据库 Sequence/自增主键、Redis INCR 、具备共识的 ID 服务或单 Leader 排序服务。但这些方案都把生成过程集中到一个线性化点，需要高可用、持久化、故障切换和热点治理。Redis INCR 在单主正常工作时原子递增，但要结合持久化和故障切换语义评估是否可能回退或重复。

 Leaf Segment 一类号段模式让应用批量领取区间，再在本地递增，显著降低中心压力；代价是趋势递增而非严格按请求时间排序，实例故障还会浪费未使用号段。多数据库设置不同起点和步长能保证不重复，却不能保证按生成时间严格单调，更不能保证无空洞。

 数据库主键还要关注索引写入。完全随机 UUID 会让 B+ 树频繁页分裂；时间有序 ID 更利于追加写，但如果业务暴露连续 ID，又可能泄漏订单量并便于枚举，因此外部标识可与内部主键分离。

 面试时最好的回答不是背三个算法，而是先把唯一性、顺序性、连续性、吞吐、可用性和信息泄漏要求拆开，再选择最低成本的满足方案。 

 14. 缓存击穿、穿透、雪崩是什么？怎么解决？

 面试官： 缓存击穿、缓存穿透、缓存雪崩是什么？怎么解决？

 回答： 

 三者的共同结果都是后端承压，但触发机制不同。

 缓存穿透 是请求的数据本来就不存在，缓存和数据库每次都 Miss。常见来源是恶意枚举、参数错误或脏数据。治理手段包括参数校验、鉴权与限流、缓存短 TTL 的空值、布隆过滤器或 Cuckoo Filter。过滤器存在误判且需要维护新增/删除一致性，不能替代数据库校验；空值缓存也要防止占满缓存。

 缓存击穿 是某个高热 Key 在失效或回源期间，大量并发同时访问数据库。常用方案有 SingleFlight/互斥回源、逻辑过期加异步刷新、提前刷新、热点 Key 永不过期但由版本切换更新，以及本地缓存兜底。互斥锁必须有超时、持有者标识和异常释放；等待线程要有 Deadline，不能无限阻塞。

 缓存雪崩 是大量 Key 在相近时间失效，或整个缓存集群、网络链路同时不可用，导致大规模流量回源。解决方案包括 TTL 随机抖动、分批预热、缓存高可用与分片、本地多级缓存、限流、熔断、请求排队和后端容量保护。需要注意，随机 TTL 只能缓解集中失效，不能解决 Redis 整体故障。

 成熟系统还应处理缓存与数据库一致性。常见 Cache-Aside 流程是读缓存 Miss 后查库并回填，写操作先更新数据库再删除缓存，并通过消息、Binlog 或延迟双删处理失败窗口。对强一致业务，不能只靠“设置一个更短 TTL”；可以使用版本号、事务消息或直接绕开缓存。

 压测时应模拟热点过期、随机不存在 Key、缓存节点宕机、网络抖动和回源慢查询，并观察数据库 QPS、连接池、缓存命中率、回源并发和恢复时间。 穿透是不存在数据反复穿过，击穿是单个热点被打穿，雪崩是大面积缓存同时失守；治理重点分别是拦截无效请求、合并热点回源和保护整个后端。 

 15. Redis为什么能支撑高并发？

 面试官： Redis为什么能支撑很高并发？

 追问： Redis 6.0之后加了多线程IO，还能叫单线程吗？

 回答： 

 Redis 高并发不是因为某一个“单线程黑科技”，而是数据路径短、事件模型简单、数据结构高效和批量化能力共同作用的结果。

 首先，大多数访问在内存完成，避免了磁盘随机 I/O；但不能说网络请求是“纳秒级”，真实延迟还包含网络、协议解析、排队、持久化和主从复制，通常应以微秒到毫秒级服务指标衡量。

 其次，Redis 使用事件循环和 I/O 多路复用管理大量连接，避免为每个连接创建一个阻塞线程。核心命令执行长期以串行语义为主，因此单条命令天然具有原子性，也减少了共享数据结构上的锁竞争和上下文切换。但耗时 命令、Lua 脚本或大 Key 仍会阻塞后续请求，所以“单线程”不等于任何场景都快。

 再次，Redis 针对数据形态选择紧凑结构，例如 SDS、字典、Intset、Listpack、Quicklist 和 Skiplist，并结合渐进式 Rehash、过期策略和内存分配优化。Pipeline、MGET/MSET、连接复用和批量命令能够摊薄网络往返成本；集群分片则把压力扩展到多个节点。

 Redis 6.0 之后引入多线程网络 I/O，后续版本也持续演进并行能力。因此现在更准确的说法是： Redis 不是一个所有工作都由单线程完成的程序；它可以使用后台线程和 I/O 线程，但大量核心命令仍保持每个分片内的串行执行语义。 网络读取、协议处理和写回可以并行，命令对核心键空间的执行模型仍强调确定性和低锁开销。

 工程上还要关注高并发下的反例：大 Key 删除、全量扫描、复杂集合运算、Fork 抖动、AOF fsync 、主从全量同步、热点 Key 和客户端输出缓冲区都可能成为瓶颈。优化顺序通常是先修正命令复杂度和数据模型，再用 Pipeline 和连接池降低 RTT，随后做热点拆分、读写分离或 Cluster 扩容。

 Redis 能扛高并发的本质，是让绝大多数命令沿着短而可预测的数据路径执行；一旦命令复杂度、数据体量或持久化路径变得不可预测，单线程语义反而会放大尾延迟。 

 16. ThreadLocal为什么可能内存泄漏？

 面试官： ThreadLocal为什么可能内存泄漏？

 追问： 怎么避免？

 回答： 

 每个 Java Thread 内部都可以持有一个 ThreadLocalMap 。Map 中的 Entry 对 ThreadLocal Key 使用弱引用，但对 Value 使用强引用。当业务代码不再持有某个 ThreadLocal 时，Key 可能被 GC 回收并变成 null ，而 Value 仍然被 Thread -> ThreadLocalMap -> Entry -> Value 这条强引用链持有。

 如果线程很快结束，整个 Thread 和 Map 都可回收，问题不明显；在线程池、Web 容器和应用服务器中，Worker 线程长期存活，陈旧 Value 就可能长时间滞留，形成内存泄漏或至少是生命周期远超预期的内存占用。还要注意 ThreadLocalMap 是开放寻址的数组结构，不是普通的 Entry 链表。Java 会在 get/set/remove 等操作中机会性清理 Stale Entry，但不保证某个不再访问的槽位立即被清除。

 标准写法是：

 private static final ThreadLocal CONTEXT = new ThreadLocal<>();

try {
 CONTEXT.set(context);
 handleRequest();
} finally {
 CONTEXT.remove();
}
 
 避免问题需要做到：

 
 每次 set() 后在 finally 中 remove() ，即使异常或取消也要执行。

 在线程池任务边界统一安装清理装饰器，避免业务开发者漏清理。

 不在 ThreadLocal 中长期保存大对象、连接、ClassLoader、请求/用户对象或安全凭证。

 在线程复用时防止上下文串号。即使没有 OOM，前一个请求的用户身份泄漏给后一个请求也是严重问题。

 异步切线程时不要假设 ThreadLocal 自动传播。应显式传递 Context，或使用框架提供的受控上下文传播机制。

 
 static final ThreadLocal 只能让 Key 自身长期存在，减少 Key 被提前回收的情况，却不能替代 remove() ；Value 仍会在线程之间残留。 InheritableThreadLocal 在线程池中更容易产生错误继承，也要谨慎使用。

 ThreadLocal 泄漏的根因不是弱引用本身，而是 Key 与 Value 生命周期不对称，再叠加长期存活线程；解决方案是把清理放到任务生命周期边界。 

 17. BeanFactory和ApplicationContext有什么差异？

 面试官： BeanFactory和ApplicationContext有什么差异？

 回答： 

 BeanFactory 是 Spring IoC 容器最基础的能力契约，负责 Bean 的注册、查找、依赖注入、作用域和生命周期协作。 ApplicationContext 建立在更完整的 BeanFactory 体系之上，面向实际应用提供统一的运行时上下文。

 二者的差异可以从四层理解：

 
 容器能力。 ApplicationContext 同时具备可列举和分层 BeanFactory 能力，并集成资源加载、环境与 Profile、国际化消息、应用事件发布等接口。

 启动流程。 常见 ApplicationContext 在 refresh() 时会自动发现并执行 BeanFactoryPostProcessor 、注册 BeanPostProcessor ，并默认预实例化非 Lazy 的 Singleton。裸 BeanFactory 通常需要调用者自行完成更多装配步骤。

 基础设施集成。 AOP 自动代理、事务、注解处理、事件、组件扫描等能力通常由 Context 启动流程中的后处理器和基础设施 Bean 完整启用。

 使用场景。 普通 Spring/Spring Boot 应用几乎都使用 ApplicationContext ； BeanFactory 更常作为底层 SPI、轻量测试或框架内部扩展点。

 
 “BeanFactory 懒加载、ApplicationContext 饿加载”只是默认行为的简化说法，不是接口层面的绝对差异。Bean 是否延迟创建取决于 Bean 定义、作用域、Context 刷新策略和是否提前被依赖。 ApplicationContext 也支持 @Lazy ， BeanFactory 也可以主动预实例化 Singleton。

 还应注意，不要把 ApplicationContext 理解成另一个与 BeanFactory 平行的容器。它仍以 BeanFactory 作为核心注册表和实例工厂，只是在其上增加应用级生命周期与服务。Spring Boot 又进一步负责创建和配置合适的 ApplicationContext ，并加载自动配置。

 一句话总结：BeanFactory 定义“Bean 怎么被管理”，ApplicationContext 定义“一个 Spring 应用如何在完整环境中启动、扩展和协作”。 

 18. 配置中心宕机了应用怎么不挂？

 面试官： 如果配置中心宕机或连不上，怎样保证应用不挂？

 回答： 

 配置中心容灾不能统一采用“失败就读本地默认值”。配置分为普通业务参数、动态开关、服务发现信息、密钥和安全策略，不同配置的 Fail-Open/Fail-Closed 策略应不同。旧的推荐排序可以继续使用，过期证书、撤销名单或权限策略却可能必须拒绝启动或进入只读模式。

 完整方案包括：

 
 Last Known Good Snapshot。 客户端把最近一次校验通过的完整配置持久化到本地，包含版本、命名空间、时间、校验和或签名。启动连接失败时，只加载兼容且未超出允许陈旧时间的快照。

 分级启动策略。 非关键配置可使用默认值或快照；关键安全配置缺失时 Fail-Fast；部分业务可进入只读或降级模式，避免带着未知权限继续写操作。

 内存继续服务。 运行期间配置中心失联，已加载配置继续生效。后台以指数退避和随机抖动重连，避免配置中心恢复时所有实例同时重试形成惊群。

 原子更新。 拉取新配置后先做 Schema、类型、范围、依赖和签名校验，再整体切换版本。不能逐字段更新，让请求读到半新半旧状态。

 版本与回滚。 保留多个可用版本，若新配置导致错误率或启动失败，能够自动回退。配置变更要有审计、灰度和权限控制。

 服务端高可用。 多节点、多可用区、持久化存储、客户端地址列表和健康检查，不能把全部可靠性寄托在客户端快照上。

 
 本地 application.yml 可以提供非敏感的最小默认值，但不应硬编码生产密钥，也不能让默认值静默绕过安全限制。快照本身要设置文件权限、加密或签名校验，防止本地篡改。

 验证时要做故障演练：冷启动时中心不可用、运行中断联、新配置损坏、版本回退、中心恢复后大规模重连，以及快照过期。观察应用是否启动、功能是否降级、配置是否一致和是否产生越权。

 配置中心容灾的核心不是“永远不挂”，而是为每类配置明确可接受的陈旧程度和失败模式，让系统在依赖失效时仍保持可解释、可审计的行为。 

 19. TCP一定需要四次挥手吗？

 面试官： TCP为什么有四次挥手？一定需要四次挥手吗？

 回答： 

 TCP 是全双工协议，两个方向的字节流可以独立关闭。主动关闭方发送 FIN，只表示“我没有更多数据要发送”，并不表示对方也发送完了。被动关闭方先 ACK 这个 FIN，应用层可能还要继续发送剩余数据；等它也关闭发送方向时，再发自己的 FIN，最后由主动关闭方 ACK。因此逻辑上存在两个独立的半关闭过程：

 A -> B: FIN
B -> A: ACK
B -> A: FIN
A -> B: ACK
 
 但“四次挥手”描述的是四个逻辑报文动作，不保证线上一定看到四个独立 TCP Segment。如果 B 收到 FIN 后应用立即关闭，并且没有待发送数据，它对第一个 FIN 的 ACK 可以与自己的 FIN 合并在同一个 Segment 中，于是抓包可能表现为三次。关键条件是被动方何时进入关闭发送方向，而不是“开启延迟 ACK 就一定三次”。

 其他情况也可能不同：双方同时主动关闭时会发生 Simultaneous Close；连接异常、进程强杀或设置特定 Socket 行为时可能通过 RST 中止，这不是正常的优雅关闭；中间设备和重传也会让抓包数量多于四个。

 最后一个 ACK 之后，主动关闭方通常进入 TIME_WAIT，等待 。原因是确保最后 ACK 丢失时还能重发，并让旧连接中的延迟报文在网络中消失，避免污染相同四元组的新连接。TIME_WAIT 不是“无用等待”，但在高并发短连接服务中需要通过连接复用、合理的端口与内核参数治理，而不是粗暴关闭协议保护。

 FIN 也占用一个序列号，ACK 确认的是对方 FIN 的下一个序列号。收到 FIN 只关闭接收方向中的“对方继续发送”能力，本端仍可以发送数据，这正是 TCP Half-Close 的语义。

 因此，TCP 关闭需要两个方向分别确认，但四个逻辑动作可以合并成更少的报文段；是否合并取决于应用关闭时机和协议栈行为。 

 20. 手撕：实现执行器，相同key串行、不同key并行

 面试官： 实现一个执行器，相同key的任务串行执行，不同key的任务并行执行。

 回答： 

 核心不变量有两个：同一个 Key 在任意时刻最多运行一个任务；不同 Key 的任务可以交给共享线程池并行运行。不能只用 ConcurrentHashMap 就认为线程安全，还要原子处理“入队、启动消费者、队列清空和删除 Key”之间的竞态，否则可能出现两个消费者同时运行，或新任务加入旧队列后无人继续消费。

 下面的实现为每个 Key 建立一条 Lane。Lane 内使用短 synchronized 临界区保护队列和运行状态，实际任务在线程池中执行，不会持锁运行。Lane 关闭与 Map 删除之间通过 closed 和条件删除处理竞态。

 import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.Executor;
import java.util.concurrent.RejectedExecutionException;

public final class KeyedExecutor {
 private final ConcurrentHashMap lanes = new ConcurrentHashMap<>();
 private final Executor executor;

 public KeyedExecutor(Executor executor) {
 this.executor = Objects.requireNonNull(executor);
 }

 public CompletableFuture submit(K key, Runnable action) {
 Objects.requireNonNull(key);
 Objects.requireNonNull(action);

 Task task = new Task(action);
 for (;;) {
 Lane lane = lanes.computeIfAbsent(key, Lane::new);
 if (lane.enqueue(task)) {
 return task.result;
 }
 // 该 Lane 已完成关闭，帮助移除后重试到新 Lane。
 lanes.remove(key, lane);
 }
 }

 private final class Lane {
 private final K key;
 private final ArrayDeque queue = new ArrayDeque<>();
 private boolean running;
 private boolean closed;

 private Lane(K key) {
 this.key = key;
 }

 boolean enqueue(Task task) {
 boolean shouldSchedule = false;
 synchronized (this) {
 if (closed) {
 return false;
 }
 queue.addLast(task);
 if (!running) {
 running = true;
 shouldSchedule = true;
 }
 }
 if (shouldSchedule) {
 scheduleNext();
 }
 return true;
 }

 private void scheduleNext() {
 try {
 executor.execute(this::runOne);
 } catch (RejectedExecutionException ex) {
 failRemaining(ex);
 }
 }

 private void runOne() {
 Task task;
 synchronized (this) {
 task = queue.pollFirst();
 if (task == null) {
 running = false;
 closed = true;
 }
 }

 if (task == null) {
 lanes.remove(key, this);
 return;
 }

 if (!task.result.isCancelled()) {
 try {
 task.action.run();
 task.result.complete(null);
 } catch (Throwable ex) {
 task.result.completeExceptionally(ex);
 }
 }

 // 前一个任务完全结束后，才调度同 Key 的下一个任务。
 scheduleNext();
 }

 private void failRemaining(Throwable cause) {
 List pending;
 synchronized (this) {
 if (closed) {
 return;
 }
 closed = true;
 running = false;
 pending = new ArrayList<>(queue);
 queue.clear();
 }
 lanes.remove(key, this);
 pending.forEach(task -> task.result.completeExceptionally(cause));
 }
 }

 private static final class Task {
 private final Runnable action;
 private final CompletableFuture result = new CompletableFuture<>();

 private Task(Runnable action) {
 this.action = action;
 }
 }
}
 
 复杂度方面，提交和出队平均为 ；空间复杂度为 ，其中 是活跃 Key 数， 是排队任务数。单个 Key 的吞吐受串行约束，不同 Key 的并行度受底层 Executor 限制。

 生产实现还应补充：每个 Key 的队列上限和背压；任务 Deadline 与取消；Metric 和 Trace；线程池关闭后的拒绝策略；热点 Key 公平性；Key 长期不释放的泄漏检查；以及是否允许前一个任务失败后继续执行后续任务。若任务有外部副作用，还要使用幂等键。

 原始常见写法中，先发现队列为空，再分别删除 processing 和 queues ，可能与并发 submit() 交错，造成任务落入即将被删除的旧队列。 这道题真正考查的不是会不会使用并发容器，而是能否证明“每个 Key 只有一个消费者”并正确处理队列从空到非空、再从非空到空的状态转换。

 讲解一下上述三题的思路

 回答： 

 由于三道题的具体题面未公开，这里只能回答讲解方法，不能虚构具体算法。讲解应采用“问题定义 -> 核心不变量 -> 方案选择 -> 正确性 -> 复杂度/风险 -> 验证”的顺序。

 先说明输入、输出、约束与自己做出的假设，再用一句话概括方案。算法题要讲清核心不变量和为什么不会漏解；工程题要画出数据流、状态、接口和失败路径；模型题要说明数据、目标函数、训练/推理差异和评测。然后解释为什么选择当前方案，以及为什么没有选择更复杂或更常见的替代方案。

 代码讲解不应逐行朗读，而应围绕模块边界、关键状态、异常处理和测试展开。若实现未完成，要明确已完成部分的行为保证、未完成部分和后续方案。最后使用样例、边界条件、反例或测试结果证明，而不是用“应该没问题”收尾。

 对项目定制题，还应主动连接简历：原项目中的哪些组件可以复用，哪些假设在新场景下失效，以及如何做最小改造。这能体现候选人理解的是问题机制，而不只是背过自己的项目代码。

 第一段实习为何时间这么短

 回答： 

 这类问题主要判断稳定性、履约意识和经历真实性。回答应直接说明客观原因、已完成的职责与交接情况，不回避，也不要贬低原团队。

 如果是项目制、短期实习或学校安排，可以说清约定周期和实际完成内容；如果因业务调整、团队变化、方向不匹配或个人选择提前结束，应说明自己如何沟通、完成交接，以及从中形成了什么更清晰的职业判断。若确实存在个人决策失误，也可以承认当时评估不充分，并说明之后如何改进岗位筛选和承诺管理。

 一个完整答案至少包含四点：实习起止和原定周期；提前或按期结束的真实原因；离开前完成的交付与交接；为什么当前岗位不会重复同样问题。避免使用“没学到东西”“领导不行”“工作太杂”这类情绪评价，也不要编造学校或家庭原因。

 面试官真正关心的是：候选人是否能对自己的选择负责，是否完成了承诺，以及当前求职方向是否稳定。事实清楚、边界明确的回答，比试图把短经历包装成长项目更可信。

 为什么不转正，而是去其它地方

 回答： 

 回答要区分“没有转正机会”“有机会但主动放弃”和“仍未到转正节点”，不能用模糊表述让面试官猜测。

 如果有转正机会但选择其他方向，可以从业务方向、技术成长、岗位职责和长期目标解释。例如原岗位更偏应用交付，而自己希望深入 Agentic RL、训练基础设施和可验证环境；或者原团队的正式岗位地域、组织方向与个人长期规划不一致。重点是说明这是一项经过比较的职业选择，而不是单纯追逐公司名气。

 如果没有转正名额或结果，应如实说明团队 HC、实习性质和反馈，不把组织原因包装成主动选择；同时说明自己从该段经历中获得了哪些可迁移能力。若转正评估未通过，更应说明收到的具体反馈、采取的改进和当前证据。

 最后落到当前岗位：阿里云 AI Infra 的 Agentic RL、工程系统和政企约束为何与自己的能力主线匹配。不要承诺“永远不离开”，而要证明自己理解岗位实际内容，并愿意在这个问题域形成持续积累。

 选择OPD的动机以及数据筛选时的策略，为什么不使用学生错误的轨迹？

 回答： 

 这里的 OPD 通常指 On-Policy Distillation。普通离线蒸馏让学生学习教师生成的轨迹，训练前缀主要来自教师分布；部署时前缀却来自学生自身，一旦学生早期出现偏差，后续就进入训练数据很少覆盖的状态。OPD 先让当前学生生成轨迹，再让教师在同一个学生前缀上提供 token 分布监督，从而缩小 train-serving mismatch。

 一种常见目标是：

 

 数据筛选至少要检查：任务和输入是否合法；最终答案或环境状态能否验证；工具执行是否真实成功；轨迹是否越权、超预算或依赖污染信息；学生与教师在当前前缀上的分布兼容度；长度、领域和难度是否均衡；训练集与评测集是否按任务模板、用户或环境去重。

 “为什么不使用学生错误轨迹”需要谨慎回答。 标准 OPD 并不必然排除所有错误轨迹 。学生错误前缀恰恰是 on-policy 分布的一部分，教师若仍能在该状态下给出可靠纠偏，保留可恢复的 near-miss 可以训练错误恢复能力。项目若只保留最终正确轨迹，通常是因为完全失败后的前缀已严重偏离教师熟悉分布，教师 token 概率不再是可信监督；错误轨迹也可能包含奖励污染、工具异常或不可恢复状态，直接蒸馏会放大噪声。

 更稳妥的策略不是“一错全删”，而是按可恢复性分层：保留错误发生前的有效前缀；对教师/学生 top-k 重合度低或 KL 异常的后缀降权、截断；保留经 verifier 确认的纠错轨迹；对系统故障和标注错误直接剔除。只保留成功轨迹会产生幸存者偏差并削弱恢复能力，因此必须通过消融比较成功轨迹、near-miss 和完整失败轨迹对任务成功率、恢复率和训练稳定性的影响。

 过程奖励和结果奖励的本质区别是什么？过程奖励的奖励信号从哪来？如何解决过程奖励信号的偏差

 回答： 

 结果奖励只评价最终状态，例如答案是否正确、测试是否通过、订单是否完成；过程奖励评价中间步骤或状态转移，例如是否选对工具、参数是否合法、是否取得必要证据、是否遵循流程。二者的本质区别是 信用分配粒度 ，不是“一个客观、一个主观”。结果奖励也可能被错误 verifier 污染，过程奖励也可以来自确定性环境。

 结果奖励通常更接近真实目标、较难被手工过程模板束缚，但长轨迹下稀疏、方差高，很难判断哪一步造成成败。过程奖励提供稠密反馈、加速学习，却容易把人为偏好的“标准步骤”错当成唯一正确路径，导致 reward hacking 或抑制新策略。

 过程信号可来自：规则和状态机；代码测试、数据库状态和工具返回；人工逐步标注；LLM/奖励模型对步骤正确性打分；从成败轨迹训练的 Process Reward Model；逆强化学习或偏好对；以及势函数差分：

 

 在满足条件时，potential-based shaping 能降低改变最优策略的风险。

 控制偏差需要多层校准：优先使用可执行 verifier 和业务状态；让不同标注者/评估器交叉复核并测一致性；对 LLM Judge 做顺序随机化、盲评和置信度校准；用 held-out 轨迹验证过程分是否真的预测最终成功；限制过程奖励权重并保留终局奖励主导；监控“过程高分但任务失败”的反例；定期用新策略轨迹重训奖励模型，减轻分布漂移。高风险业务约束应由运行时强制，不能只变成一个可被收益抵消的负奖励。

 回答： 

 “双层奖励”通常是 turn-level 过程奖励与 dialogue-level 终局奖励的组合。每轮奖励衡量意图识别、信息增益、工具选择、事实性、合规和对话效率；终局奖励衡量任务是否完成、用户目标是否满足、是否正确转人工以及总成本。可以写成：

 

 其中 是时延、Token、工具调用等成本， 是越权、重复询问、错误承诺等惩罚。权重不能拍脑袋设置，应通过离线相关性、策略消融和线上 guardrail 校准；硬合规约束不能只靠有限惩罚表达。

 用户模拟器应显式建模隐藏目标和状态。每个 episode 采样用户画像、任务目标、已知信息、耐心、语言风格、风险等级和可接受结果；模拟器只看到用户在真实场景能看到的信息，并根据 Agent 回复更新内部状态，产生下一轮话语、终止、纠正或转人工行为。对政企业务，还要覆盖信息缺失、需求变更、拒绝授权、长文本、方言/口语、对抗输入和多角色审批。

 避免过拟合不能只靠增加同义改写。应按用户、组织、任务模板和时间切分训练/验证/测试，防止同一脚本换词后跨集合泄漏；使用多个不同模型、规则模拟器和真实日志混合，随机化画像、目标、错误和环境反馈；保留真实用户盲测集；比较跨模拟器泛化；对模拟器与被训 Agent 做模型家族隔离，避免共享偏好形成共谋；定期用线上人工抽检和新失败案例更新环境。

 最终目标不是在一个模拟器里拿高分，而是在真实用户分布上提高任务成功率，同时不恶化错误转人工、合规、成本和用户体验。

 多轮对话中评测如何进行，转人工率如何评测？怎么进行的A/B测试？

 回答： 

 多轮评测必须以完整会话为单位，单轮 BLEU、相似度或 Judge 分不能代表任务完成。离线评测集应覆盖主要意图、长尾、高风险、信息缺失、目标变化和工具异常，并固定用户模拟器/回放环境版本。核心指标包括：端到端任务成功率、约束遵循率、事实与工具状态一致性、平均轮数、重复询问率、恢复率、P95 延迟、Token/工具成本、用户满意度和安全违规率。

 转人工率要先定义 eligible conversation 和 transfer event：

 

 但这个总指标不能单独优化。应区分 必要转人工 和 可避免转人工 ：高风险、用户主动要求或系统能力边界内的正确转人工是好行为；Agent 误判、循环、工具失败造成的转人工才是损失。需要同时统计应转未转率、误转率、转人工前轮数、人工处理时长、人工一次解决率和转接时上下文完整率。

 A/B 测试应按用户或会话稳定随机，避免同一用户跨组污染；提前定义主指标、guardrail、最小可检测效应、样本量和观察窗口。先做日志回放、影子流量和小比例灰度，再逐步放量。比较时控制渠道、用户类型、问题难度和时间效应，必要时采用分层随机或 CUPED 降低方差。实验期间监控合规、投诉、错误操作、延迟和人工队列容量，并设置自动回滚阈值。

 不能只报告转人工率下降。如果下降来自 Agent 拒绝转人工、错误自信或延长对话，业务反而更差。真正的成功应表现为任务成功率提高、可避免转人工下降，同时必要转人工召回和安全指标不退化。

 如何解决多轮对话的冷启动 和 业务约束遵循问题？

 回答： 

 冷启动包含两层：新系统缺少高质量对话轨迹，新用户/新场景缺少状态。训练冷启动可以从业务规则、历史人工服务日志和专家流程构造 SFT 数据，再用多样化用户模拟器生成可验证轨迹；先训练基本意图、槽位、工具和终止能力，再进入 on-policy RL。数据必须脱敏、去重并按场景切分；不能把客服历史回复直接当成全部正确答案。上线前先做离线回放和 shadow evaluation，小流量灰度后再用真实失败案例迭代。

 会话冷启动则需要在最少轮数内识别目标、收集必要槽位和权限信息。可以使用显式任务状态、分层意图路由、默认配置和澄清策略，但不能为了减少轮数猜测高风险字段。对重复用户，可以在授权后召回稳定偏好；历史推断不得覆盖当前明确指令。

 业务约束应分成软约束和硬约束：语气、简洁度、优先级等可以进入 Prompt、SFT 或 reward；权限、金额、数据范围、流程状态、合规和不可逆操作必须由 Schema、规则引擎、状态机、工具鉴权和人工审批强制执行。模型只生成候选动作，执行层再次检查 precondition、幂等和副作用。

 训练中可以加入合规正反例、对抗用户、拒答与正确转人工轨迹，并用约束奖励或 constrained policy optimization 减少违规；但 RL 奖励不能替代硬安全边界。评测要同时看任务成功率和每类约束违反率，并对严重违规采用零容忍门禁，而不是用平均奖励掩盖低频高损失事件。

 Verl中的AgentLoop的特点是什么？

 回答： 

 verl 的 AgentLoop 是面向 多轮 rollout 与 Agentic RL 训练 的轨迹生成抽象。它不是 LangGraph 一类面向线上业务编排的完整 Agent 框架，也不负责规定工具应如何定义；它关心的是如何让用户自定义循环与模型、工具或环境交互，并产出可用于 PPO/GRPO 等训练的准确轨迹。

 核心接口是 AgentLoopBase.run(...) 。自定义实现可以多次调用生成服务、执行工具、与环境交互或反思，最终返回 AgentLoopOutput 。关键字段包括 prompt_ids 、 response_ids 和 response_mask ：模型自己生成的 token 标为 1，工具 Observation 和 padding 标为 0，使策略损失只作用于策略生成部分。当前实现还可携带多模态数据、轨迹奖励、轮数、指标和额外字段。

 它的工程特点包括：

 
 异步并发 rollout。 Worker 为样本启动协程，适合工具等待时间不一致的多轮轨迹。

 推理后端抽象。 可对接 vLLM、SGLang 等异步生成服务，并支持 token-in/token-out 与聊天接口。

 请求级负载均衡与粘性会话。 首轮选择负载较低的推理服务，后续轮次保持到同一实例，利于缓存和会话一致性。

 训练与 rollout 协同。 rollout 前同步训练权重并唤醒推理服务，结束后释放 KV Cache、卸载权重，为训练阶段让出资源。

 保留原始 token 轨迹。 多轮 RL 中若把最终 messages 重新套 chat template，工具解析和 decode-encode 可能改变 token，导致轨迹偏离行为策略。AgentLoop 直接维护连续 token 和 mask，避免这一关键 off-policy 误差。

 可插拔循环。 单轮、工具调用或业务自定义 AgentLoop 可以通过配置注册；框架提供调度与训练接口，工具语义、环境状态和终止条件仍由用户实现。

 
 局限也要说明：多轮轨迹的 reward 归因、工具错误、超长上下文、环境可恢复性和并发尾延迟不会因为使用 AgentLoop 自动解决；其 API 在不同版本仍可能演进，生产项目必须锁定版本并以实际代码为准。

 业务方向：Agentic RL训练，2B方向

 回答： 

 这条更像面试官披露的信息，而不是需要候选人作答的问题。反问的目标应是确认岗位的真实训练闭环和工程约束，而不是继续展示名词。

 可以围绕以下方向提问：2B 是模型参数规模、业务线代号还是专项名称；当前 Agentic RL 的主要任务是工具调用、多轮客服、代码/数据分析还是通用政企 Agent；训练使用 PPO、GRPO、OPD 或混合方案的原因；环境和 verifier 如何构造；rollout 是在线真实系统、沙箱还是用户模拟器；最主要瓶颈是环境吞吐、reward 可靠性、长轨迹稳定性还是线上泛化；岗位需要负责算法、训练框架、推理基础设施还是评测平台中的哪些部分。

 一面

 根据简历中的项目定制化了三个题目，限时40分钟，三选二

 回答： 

 针对“40 分钟、三选二”的项目定制题，合理策略是先用 2～3 分钟完成选题和时间预算：快速判断每题的需求清晰度、可验证性、与自己熟悉技术栈的匹配度以及实现风险，优先选择能够形成完整闭环的两题，而不是选择看起来最炫但无法在时限内验证的题。

 执行时可以把每题拆成四段：先复述目标、输入输出、约束和非目标；再给出最小可行设计与关键数据结构；然后实现主流程和最重要的异常路径；最后运行样例、自造边界用例或最小测试。建议预留至少 5～8 分钟做验证与讲解准备。若题目来自简历项目，还要说明新题与原项目哪些条件相同、哪些不同，不能机械复制已有方案。

 评分重点通常不只是代码是否完成，还包括问题澄清、方案取舍、代码边界、测试意识和能否解释失败。遇到模糊条件应显式写下假设；无法完成全部功能时，应交付一个行为正确、边界明确、可继续扩展的版本，并说明剩余风险。不要为了覆盖更多功能牺牲核心正确性。

 自我介绍，实习/项目/自我优势等

 回答： 

 针对 AI Infra、政企业务和 Agentic RL 岗位，自我介绍应在 90 秒左右建立“工程系统 + 模型训练 + 业务落地”的主线，而不是逐项念简历。

 可以按以下结构组织：

 
 一句话定位。 说明学历或工作阶段、主要方向，以及最相关的能力，例如大模型后训练、Agent 多轮交互、分布式训练或推理工程。

 选择一段最相关实习。 交代业务目标、数据规模、自己负责的模块、关键技术决策和真实验证指标。必须区分团队成果与个人贡献。

 选择一个代表项目。 用“问题 -> 数据/环境 -> 训练方法 -> 奖励与评测 -> 部署约束”讲清闭环。若项目涉及 OPD 或多轮 RL，要说明为什么该方法比 SFT、离线蒸馏或单轮 RL 更适合，以及失败轨迹如何处理。

 总结自我优势。 不说“学习能力强”这类空话，而是用证据说明：能够把论文方法落到训练代码，能处理 reward 偏差、rollout 稳定性和评测泄漏，也理解政企业务中的权限、合规、可审计与人工接管。

 落到岗位。 说明自己希望继续解决 Agentic RL 从环境构造、轨迹生成、训练到线上评测的系统问题。

 
 所有指标都应给出口径、样本范围和对照组。没有线上 A/B 就明确说是离线回放或灰度数据；不能把模型自评、单次演示或团队总体收益包装成个人线上增益。

 交流环节

 讲解一下上述三题的思路

 回答： 

 由于三道题的具体题面未公开，这里只能回答讲解方法，不能虚构具体算法。讲解应采用“问题定义 -> 核心不变量 -> 方案选择 -> 正确性 -> 复杂度/风险 -> 验证”的顺序。

 先说明输入、输出、约束与自己做出的假设，再用一句话概括方案。算法题要讲清核心不变量和为什么不会漏解；工程题要画出数据流、状态、接口和失败路径；模型题要说明数据、目标函数、训练/推理差异和评测。然后解释为什么选择当前方案，以及为什么没有选择更复杂或更常见的替代方案。

 代码讲解不应逐行朗读，而应围绕模块边界、关键状态、异常处理和测试展开。若实现未完成，要明确已完成部分的行为保证、未完成部分和后续方案。最后使用样例、边界条件、反例或测试结果证明，而不是用“应该没问题”收尾。

 对项目定制题，还应主动连接简历：原项目中的哪些组件可以复用，哪些假设在新场景下失效，以及如何做最小改造。这能体现候选人理解的是问题机制，而不只是背过自己的项目代码。

 第一段实习为何时间这么短

 回答： 

 这类问题主要判断稳定性、履约意识和经历真实性。回答应直接说明客观原因、已完成的职责与交接情况，不回避，也不要贬低原团队。

 如果是项目制、短期实习或学校安排，可以说清约定周期和实际完成内容；如果因业务调整、团队变化、方向不匹配或个人选择提前结束，应说明自己如何沟通、完成交接，以及从中形成了什么更清晰的职业判断。若确实存在个人决策失误，也可以承认当时评估不充分，并说明之后如何改进岗位筛选和承诺管理。

 一个完整答案至少包含四点：实习起止和原定周期；提前或按期结束的真实原因；离开前完成的交付与交接；为什么当前岗位不会重复同样问题。避免使用“没学到东西”“领导不行”“工作太杂”这类情绪评价，也不要编造学校或家庭原因。

 面试官真正关心的是：候选人是否能对自己的选择负责，是否完成了承诺，以及当前求职方向是否稳定。事实清楚、边界明确的回答，比试图把短经历包装成长项目更可信。

 为什么不转正，而是去其它地方

 回答： 

 回答要区分“没有转正机会”“有机会但主动放弃”和“仍未到转正节点”，不能用模糊表述让面试官猜测。

 如果有转正机会但选择其他方向，可以从业务方向、技术成长、岗位职责和长期目标解释。例如原岗位更偏应用交付，而自己希望深入 Agentic RL、训练基础设施和可验证环境；或者原团队的正式岗位地域、组织方向与个人长期规划不一致。重点是说明这是一项经过比较的职业选择，而不是单纯追逐公司名气。

 如果没有转正名额或结果，应如实说明团队 HC、实习性质和反馈，不把组织原因包装成主动选择；同时说明自己从该段经历中获得了哪些可迁移能力。若转正评估未通过，更应说明收到的具体反馈、采取的改进和当前证据。

 最后落到当前岗位：阿里云 AI Infra 的 Agentic RL、工程系统和政企约束为何与自己的能力主线匹配。不要承诺“永远不离开”，而要证明自己理解岗位实际内容，并愿意在这个问题域形成持续积累。

 选择OPD的动机以及数据筛选时的策略，为什么不使用学生错误的轨迹？

 回答： 

 这里的 OPD 通常指 On-Policy Distillation。普通离线蒸馏让学生学习教师生成的轨迹，训练前缀主要来自教师分布；部署时前缀却来自学生自身，一旦学生早期出现偏差，后续就进入训练数据很少覆盖的状态。OPD 先让当前学生生成轨迹，再让教师在同一个学生前缀上提供 token 分布监督，从而缩小 train-serving mismatch。

 一种常见目标是：

 

 数据筛选至少要检查：任务和输入是否合法；最终答案或环境状态能否验证；工具执行是否真实成功；轨迹是否越权、超预算或依赖污染信息；学生与教师在当前前缀上的分布兼容度；长度、领域和难度是否均衡；训练集与评测集是否按任务模板、用户或环境去重。

 “为什么不使用学生错误轨迹”需要谨慎回答。 标准 OPD 并不必然排除所有错误轨迹 。学生错误前缀恰恰是 on-policy 分布的一部分，教师若仍能在该状态下给出可靠纠偏，保留可恢复的 near-miss 可以训练错误恢复能力。项目若只保留最终正确轨迹，通常是因为完全失败后的前缀已严重偏离教师熟悉分布，教师 token 概率不再是可信监督；错误轨迹也可能包含奖励污染、工具异常或不可恢复状态，直接蒸馏会放大噪声。

 更稳妥的策略不是“一错全删”，而是按可恢复性分层：保留错误发生前的有效前缀；对教师/学生 top-k 重合度低或 KL 异常的后缀降权、截断；保留经 verifier 确认的纠错轨迹；对系统故障和标注错误直接剔除。只保留成功轨迹会产生幸存者偏差并削弱恢复能力，因此必须通过消融比较成功轨迹、near-miss 和完整失败轨迹对任务成功率、恢复率和训练稳定性的影响。

 过程奖励和结果奖励的本质区别是什么？过程奖励的奖励信号从哪来？如何解决过程奖励信号的偏差

 回答： 

 结果奖励只评价最终状态，例如答案是否正确、测试是否通过、订单是否完成；过程奖励评价中间步骤或状态转移，例如是否选对工具、参数是否合法、是否取得必要证据、是否遵循流程。二者的本质区别是 信用分配粒度 ，不是“一个客观、一个主观”。结果奖励也可能被错误 verifier 污染，过程奖励也可以来自确定性环境。

 结果奖励通常更接近真实目标、较难被手工过程模板束缚，但长轨迹下稀疏、方差高，很难判断哪一步造成成败。过程奖励提供稠密反馈、加速学习，却容易把人为偏好的“标准步骤”错当成唯一正确路径，导致 reward hacking 或抑制新策略。

 过程信号可来自：规则和状态机；代码测试、数据库状态和工具返回；人工逐步标注；LLM/奖励模型对步骤正确性打分；从成败轨迹训练的 Process Reward Model；逆强化学习或偏好对；以及势函数差分：

 

 在满足条件时，potential-based shaping 能降低改变最优策略的风险。

 控制偏差需要多层校准：优先使用可执行 verifier 和业务状态；让不同标注者/评估器交叉复核并测一致性；对 LLM Judge 做顺序随机化、盲评和置信度校准；用 held-out 轨迹验证过程分是否真的预测最终成功；限制过程奖励权重并保留终局奖励主导；监控“过程高分但任务失败”的反例；定期用新策略轨迹重训奖励模型，减轻分布漂移。高风险业务约束应由运行时强制，不能只变成一个可被收益抵消的负奖励。

 多轮对话RL中怎么设置的双层奖励？怎么构造的用户模拟器？如何避免模拟器数据的过拟合问题？

 回答： 

 “双层奖励”通常是 turn-level 过程奖励与 dialogue-level 终局奖励的组合。每轮奖励衡量意图识别、信息增益、工具选择、事实性、合规和对话效率；终局奖励衡量任务是否完成、用户目标是否满足、是否正确转人工以及总成本。可以写成：

 

 其中 是时延、Token、工具调用等成本， 是越权、重复询问、错误承诺等惩罚。权重不能拍脑袋设置，应通过离线相关性、策略消融和线上 guardrail 校准；硬合规约束不能只靠有限惩罚表达。

 用户模拟器应显式建模隐藏目标和状态。每个 episode 采样用户画像、任务目标、已知信息、耐心、语言风格、风险等级和可接受结果；模拟器只看到用户在真实场景能看到的信息，并根据 Agent 回复更新内部状态，产生下一轮话语、终止、纠正或转人工行为。对政企业务，还要覆盖信息缺失、需求变更、拒绝授权、长文本、方言/口语、对抗输入和多角色审批。

 避免过拟合不能只靠增加同义改写。应按用户、组织、任务模板和时间切分训练/验证/测试，防止同一脚本换词后跨集合泄漏；使用多个不同模型、规则模拟器和真实日志混合，随机化画像、目标、错误和环境反馈；保留真实用户盲测集；比较跨模拟器泛化；对模拟器与被训 Agent 做模型家族隔离，避免共享偏好形成共谋；定期用线上人工抽检和新失败案例更新环境。

 最终目标不是在一个模拟器里拿高分，而是在真实用户分布上提高任务成功率，同时不恶化错误转人工、合规、成本和用户体验。

 多轮对话中评测如何进行，转人工率如何评测？怎么进行的A/B测试？

 回答： 

 多轮评测必须以完整会话为单位，单轮 BLEU、相似度或 Judge 分不能代表任务完成。离线评测集应覆盖主要意图、长尾、高风险、信息缺失、目标变化和工具异常，并固定用户模拟器/回放环境版本。核心指标包括：端到端任务成功率、约束遵循率、事实与工具状态一致性、平均轮数、重复询问率、恢复率、P95 延迟、Token/工具成本、用户满意度和安全违规率。

 转人工率要先定义 eligible conversation 和 transfer event：

 

 但这个总指标不能单独优化。应区分 必要转人工 和 可避免转人工 ：高风险、用户主动要求或系统能力边界内的正确转人工是好行为；Agent 误判、循环、工具失败造成的转人工才是损失。需要同时统计应转未转率、误转率、转人工前轮数、人工处理时长、人工一次解决率和转接时上下文完整率。

 A/B 测试应按用户或会话稳定随机，避免同一用户跨组污染；提前定义主指标、guardrail、最小可检测效应、样本量和观察窗口。先做日志回放、影子流量和小比例灰度，再逐步放量。比较时控制渠道、用户类型、问题难度和时间效应，必要时采用分层随机或 CUPED 降低方差。实验期间监控合规、投诉、错误操作、延迟和人工队列容量，并设置自动回滚阈值。

 不能只报告转人工率下降。如果下降来自 Agent 拒绝转人工、错误自信或延长对话，业务反而更差。真正的成功应表现为任务成功率提高、可避免转人工下降，同时必要转人工召回和安全指标不退化。

 如何解决多轮对话的冷启动 和 业务约束遵循问题？

 回答： 

 冷启动包含两层：新系统缺少高质量对话轨迹，新用户/新场景缺少状态。训练冷启动可以从业务规则、历史人工服务日志和专家流程构造 SFT 数据，再用多样化用户模拟器生成可验证轨迹；先训练基本意图、槽位、工具和终止能力，再进入 on-policy RL。数据必须脱敏、去重并按场景切分；不能把客服历史回复直接当成全部正确答案。上线前先做离线回放和 shadow evaluation，小流量灰度后再用真实失败案例迭代。

 会话冷启动则需要在最少轮数内识别目标、收集必要槽位和权限信息。可以使用显式任务状态、分层意图路由、默认配置和澄清策略，但不能为了减少轮数猜测高风险字段。对重复用户，可以在授权后召回稳定偏好；历史推断不得覆盖当前明确指令。

 业务约束应分成软约束和硬约束：语气、简洁度、优先级等可以进入 Prompt、SFT 或 reward；权限、金额、数据范围、流程状态、合规和不可逆操作必须由 Schema、规则引擎、状态机、工具鉴权和人工审批强制执行。模型只生成候选动作，执行层再次检查 precondition、幂等和副作用。

 训练中可以加入合规正反例、对抗用户、拒答与正确转人工轨迹，并用约束奖励或 constrained policy optimization 减少违规；但 RL 奖励不能替代硬安全边界。评测要同时看任务成功率和每类约束违反率，并对严重违规采用零容忍门禁，而不是用平均奖励掩盖低频高损失事件。

 Verl中的AgentLoop的特点是什么？

 回答： 

 verl 的 AgentLoop 是面向 多轮 rollout 与 Agentic RL 训练 的轨迹生成抽象。它不是 LangGraph 一类面向线上业务编排的完整 Agent 框架，也不负责规定工具应如何定义；它关心的是如何让用户自定义循环与模型、工具或环境交互，并产出可用于 PPO/GRPO 等训练的准确轨迹。

 核心接口是 AgentLoopBase.run(...) 。自定义实现可以多次调用生成服务、执行工具、与环境交互或反思，最终返回 AgentLoopOutput 。关键字段包括 prompt_ids 、 response_ids 和 response_mask ：模型自己生成的 token 标为 1，工具 Observation 和 padding 标为 0，使策略损失只作用于策略生成部分。当前实现还可携带多模态数据、轨迹奖励、轮数、指标和额外字段。

 它的工程特点包括：

 
 异步并发 rollout。 Worker 为样本启动协程，适合工具等待时间不一致的多轮轨迹。

 推理后端抽象。 可对接 vLLM、SGLang 等异步生成服务，并支持 token-in/token-out 与聊天接口。

 请求级负载均衡与粘性会话。 首轮选择负载较低的推理服务，后续轮次保持到同一实例，利于缓存和会话一致性。

 训练与 rollout 协同。 rollout 前同步训练权重并唤醒推理服务，结束后释放 KV Cache、卸载权重，为训练阶段让出资源。

 保留原始 token 轨迹。 多轮 RL 中若把最终 messages 重新套 chat template，工具解析和 decode-encode 可能改变 token，导致轨迹偏离行为策略。AgentLoop 直接维护连续 token 和 mask，避免这一关键 off-policy 误差。

 可插拔循环。 单轮、工具调用或业务自定义 AgentLoop 可以通过配置注册；框架提供调度与训练接口，工具语义、环境状态和终止条件仍由用户实现。

 
 局限也要说明：多轮轨迹的 reward 归因、工具错误、超长上下文、环境可恢复性和并发尾延迟不会因为使用 AgentLoop 自动解决；其 API 在不同版本仍可能演进，生产项目必须锁定版本并以实际代码为准。

 反问环节

 业务方向：Agentic RL训练，2B方向

 1. 自我介绍 + 详细了解（在校成绩、科研产出、项目经历）

 
 这题没啥技术含量，但面试官会追问细节，建议提前想好"故事线"。

 
 我的经验 ：别平铺直叙"我做了什么什么"，而要说"我遇到了什么问题，我是怎么解决的，结果是什么"。面试官听的不是你做了多少事，而是你做事的思路和深度。

 2. 平常怎么用AI辅助编码？

 
 这个我前面面经里也写过。不同面试官关注的点不一样——上一家关注"你用过哪些工具"，阿里云这位更关注"你是拿AI做什么类型的工作"。

 
 我的回答 ：

 
 现在基本离不开AI Coding工具了。主要是Claude Code和Cursor，但使用场景分几类：

 
 
 写胶水代码 ：比如写个Python脚本处理数据、写个配置文件，这类重复性工作直接让AI生成，我只需要review。

 
 重构优化 ：把一段写得烂的代码丢给AI，让它提优化建议，或者自动重构成更清晰的版本。

 
 写测试用例 ：手写单元测试太浪费时间了，让AI根据函数签名和逻辑生成测试用例，我只需要补边界条件。

 
 
 关键认知 ：AI写代码的能力很强，但"知道要写什么代码"的能力还是得自己来。它擅长实现，不擅长设计。别把架构决策交给AI。

 
 3. 你提到了用Skill，介绍一下你常用的Skill

 
 前面聊到AI Coding工具的时候我提了一句"会写一些自定义Skill来提升效率"，面试官立刻抓住了这点往下追问。这里指的是Claude Code里的Skill功能——把一些固定的操作流程封装成一个可复用的Skill。

 
 我常用的Skill ：

 
 
 代码审查Skill ：提交代码前跑一遍，检查潜在的bug、性能问题、代码风格。输入是diff，输出是审查意见列表。

 
 单元测试生成Skill ：给定一个函数，自动生成对应的测试用例，覆盖正常路径和边界条件。

 
 API文档生成Skill ：从代码注释和函数签名生成规范的API文档。

 
 
 面试官追问："这些Skill是你自己写的还是用的现成的？"我说自己写过几个简单的，也有直接从社区拿来改的。

 
 4. 这些Skill之间的区别知道吗？有看过知名Skill里面是怎么写的吗？

 
 这个问题把我问住了。我用Skill就是"能用就行"，从来没想过不同Skill的设计模式有什么区别。

 
 面试后查的资料 ：

 
 Skill的本质是一份结构化的Prompt + 执行逻辑。不同Skill的区别主要体现在几个维度：

 
 
 输入来源 ：有的是从用户对话中提取参数（比如"帮我review这段代码"），有的是从文件系统读取（比如"检查整个项目的lint错误"）。

 
 输出格式 ：有的只返回文本（如"代码解释"），有的需要返回结构化数据（如"JSON格式的审查报告"），有的需要执行操作（如"自动修复"）。

 
 执行环境 ：有些Skill纯粹是Prompt层面的（只是让模型按特定方式思考），有些需要调用外部工具（如运行测试、执行lint）。

 
 交互模式 ：一次性完成 vs 多轮对话逐步推进。

 
 
 知名Skill的设计 ：我确实看过社区一些热门Skill的源码，比如"单元测试生成"类的Skill，写得好的通常会把"分析函数逻辑→识别边界条件→生成测试用例→执行验证"拆成4个步骤，每个步骤有自己的子Prompt，而不是一股脑全塞给模型。

 
 5. 自己写过Skill吗？是用来做什么的？写Skill要注意什么？

 
 我写过一个"Git Commit Message生成器"的Skill，每次commit的时候自动生成符合规范的提交信息。

 职责单一 ：一个Skill只做一件事。别搞那种"既能review代码又能生成文档还能跑测试"的大杂烩。

 
 输入输出明确 ：用户调用Skill时需要传什么参数，Skill输出什么格式，要定义清楚。

 Token管理 ：Skill内部可能会调用多次LLM，每次的Prompt要节制，别一次吃掉大量Token。

 双阶段网络算法更精细，把任务分成了正负样本分类、 bbox 初次回归以及类别分类和 bbox 二次回归。

 而 YOLO 算法更简单粗暴，使用 backbone 对输入图像提取特征后，将特征图划分成 S × S S\times S S × S 的网格，物体的中心坐标落在哪个网络内，该网格（ grid ）就负责预测目标的置信度、类别和 bbox ； YOLOv2-v5 通过 1 × 1 1 \times 1 1 × 1 卷积输出特定通道数的特征图来，特征图有 N 个通道，对应的每个 grid 都会有 N 个值，分别对应置信度、类别和 bbox 坐标。

 2，说说你对 Focal Loss 的理解，为什么能解决分类问题中的类别不平衡问题？

 作者认为一阶段检测网络的精度不高的原因主要在于：极度不平衡的正负样本比例，从而导致 梯度（ gradient ）被容易样本（ easy example ）的损失主导 。

 作者通过 Focal Loss 公式让置信度高（即容易样本）的样本的损失衰减的更厉害，从而降低容易样本的 Loss 权重，从而让模型在后期尽量去学习那些 hard 的样本。

 3，如何在模型训练的时候判断是否过拟合，及模型过拟合问题如何解决？

 将训练数据划分为训练集和验证集， 80% 用于训练集， 20% 用于验证集（训练集和验证集一定不能相交）；训练的时候每隔一定 Epoch 比较验证集但指标和训练集是否一致，如果不一致，并且验证集指标变差了，即意味着过拟合。

 
 数据增强 , 增加数据多样性;

 正则化策略：如 Parameter Norm Penalties (参数范数惩罚), L1, L2 正则化;

 模型融合, 比如 Bagging 和其他集成方法;

 添加 BN （batch normalization）层或者 dropout 层（现在基本不用）;

 Early Stopping (提前终止训练)。

 underfitting 欠拟合的表现就是模型不收敛，即训练过程中验证集的指标比较差， Loss 不收敛。欠拟合的原因有很多种，这里以神经网络拟合能力不足问题给出以下参考解决方法：

5，何谓正则化？

通过给模型的代价函数（损失函数）添加被称为正则化项（`regularizer`）的惩罚，这称为将模型（学习函数为 $f(x; θ)$）正则化。正则化是一种思想（策略），**给代价函数添加惩罚**只是其中一种方法。

6，`L2` 正则化（权重衰减）原理，为什么它能防止模型过拟合？系数 $\lambda $ 如何取值？

`L2` 正则化（权重衰减）是另外一种正则化技术，通过加入的正则项对参数数值进行衰减，得到更小的权值。**当 $\lambda$ 较大时，会使得一些权重几乎衰减到零，相当于去掉了这一项特征，类似于减少特征维度**。假设待正则的网络参数为 $w$，`L2` 正则化为各个元素平方和的 $1/2$ 次方，其形式为：

$$L2 = \frac{1}{2}\lambda ||w||^{2}_{2}$$

实际使用时，一般将正则项加入目标函数，通过整体目标函数的误差反向传播，从而实现正则化影响和指导模型训练的目的。

7，`L1` 正则化原理，系数 $\lambda $ 如何取值？

`L1` 范数: 为向量 `x` 各个元素绝对值之和。`L1` 正则化可以使权值参数稀疏，方便特征提取。

vector > matrix_mul(vector > A, vector > B){
 /*二维矩阵相乘函数，时间复杂度 O(n^3)
 */
 // vector > A_T = matrix_transpose(A);

 int new_rows = A.size();
 int new_cols = (*B.begin()).size();
 int L = B.size();
 vector > C(new_rows, vector (new_cols,0));

 for(int i=0; i<new_rows; i++){
 for(int j=0; j<new_cols;j++){
 for(int k=0; k<L; k++){
 C[i][j] += A[i][k]*B[k][j];
 }
 // C[i][j] = vector_mul(A[i], get_col(B, j));

}

## 个人秋招经验分享（算法转研发）

来源：牛客网 ｜ 类型：面经 ｜ 发布：2021-09-19 ｜ [原文链接](https://www.nowcoder.com/discuss/353158565550563328)

本人情况，普通 211 本硕，今年四月找算法实习四处碰壁后下决心转研发，无实习无项目经历，截止目前已经收到阿里云，字节，海康，大华，贝壳的意向，其他的还有华为（待主管面），被 pass 的也有很多，拼多多 (hr 面挂 ) ，腾讯（ 2 面挂），以及数不清的中小厂二面挂，如有赞，滴滴等 

 
 

 打算将这五个月认识到的问题以及求职的方法做一个总结，并分享给大家，希望能帮助到和我一样想要转岗的人 

 
 

 关于转岗原因，每个人都有每个人的想法，我主要分享一下为了转岗我做了哪些事情 

 
 

 首先，是准备阶段。 

 
 

 考虑到我没有实习没有项目，在项目上一定是很吃亏的无法说服面试官，于是我考虑走底层与源码路线，即告诉面试官自己阅读过很多源码和很多底层实现。 

 
 

 为此，我做了一些准备。如 jvm 底层（细到字节码）， mysql 底层（细到 buffer pool ）， spring 底层（细到 refresh 整个流程， factory 初始化了哪些 processor 及其作用）， juc 大部分实现类的源码（如线程池用了哪些锁）， dubbo 源码等我自己都琢磨了一遍。琢磨方法是，先找视频看看，再自己翻一翻源码，最后进行思考与总结。 

 
 

 到现在，源码看多了反而变成了一种爱好，我没有背过八股文，我的学习方式是通过自己去探索底层实现并总结，反而记得会比单纯背八股文要牢而且有深度。 

 
 

 为了进一步充实简历，我写了两个耳熟能祥的项目，一个 rpc 框架，一个秒杀。目前看来，两个项目在中小厂面试官眼里就是没用的玩具，而大厂面试官很愿意跟你聊你具体实现的思路。对应到我的面经中就是，中小厂项目面基本都挂了，而大厂项目面聊得还可以。当然，我的两个项目都是自己经过优化的项目，加入了自己的理解与设计，在面试时才能保持从容。 

 
 

 进大厂最关键的一步还是算法基础，逢面必问。对此，我将力扣刷了近 400 道题，并对于有共性的解题方法进行总结，对于高频题我每周都会复习一遍。 

 
 

 接着，是实战阶段 

 
 

 我认为提前批与海投，成为我转岗成功的关键。我通过海投中小厂完成了面试练手，到了面大厂时变得十分从容并且游刃有余。大部分公司提前批除了免笔试外，流程也很快， hc 也会相对更多。在面试之后，我会根据面试官提出的问题与建议对我的项目进行优化。 

 
 

 最后，一些题外话 

 
 

 个人面下来，最大的感受是大厂偏底层，注重基础与个人学习能力，中小厂偏实战，注重个人实战经验，原因看破不说破。因此，我认为如果想进大厂，没有落地项目不要紧，打好基础，让面试官看到你发光的一面也是可以的
