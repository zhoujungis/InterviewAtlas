 三、失败经验分享 

 总聊自己也没什么意思，我给大家分享一些我面试出现过的很不应该的问题，不枉大家花费自己宝贵的时间阅读我的文章。为什么给大家分享失败经验，是因为我认为成功的路只有一条，而我远不算秋招成功的那一批人，但是失败的原因千奇百怪，避开一些失败的路，说不定误打误撞就走上成功的路。 

 1.面试定位 

 不同轮次的面试，他所代表的定位与含义是不同的。一般来说，能够约面，代表用人部门已经认可了你的简历，我是不推荐大家相信KPI面的说法的，公司有KPI面不假，但是当你接受了“自己面试失败是因为KPI”之后，你不会对面试有兴奋性了，你会认为“给我面试就是KPI”，导致你的每一次面试都没有强烈的表现欲，这是很严重的恶性循环：你面试失败-你认为是被KPI-你认为下一个也是KPI-你不好好准备-你面试失败-你验证了上一个是KPI-你不好好准备下一个。 

 一般来说，一面是同事面，二面是组长面，三面是部门主管面，一面更多考察技术深度，二面针对场景与潜在问题做提问，三面会宏观的针对部门业务，技术前景等做提问。 

 那么对待不同轮次的面试，准备策略肯定是不同的 ，一面之前对八股要多进行复习，包括简历上写的技术栈也要进行复习；二面就得针对简历中的业务内容做了解，摸透场景，数据流动，模块上下游，潜在的问题等；三面问的就是储备之外的问题了，什么都有可能问的出来，多看面经多积累就好。 

 我之前的失败经验就是，面试的时候，还没有摆正秋招的心态，当成找实习去准备，疯狂的背八股，刷力扣，最后一个都不问，大厂一面顺利通过，大厂二面全军覆没，国庆假期我每天抽出两三个小时针对性的捶打简历，上网搜索资料做知识补充，回去问同事具体的细节，最近的面试体验确实就好了一些。 

 2.自我介绍与答题技巧 

 自我介绍方面，不建议大家用一个通用的话术面试每一家公司，我更推荐大家 针对不同的岗位，要有不同的准备 ，比如针对数据岗，我的自我介绍更多的落在技术栈与职业规划，针对不垂直的业务岗，我的自我介绍着重讲业务背景等。 

 答题技巧方面， 首先你的回答一定是要有逻辑的 ，如果措辞不完全，可以向面试官申请拿张干净的纸和笔，一般面试官都会同意的，就在纸上写写你要说的东西，整理好语言再回答。然后答案我一般是总分结构的给出，先给我的大体思路，再说具体细节； 其次你说的东西要能落在你的简历上 ，尤其是和你的实习，和你的项目贴近的场景，一定要结合你的简历去说，给面试官兴趣，让他追问你的工作，把主动权掌握在你手上。 

 3.反问 

 反问是我最失败的地方，举几个例子：影石一面反问，我问面试官为什么没有问我的简历，是过往经历不匹配吗，我面试xx（其他大厂）都会问简历，遂第二天挂；小鹏二面问我有几个Offer和流程中，我把我所有二面所有意向所有横向全跟他说了，国庆节假期给我发邮件说挂。 

 反问是真正由你主导面试的部分，你的问题也很有含金量，如果只是问工作地在哪，部门的业务是什么，我的不足有哪些，那么这次反问是没有意义的。 多问一些你能做的，面试官能跟你讨论的，少问一些彼此都不能左右的常识 。 

 4.场景题 

 场景题曾经是我找实习最头疼的地方，每次遇到场景题，我首先就主动缴械了，后面面试多了之后，我对场景题总结出了一套自己的规律，可以理解为是类似AI Coding的模版，大家可以自己尝试套用： 

 1.这个场景是独立的，还是有上下游的？有上下游的话，要考虑业务的解耦，不要把自己服务的状态和其他服务强绑定； 

 2.这个场景有没有高实时性的需求？有的话考虑使用内存； 

 3.这个场景是不是分布式的？是的话需要考虑负载均衡与数据完整性，还要考虑分布式单点故障的可靠性； 

 4.服务内有没有上下游？有的话需要用消息队列做数据与通知的触达； 

 5.有没有持久化的需求？有的话需要接日志系统与存储方案，并且存储方案要考虑一致性； 

 6.数据量级是多少？海量数据要怎么存放？需不需要冷热分离、分库分表等？ 

 7.权限控制怎么做？做权限层网关还是每个接口独立鉴权？ 

 8.目前的这些组件，若有一个宕机了，整个系统还能不能运行？如果不能，怎么让他还能够运行起来，并不产生错误的结果？还是直接熔断该服务？ 

 9.会不会有并发冲突？会不会有幂等性问题？ 

 每次写场景题之前， 先思考这9个问题，再进行答案的探讨 ，你会有不一样的理解。现在使用我的这个规律，解答下面一道问题，可以把你的答案发布到评论区，供大家共同讨论： 

 思考你要设计一个分布式日志存储服务，是用来记录你现在的平台的日志，但是你的日志散落在各处，没办法统一管理，然后你的这个日志服务是要接Agent做分析的，但是这个分析日志的Agent不用你去编写，你只需要聚焦于这个日志存储服务。你的平台用户量很大，公司内部，公司外部都会使用，你的日志也很多，有系统日志，业务日志，你要怎么保证日志的可见性？并且你的平台已经存在了两三年了，日志量非常大，这个时候你又要怎么处理？ 

 

 四、秋招体会分享 

 由于业务，算法等赛道我不熟悉， 我只说一说我身处Data赛道的体会 。 

 现在已经是我秋招的第42天，去年这个时候我的师兄师姐有一些已经拿到了满意的结果，我认为我是比他们强的，但是我甚至拿不到去年同期他们的结果。 今年的秋招对Data Infra人来说是地狱级别的 ，去年只需要会Java基础，常见的场景题，再会一些Agent基础，甚至RAG基础就可以，没有实习我都可以接受你进来干中学；今年完全不是这样，我要懂Data+AI，要懂Doris（阿里云二面挂在这），要懂NebulaGraph（字节二面挂在这），要懂基于滑动窗口的分布式文件传输限速桶的Java实现（百度二面挂在这），要懂Kafka的集群运维（雷火一面挂在这），要懂Flink各个算子不同状态的监控方案（美团一面挂在这），还有更多就不说了，说不过来。 

 和26相比，27秋招难度大很多，但是世界本身就是不公平的，就像23秋招的人回看24的一样。 

 鹰隼不会羡慕金丝雀，因为优渥的土壤根本培育不出能够逆流而上的野兽， 对于那些想继续互联网秋招的牛友 ，现在唯一要做的就是把自己锻炼到简历上的每一个字你都能展开一千字论述，每一条八股你都能从开天辟地说到宇宙热寂，每一道力扣热题你看见题号就能默写出他的AC代码，每一道场景题你都能在心里搭建起他的框架。因为面试不代表意向，面试只是一个机会，你只有赢过这一场面试才能抓住这个机会，但也只是个机会，100次投递才可能换来1次机会，100次机会才可能转化成一次成功。 

 对于对互联网秋招失去信心的人来说 ，考公考编与国央企，是当下不一定最正确，但一定不会错的选择，今年的秋招确实不简单，我其实更建议学历与实习一般的人去考这种公司，这种稳定性是互联网无论大小厂都给不了的。 

 对于在思考日后升学还是就业的人来说 ，其实在就业方面我是后悔读研的，因为方向不对走不通算法，其次时机不好赶上堪比23秋招的地狱难度，如果把现在的我平移到24或者26秋招，可能结果会比现在好很多；但是在生活方面，我没有后悔读研，我在读研期间认识了现在的女朋友，翘课翘实验跟她一起游历祖国的大好河山，现在已经一起走过了十几个省份与特区；找到了几份不错的实习，让我在步入社会之前先以学生的身份接触到社会的运行规律，接触企业工程化的计算机知识，认识了很多互联网领域的精英，和他们共事，和他们的交流，是我一生的财富；实习赚到的钱也给我爸配了一套电脑，给我妈和女朋友买了很多首饰，给我家和娘家亲戚买了很多礼物。具体怎么选择，没人知道三年后是什么样子。

 3. 语音数据集应该如何构造，怎样避免训练集和测试集泄漏？ 

 语音数据集不能只按照音频文件随机切分。若同一个说话人、车辆、录音设备或相同脚本同时出现在训练集和测试集，最终指标会明显虚高。 

 更合理的切分单位是说话人或场景组： 

 from collections import defaultdict
import random

def split_by_speaker(records, ratios=(0.8, 0.1, 0.1), seed=42):
 groups = defaultdict(list)
 for item in records:
 groups[item["speaker_id"]].append(item)

 speakers = list(groups)
 random.Random(seed).shuffle(speakers)

 n = len(speakers)
 train_end = int(n * ratios[0])
 valid_end = train_end + int(n * ratios[1])

 train_ids = speakers[:train_end]
 valid_ids = speakers[train_end:valid_end]
 test_ids = speakers[valid_end:]

 def flatten(ids):
 return [x for sid in ids for x in groups[sid]]

 return flatten(train_ids), flatten(valid_ids), flatten(test_ids)

 4. 训练语音大模型时，遇到 loss 不下降或突然 NaN，如何定位？

 长句和打断场景下的稳定性。 

 
 6. 流式 ASR 中为什么会出现 partial result 回退？如何减少？ 

 流式识别在早期只看到部分声学上下文，模型可能先输出一个局部最优结果。随着后续音频到达，新的声学证据会改变路径，因此已经输出的 token 可能被修正。 

 常见原因包括： 

 
 右上下文不足； 

 音素边界尚未确定； 

 beam search 路径发生切换； 

 端点检测提前截断； 

 语言模型对长距离上下文依赖较强； 

 chunk 之间的 cache 或位置编码拼接错误。

 8. 长期记忆系统如何区分事实记忆、偏好记忆和临时上下文？ 

 记忆不能把所有历史对话直接写入数据库，否则会造成噪声累积、隐私风险和检索污染。 

 可以将记忆划分为： 

 
 临时上下文：只在当前会话或短时间内有效； 

 情景记忆：某次具体事件和其发生时间； 

 语义记忆：用户长期稳定的事实； 

 偏好记忆：用户持续表现出的喜好； 

 任务记忆：未完成任务和待办状态。 

 
 每条记忆至少应包含内容、来源、时间、置信度、有效期和访问权限： 

 memory = {
 "content": "用户偏好夜间使用简洁回答",
 "type": "preference",
 "source": "conversation",
 "confidence": 0.86,
 "created_at": 1710000000,
 "expires_at": None,
 "sensitivity": "normal"
}
 
 写入前要判断是否具有长期价值，检索时还要考虑时间衰减、任务相关性和用户授权。对于地址、健康、财务等敏感信息，应默认不长期保存，或要求明确授权。 

 9. 跨轮对话的上下文如何压缩，同时避免丢失关键约束？ 

 上下文压缩不能简单截取最近 N 轮。需要把对话拆成事实、约束、未完成任务、工具结果和历史闲聊。

 "confirmed": ["capacity"],
 "missing": ["building", "exact_time"],
 "pending_actions": [],
 "recent_turns": []
}

 数值、时间和权限约束；

lz情况：UCL机器学习硕士 利物浦计算机本科 有过互联网算法简短实习 实习经验不算丰富 本科和硕士的毕业项目都是机器学习相关 

 非常特别的面试体验 面试官人都很好 专业细致 面试全程体验满分。

 
 

 一面（技术面）： 

 全程一小时左右 流程比较常规 面试官很有耐心 不会打断发言 而且对项目非常有热情 过程很是轻松愉悦

 主要的技术问题以项目经验展开 大部分时间是在聊项目 难度不大

 常规自我介绍 项目：以项目为中心 问了一些机器学习 NLP相关的比较基础的问题 然后又根据具体的一些项目细节 问了一些比较深入的问题 主要是有关技术细节 对做过的项目有比较深刻的理解的话还是比较好回答的 算法题：写了一道算法题 难度大概是简单到中等之间 写的比较快 没占用太多时间 提问环节：问了一些岗位和公司相关的问题 面试官介绍的时候真的很有热情哈哈 

 二面（技术面）： 

 全程也是一个小时左右 面试官职级应该是更高一些 相对比较严格 问题也比较尖锐深入一些 但是也是比较温和有耐心的 

 常规自我介绍 项目：依旧是比较以项目为中心的提问 相比一面问了一些角度更广、更高层面的东西 比如项目的实际意义 对科研项目落地的思考等等 还是比较深入的 算法题：也做了一道算法题 难度也大概是中等左右 提问环节：这个部分记得不太清楚了～ 

 HR面： 

 相对比较简短 十几二十分钟的样子 都是比较常规的问题 下面就不细说了 全程氛围轻松像是聊天 HR小姐姐好看温柔

 自我介绍 工作地点的确认 其他offer 对公司的看法 工作期待，薪资待遇 Update：
