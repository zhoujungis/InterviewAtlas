## 新易盛 嵌入式软件开发 一面面经

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-23 ｜ [原文链接](https://www.nowcoder.com/discuss/943079361354256384)

1. 用一两分钟介绍一下自己，以及和嵌入式相关的经历？

 
 先报学校/专业/求职方向，再落到嵌入式相关经历，避免流水账。

 挑 1～2 个最能说明能力的点：比如某块外设驱动、RTOS 任务划分、通信协议联调。

 每个项目用「背景—职责—难点—结果」说清，结果尽量量化，如周期、带宽、稳定性。

 最后收口到为什么投新易盛嵌入式：设备侧控制、通信、可靠性更贴近自己积累。

 
 2. 你简历里这个项目，从需求到联调你具体负责哪一段？

 
 先划清边界：需求澄清、方案、驱动、协议、应用逻辑、测试各自谁主导。

 说明自己主导的模块输入输出：接口、时序、错误码、资源占用。

 讲清楚和其他模块的依赖：谁提供时钟/中断/DMA，谁消费数据。

 联调时自己怎么定位问题：示波器/逻辑分析仪、日志、抓包、最小复现。

 最后补一句交付物：代码、文档、测试用例或量产问题闭环。

 
 3. 项目里最难排查的一次异常是什么，你怎么定位的？

 
 先描述现象：偶发复位、丢包、响应变慢、某外设偶发失败。

 缩小范围：硬件/供电、时钟配置、中断优先级、DMA/缓存一致性、协议时序。

 用证据说话：波形、寄存器、调用栈、时间戳日志，而不是猜。

 给出根因和修复：例如中断里做了过重逻辑、临界区过长、缓冲区竞态。

 说明防再发：断言、看门狗、压力测试、边界用例补齐。

 
 4. 新易盛做光模块相关产品，你对光模块/光通信嵌入式侧了解多少？

 
 光模块是光电转换单元，常见形态有光收发一体模块，面向数据中心/电信链路。

 嵌入式侧常见工作：MCU 管理、寄存器/EEPROM 配置、监控告警、固件升级、通信接口。

 业务侧常接触 I2C/MDIO 类管理口、UART 调试、GPIO 控制、温度/电压/光功率监控。

 强调自己会先从「可配置、可监控、可升级、可诊断」理解设备固件职责。

 不熟悉的细节坦诚说明，并表示可用数据手册和现有驱动框架快速上手。

 
 5. 为什么从原课题/原方向转到嵌入式软件，而不是继续深造或做原方向？

 
 动机落到工程：更喜欢把需求做成可量产、可维护的软件与系统。

 说明已具备的迁移基础：C、板级调试、协议、实时性或 Linux 经验。

 对比原方向：研究偏探索，嵌入式偏交付与稳定性，自己更匹配后者。

 对公司选择说明：光通信设备固件兼具底层驱动和产品约束，成长路径清晰。

 
 6. volatile 和 const 分别解决什么问题？能一起用吗？

 
 volatile 告诉编译器变量可能被「程序外」改变，禁止不当优化缓存。

 典型场景：硬件寄存器、中断/多上下文共享标志、DMA 可见缓冲区状态。

 const 表达只读约束，便于接口安全和放只读区，不保证物理上不可写。

 可以组合： const volatile 常用于只读状态寄存器，既防误写又防优化丢读。

 注意： volatile 不是原子，也不替代互斥；多核/中断共享仍要临界区或原子操作。

 
 7. 解释一下内存对齐，以及 #pragma pack / 属性 packed 的影响？

 
 对齐是为了 CPU 高效访问，成员按类型对齐要求插入 padding。

 结构体大小通常对齐到最大成员对齐值的整数倍。

 packed 可压缩布局、减小体积，但可能带来非对齐访问代价或特定平台异常。

 和协议/文件布局交互时，明确大小端、padding、位域规则，避免隐式依赖。

 跨编译器要以明确序列化或固定布局协议为准，不要只靠本机 sizeof 假设。

 
 8. 中断服务函数里哪些事能做，哪些不该做？

 
 能做：清中断标志、搬极少量数据、置事件/给信号量、启动下一次传输。

 不该做：printf、malloc/fre

 优点方面

 专业技能扎实：解释：在嵌入式系统相关知识领域有着较为深厚的积累，比如熟悉 C 语言（嵌入式开发中极为常用的编程语言），对其指针操作、内存管理、数据结构运用等方面都掌握得很熟练，能够运用 C 语言高效地实现各种功能模块同时，对微控制器的架构、寄存器配置以及各类外设接口的使用也有较深的理解，能快速完成硬件初始化并进行稳定的通信与控制工作。

 调试和解决问题能力强： 解释：熟练掌握多种嵌入式调试工具，像 JTAG 调试器、示波器、逻辑分析仪配合调试软件等，当系统出现问题（如程序死机、数据传输错误、硬件设备无响应等）时，能够有条不紊地通过分析日志、设置断点、查看寄存器值、监测信号波形等手段逐步定位问题根源，无论是软件逻辑漏洞还是硬件层面的异常都能尽力排查出来，并快速给出有效的解决方案，减少项目开发周期因问题排查而延长的时间成本。

 学习能力好，能快速掌握新技术： 解释：嵌入式领域技术迭代也较快，新的芯片架构、开发工具以及行业标准不断涌现，能够快速自主学习新知识，将其融入到实际项目开发中。比如当有新的低功耗微控制器推出，能迅速通过阅读官方文档、参考示例代码等方式掌握其关键特性和开发流程，运用到对功耗有严格要求的物联网设备开发项目中，使产品在性能和功耗方面保持竞争力。

 缺点方面

 有时过于追求完美，导致项目进度稍有延迟： 解释：在开发嵌入式软件时，由于深知系统稳定性和准确性的重要性，总是希望把每个功能模块、每一行代码都做到尽善尽美，会花费较多时间去反复检查、优化一些细节，比如对一些已经能正常工作的代码还会去考虑有没有更高效的算法实现、有没有更严谨的异常处理方式等。虽然最终的成果质量较高，但偶尔也会使得项目整体进度比计划稍微滞后一点，后续也意识到需要更好地平衡好质量和进度之间的关系。

 面对大规模代码重构时，初期会有些吃力： 解释：当嵌入式项目经过长时间迭代，代码量变得庞大且逻辑复杂，需要进行大规模重构（比如更换新的软件架构、整合重复功能模块等）时，在一开始可能难以迅速梳理清楚全部的代码逻辑和依赖关系，需要花费一些时间去深入分析、画架构图、整理模块间调用关系等，才能制定出合理的重构方案。不过一旦完成了前期的梳理工作，后续就能高效地推进重构工作，并且保证重构后的代码质量和性能都能得到提升。
