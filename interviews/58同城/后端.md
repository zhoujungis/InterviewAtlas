## 58同城 C++ 二面面经

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-21 ｜ [原文链接](https://www.nowcoder.com/discuss/942366837239472128)

1. 广告检索这条漏斗，每一层的耗时预算是多少？

 参考答案：

 
 预算拆分：召回 15 ms、粗排 8 ms、精排 25 ms、重排 5 ms，加上网关和序列化，端到端 p99 压在 80 ms 以内。

 请求量级：日均 3.2 亿请求，峰值 1.8 万 QPS，单次召回 3000 条、粗排留 300、精排留 30、最终出 8 条。

 超时策略：每层独立 deadline，精排超时直接退回粗排分数，实测降级触发率 0.4%，收益损失 6%。

 
 2. 倒排索引和正排索引分别存什么，为什么不能只留一种？

 参考答案：

 
 倒排职责：term 到 docId 列表，只存 docId 和基础权重用于召回，5 亿文档约 120 GB，内存放不下，按 term 哈希分片。

 正排职责：docId 到完整属性（出价、类目、质量分），用于过滤和排序，落在 RocksDB 上，随机读 p99 1.2 ms。

 分工原因：只用倒排没法按出价排序，只用正排要全表扫；靠 docId 对齐，一次请求约 3000 次正排读，批量 mget 压到 12 次 IO。

 
 3. 多路召回的结果怎么融合，重复的广告怎么去重？

 参考答案：

 
 分数归一：各路分布差异大，先做分位数归一再加权，权重来自离线 LR，每小时更新一次。

 去重策略：按 adId 去重保留最高分，同时按计划 ID 做频控，同一计划最多出 2 条，重复曝光率从 7% 降到 0.8%。

 融合代价：加权融合比简单截断 CTR 高 4.2%，但要多花 3 ms 做归一化，在 3000 条上用 SIMD 批处理压到 0.6 ms。

 
 4. CTR 模型怎么服务化，特征拼接放在哪一侧？

 参考答案：

 
 模型形态：双塔加 DIN，离线导出 ONNX，线上用 onnxruntime 推理，300 维特征单次 1.8 ms。

 特征位置：ID 类特征在服务端查 embedding 表（Redis，p99 0.8 ms），数值特征本地拼，避免把 300 维整体传给模型服务多一次 RPC。

 加载方式：模型文件 400 MB，启动 mmap 加载，热更新用双 buffer 切换，切换瞬间 QPS 掉 3%、持续 2 秒。

 
 5. 用户刚搜过的词，多久能进模型？

 参考答案：

 
 分层时效：曝光点击走 Kafka，Flink 10 秒窗口聚合成实时特征；用户画像 T+1；商品侧统计 5 分钟一次。

 存储选型：实时特征写 Redis Hash，单 key 约 200 个字段，TTL 7 天，读写 p99 分别 1.1 ms 和 0.9 ms。

 一致性坑：Flink 作业重启会丢窗口内数据，开了 30 秒 checkpoint，最多回退 30 秒，实测特征缺失率 0.05%。

 
 6. 手撕：多路有序结果归并去重，取 top-k。

 参考答案：

 
 数据结构：k 路各一个游标，小顶堆存每路当前元素，每次取堆顶，复杂度 O(N log k)，10 路各 1000 条只要 0.4 ms。

 去重方式：哈希集合记录已输出 id，命中就跳过并推进该路游标，注意要循环 pop 直到取出新值。

 边界处理：某路耗尽要及时移出堆否则死循环；k 大于总条数时直接全量排序更快，省掉堆的维护开销。

 
 7. 手撕：布隆过滤器，误判率怎么算？

 参考答案：

 
 公式：m 位、k 个哈希、插入 n 个元素，误判率约 (1 - e^(-kn/m))^k，k 取 (m/n)·ln2 时最优。

 参数实例：1 亿条广告 ID、1% 误判，算出来 m = 9.6 亿位即 114 MB，k = 7。

 实现细节：用 double hashing 从一个 64 位哈希派生 k 个位置（h1 + i·h2），比调 k 次 murmur 快 2.5 倍。

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-21 ｜ [原文链接](https://www.nowcoder.com/discuss/942366675079290880)

1. 你的系统怎么应对突增流量？

 参考答案：

 
 监控先行：QPS、延迟、饱和度指标实时看；没有监控就不知道什么时候该扩容。

 预案：限流（保核心接口）、降级（关非核心）、扩容（提前备机器）；预案要演练，不是文档里躺着。

 架构层面：无状态服务可水平扩、缓存挡读、MQ 削峰写——信息平台高峰很陡（招聘季、节假日），弹性是刚需。

 
 2. 反爬虫你了解吗？常见手段和对抗？

 参考答案：

 
 识别：IP/UA/行为指纹（鼠标轨迹、请求间隔）、设备指纹、滑块验证码、无感验证。

 对抗升级：爬虫用代理池 + 真实浏览器内核 + 分布式慢速率；防守用行为模型 + 图谱关联（同设备多账号）。

 认知：攻防是成本博弈——别追求 100% 拦截（误伤真实用户），追求「让对方成本高于收益」。

 
 3. 高并发下计数器（如帖子的浏览量）怎么设计？

 参考答案：

 
 问题：每次浏览都写 DB/Redis 单 key 热点打爆；实时性不重要但量极大。

 方案：本地累加 + 批量异步刷（每 N 秒合并一次）、分片计数（key 加随机后缀）、写 MQ 由消费端聚合。

 展示与真实的分离：展示数可以近似（用户看不出 1 的差距），落库数才要准——按业务定一致性级别。

 
 4. 短链服务怎么设计？

 参考答案：

 
 核心：长链 → 短码映射；短码 6~8 位 base62，存储 KV + 301/302 跳转。

 发号：自增 id 转 base62（有序、无冲突）；分布式发号（号段模式或雪花）；别用 hash（有碰撞且长）。

 细节：跳转用 302（可统计）还是 301（可缓存）按分析需求；短码防遍历（加随机位）、高 QPS 全走缓存。

 
 5. 图片和视频这类大文件怎么存取？

 参考答案：

 
 存储：对象存储（OSS/S3）+ CDN；元数据（大小、格式、路径）存 DB/Cache。

 上传：分片上传 + 断点续传；客户端直传对象存储（服务端只发临时凭证，省自身带宽）。

 处理：缩略图、水印、转码走异步 pipeline；原图只存一份，派生图按需生成 + 缓存。

 
 6. 搜索的排序策略？相关性怎么工程化？

 参考答案：

 
 多阶段：召回（倒排 + 向量）→ 粗排（轻量模型/规则）→ 精排（模型打分）→ 重排（业务规则、多样性）。

 相关性问题：分词不准（「纳指」不是「纳 + 指」）、同义词、意图识别（找保姆 vs 找工作）；用 query 改写 + 行业词库补。

 评估：离线看 NDCG、在线看点击率/转化率；badcase 集驱动迭代，不能凭感觉调权重。

 
 7. 推荐系统召回路 C++ 能做什么？

 参考答案：

 
 召回层：多路召回（协同、向量、热门、运营）+ 合并去重，毫秒级完成——纯计算密集，C++/性能敏感语言的主场。

 工程点：向量检索引擎（HNSW/IVFPQ）、特征快照复用、批量打分 SIMD。

 隔离：线上模型服务（TF Serving/Triton）和召回服务的职责边界，别什么都往 C++ 里堆。

 
 8. 消息推送（push）系统怎么设计？

 参考答案：
