 首先保存现场信息，重点查看： dmesg 

 关注：

 - Call Trace
- PC
- LR
- RIP
- Oops
- BUG
- Unable to handle...

 常见原因包括：

 - 空指针解引用；
- 野指针；
- 越界访问；
- use-after-free；
- double free；
- 竞态条件；
- 中断处理错误；
- DMA 内存访问异常。

 
 如果能够稳定复现，可以结合：日志 + gdb /addr2line + ftrace + KASAN + lockdep进一步定位。

 2. PHY 驱动中是否涉及中断机制？如果发生链路状态变化，驱动是如何感知并向上层通知的？

 PHY 驱动可以使用中断，也可以采用轮询方式检测 PHY 的链路状态，具体取决于硬件是否提供相应的中断能力以及驱动设计。

 例如网线插拔导致 Link 状态发生变化：

 PHY 检测到 Link 状态变化
 ↓
PHY 产生中断
 ↓
SoC GPIO/IRQ 收到中断
 ↓
PHY 驱动处理中断
 ↓
读取 PHY 状态寄存器
 ↓
判断 Link Up / Link Down
 ↓
通知网络子系统
 ↓
MAC/网络协议栈更新链路状态

 
 在 Linux 网络驱动中，PHY 与 MAC 通常通过 phylib 协作。

 如果没有使用 PHY 中断，也可以通过周期性读取 PHY 状态寄存器来检测链路状态变化。

 所以面试时可以强调：PHY 链路状态检测既可以采用中断，也可以采用轮询，具体取决于 PHY 芯片和驱动实现。

 3. Linux 驱动中的 probe () 函数主要负责什么？设备和驱动是如何完成匹配的？

 获取设备资源；

 分配 DMA / 内存资源；

 注册字符设备或其他子系统接口；

 保存设备私有数据。

 
 设备和驱动的匹配通常由 Linux 总线框架完成。

 设备节点
 ↓
compatible
 ↓
总线匹配
 ↓
driver_match_device()
 ↓

 ↓
调用 probe()

 
 不同总线的匹配规则有所不同，例如 Platform、I2C、SPI 等。

 4. Linux 中设备树（Device Tree）主要解决什么问题？驱动为什么需要读取设备树？

 Device Tree 主要用于描述硬件信息，把硬件配置从驱动代码中分离出来。

 例如：

 硬件信息
├── GPIO
├── IRQ
├── I2C 地址
├── SPI 配置
├── 时钟
├── 电源
└── compatible

 
 驱动本身不需要把这些硬件参数全部硬编码，而是通过 Device Tree 获取。

 同一套驱动代码

 5. Linux 驱动中 interrupt 和 threaded interrupt 有什么区别？

 普通中断处理主要由硬中断上下文执行，要求处理函数尽快完成。而 threaded interrupt 会把主要处理工作放到内核线程上下文中执行。

 可以理解为：

 普通 IRQ：

 硬件
 ↓
IRQ Handler
 ↓
快速处理

 
 而 threaded IRQ：

 硬件
 ↓
Primary Handler
 ↓
唤醒 IRQ Thread
 ↓
线程上下文处理

 
 这样可以把一些需要睡眠或者执行时间较长的工作放到线程中处理。

 典型接口是： request_threaded_irq(); 

 6. 什么是 DMA？驱动中使用 DMA 时需要注意哪些问题？

 DMA 是 Direct Memory Access，即直接内存访问。

 传统方式：外设 → CPU → 内存

 DMA：

 外设 ─────────→ 内存
 DMA

 
 CPU 主要负责配置 DMA，传输完成后通过中断等方式获得通知。

 优点是：

 
 降低 CPU 搬运数据的负担；

 提高大量数据传输效率；

 减少 CPU 参与次数。

 
 驱动使用 DMA 时需要重点考虑：

 
 DMA 地址；

 Cache 一致性；

 DMA buffer 生命周期；

 内存对齐；

 DMA 映射与解除映射；

 设备与 CPU 对 buffer 的访问同步。

 
 尤其在 Cache 开启的系统中，CPU Cache 和 DMA 看到的数据可能不一致，这是驱动开发中非常重要的问题。

 7. Linux 中 copy_to_user () 和 copy_from_user () 为什么不能直接用 memcpy () 替代？

 因为用户空间地址属于不可信的用户地址空间，内核不能简单地把它当作普通内核地址访问。

 例如：

 用户空间
 ↓
copy_from_user()
 ↓
内核空间

 
 以及：

 内核空间
 ↓
copy_to_user()
 ↓
用户空间

 
 这些接口会进行必要的用户地址访问检查和异常处理。

 如果驱动直接：

 memcpy(kernel_buf, user_buf, size);

 
 可能导致非法地址访问，严重时甚至触发 Kernel Oops。

 因此驱动与用户空间交换数据时，通常应该使用：

 
 copy_to_user() 

 copy_from_user() 

 
 而不是直接使用 memcpy ()。

1. Linux 启动过程中，BootLoader（U-Boot）主要负责哪些工作？

 U-Boot 可以理解为 Linux 内核启动之前的一段引导程序，主要负责硬件初始化、加载内核、准备启动参数以及跳转到内核执行。

 典型启动流程可以概括为：

 上电
 ↓
BootROM
 ↓
加载 U-Boot
 ↓
初始化 DDR、时钟、串口等硬件
 ↓
初始化存储设备
 ↓
加载 Linux Kernel / Device Tree
 ↓
设置 bootargs 等启动参数
 ↓
跳转到 Kernel
 ↓
Linux 内核启动

 
 在嵌入式 Linux 中，U-Boot 还可以负责网络启动、固件升级、启动菜单以及内核和设备树的选择等工作。

 2. 什么是原子操作？它解决了什么问题？Linux 中常见的原子操作有哪些？

 原子操作是指一个操作在执行过程中不会被其他 CPU 或线程打断，外界只能看到操作执行前或者执行后的状态，不能看到中间状态。

 例如多个 CPU 同时执行：

 counter++;

 
 实际上可以拆成 “读 → 修改 → 写” 三个步骤，多核情况下可能发生数据竞争。

 如果使用原子操作：

 atomic_inc(&counter);

 
 就可以保证自增操作的原子性。

 Linux 中常见的原子操作包括：

 
 atomic_read() 

 atomic_set() 

 atomic_inc() 

 atomic_dec() 

 atomic_add() 

 atomic_sub() 

 atomic_cmpxchg() 

 
 不过需要注意，原子操作主要适合保护简单变量或者简单状态更新。如果需要保护一组复杂操作，通常还是需要使用锁。

 3. 在单核 CPU 上，如果当前正在执行一个低优先级任务，此时高优先级实时任务进入就绪态，CPU 会如何进行调度？

 如果系统采用可抢占式调度，那么高优先级任务进入就绪态后，可以抢占当前正在运行的低优先级任务。

 例如：

 低优先级任务运行
 ↓
高优先级任务就绪
 ↓
触发调度
 ↓
保存低优先级任务上下文
 ↓
切换到高优先级任务

 
 等高优先级任务阻塞、挂起或者主动让出 CPU 后，低优先级任务才有机会继续运行。

 需要注意的是，如果当前处于禁止抢占、关中断或者某些不可抢占的临界区，高优先级任务并不能立即抢占，而要等到可以进行调度的时机。

 4. Tasklet 执行过程中如果需要访问共享数据，应该如何保证临界区安全？为什么不能简单使用互斥锁？

 Tasklet 属于软中断上下文，不能睡眠，因此不能使用可能导致睡眠的互斥锁。

 如果 Tasklet 访问的数据同时可能被其他上下文修改，可以根据具体场景使用：

 自旋锁
 ↓
spin_lock()
 ↓
访问共享资源
 ↓
spin_unlock()

 
 如果共享数据还会被硬中断访问，通常还需要考虑中断上下文并发问题，例如使用：

 
 spin_lock_irqsave() 

 spin_unlock_irqrestore() 

 
 核心原因是：Tasklet 运行在原子上下文，不能睡眠，而 mutex 获取失败时可能让当前执行实体睡眠，因此不适合在 Tasklet 中使用。

 5. Linux 中的互斥锁主要解决什么问题？它与自旋锁相比有什么区别，分别适用于什么场景？

 互斥锁和自旋锁都是为了保护共享资源，避免多个执行流同时访问导致数据竞争。最大的区别在于获取不到锁时的处理方式。

 互斥锁： 

 获取锁
 ↓
成功 → 执行临界区
 ↓
失败
 ↓
当前任务睡眠
 ↓
等待锁释放

 
 自旋锁： 

 获取锁
 ↓
成功 → 执行临界区
 ↓
失败
 ↓
一直循环等待

 
 因此：

 
 mutex：适合进程上下文，临界区较长、允许睡眠的场景。

 spinlock：适合临界区很短，或者不能睡眠的上下文，例如中断 / 软中断相关场景。

 
 简单记忆就是：能睡眠的场景优先考虑 mutex，不能睡眠的场景考虑 spinlock。

## 地平线嵌入式软件开发二面 面经（Linux内核深度考察）

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-08-04 ｜ [原文链接](https://www.nowcoder.com/discuss/914112674445656064)

1. page fault 发生后，Linux 从进入异常到把物理页填好并返回用户态，中间关键路径是什么？

 
 用户态访问未映射或权限不匹配地址，触发架构异常，进入内核 page fault 处理入口。

 内核先区分内核态/用户态、指令/数据访问，并取出 fault 地址与错误原因。

 查 VMA：地址不在任何 VMA → 非法访问，走 SIGSEGV；在 VMA 内再看读/写/执行权限是否匹配。

 合法缺页则走 demand paging：分配物理页、必要时读文件/swap、建立页表项，并处理 COW 等特殊情况。

 页表更新后做必要的 TLB 同步，返回用户态，CPU 重试那条访存指令。

 若是写只读私有页，通常走 COW：复制一页再改权限，而不是直接改原物理页。

 
 2. 为什么内核里不能随便在持有自旋锁时睡眠？真正危险点在哪？

 
 自旋锁假设临界区很短，持锁者通过忙等占用 CPU，不主动让出。

 若持锁线程睡眠，同核或其他核上等待同一把锁的线程会一直空转，可能形成死锁或长时间饥饿。

 中断/软中断上下文本身就不能睡眠；若中断路径也要拿同把锁，睡眠会把系统直接卡死。

 需要睡眠的互斥应使用 mutex/rwsem；短临界区、禁止抢占/关中断场景才用 spinlock。

 工程上要检查调用链：持锁期间禁止 copy_from_user、kmalloc(GFP_KERNEL)、阻塞 IO 这类可能调度的路径。

 
 3. mmap 一段文件后，第一次读和第一次写，内核行为有什么本质差别？

 
 第一次读通常触发读缺页：按 VMA 找到文件映射，把文件页读入 page cache，再映射到进程地址空间。

 只读共享映射下，多个进程可映射到同一 page cache 页，省内存。

 第一次写私有映射（MAP_PRIVATE）常触发 COW：先有只读映射，写时复制出匿名页，后续写不再污染文件页。

 共享可写映射（MAP_SHARED）写的是 page cache，脏页之后由写回路径落到文件。

 所以“读”更偏共享与缓存命中，“写”还要考虑 COW、脏页、写回和一致性语义。

 
 4. 用户态 free 后继续写，为什么有时立刻崩，有时过很久才崩，甚至表现为别的模块异常？

 
 free 通常只是把块还给分配器，不一定立刻归还给内核或取消页映射，原地址短期内仍可能可写。

 若这块很快被新分配复用，越界写会破坏别的对象元数据，故障点远离真正的 free 点。

 若写入落在尚未回收且仍属本进程的页内，可能暂时不触发缺页，形成“延迟爆炸”。

 一旦分配器校验、下一次 malloc/free、或附近对象被使用，才会以崩溃、断言或数据错乱暴露。

1. 自我介绍，重点说项目经验和用到的技术栈

 2. Linux 内核态和用户态的区别是什么？系统调用的流程说一下

 
 用户态权限受限，不能直接访问内核数据结构、页表和绝大多数硬件寄存器；内核态拥有完整特权，可操作全部内存与外设。

 CPU 用特权级隔离：ARM64 上进程跑在 EL0，内核跑在 EL1；切换必须走异常路径，用户代码不能随意跳进内核。

 系统调用流程：用户程序调库函数（如 read ）→ 把调用号和参数放进约定寄存器 → 执行 svc 陷入内核 → 内核根据调用号查 sys_call_table。

 内核先做权限和参数校验，再执行真正逻辑，最后恢复用户上下文返回；失败通常返回负错误码，glibc 转成 errno 。

 本质是受控的提权入口：既提供文件、进程、网络等能力，又保证隔离，不让应用随意破坏内核。

 
 3. 进程间通信有哪些方式？管道、消息队列、共享内存分别适合什么场景？

 
 常见方式有：匿名/命名管道、消息队列、共享内存、信号量、信号、Unix/TCP Socket，以及 eventfd 等。

 管道是字节流，实现简单，适合父子进程或本地单向数据流；没有明显消息边界，大吞吐时拷贝开销明显。

 消息队列按消息收发，可带类型或优先级，适合控制命令、状态事件；不适合连续大块图像或点云。

 共享内存几乎零拷贝，吞吐最高，适合摄像头帧、模型输入输出等高频大缓冲；必须自己做同步、生命周期和版本兼容。

 实践上常「共享内存传数据 + 消息队列/信号量做通知」，跨机通信再上 Socket。

 
 4. 虚拟内存是什么？页表的作用是什么？TLB 是干什么的？

 
 虚拟内存让每个进程拥有独立的线性地址空间，由 MMU 映射到物理页，支持进程隔离、按需分配，也可配合换页扩展可用内存。

 页表记录虚拟页到物理页的映射，以及可读/可写/可执行、用户/内核、是否可缓存等权限；访问非法页会触发缺页或权限异常。

 缺页时内核决定：分配物理页、从文件读入，还是判定段错误杀掉进程。

 TLB 是页表项的硬件高速缓存，命中后不用每次访存都走多级页表，否则地址翻译会非常慢。

 修改页表、切换进程地址空间后要失效相关 TLB；多核还要做 TLB shootdown，保证各核对同一映射认识一致。

 
 5. malloc 底层是如何实现的？和 mmap 有什么关系？

 
 malloc 一般不直接找内核要每一小块，而是用户态分配器（如 glibc ptmalloc）先向系统拿大片内存，再在进程内切分、合并、按 size class 管理。

 小块通常通过 brk / sbrk 扩展堆顶；超过阈值的大块，分配器更倾向直接 mmap 匿名映射。

 mmap 出来的大块可以整段 munmap 还给内核，有利于控制长期碎片；小块则更多留在用户态复用，不一定立刻回系统。

 多线程下会有多个 arena 降低锁竞争，但嵌入式里频繁 malloc/free 仍可能抖动，关键路径常用内存池或预分配缓冲。

 
 6. Linux 设备驱动模型说一下，字符设备驱动的注册流程是什么？

 
 Linux 驱动模型以总线-设备-驱动为核心：设备挂到总线上，驱动注册后按匹配规则绑定，成功则调用 probe ，卸载走 remove 。

 底层靠 kobject / kset 管理对象生命周期， device / class 把设备和属性导出到 sysfs，方便用户态查看和配置。

 字符设备面向字节流访问，核心是填充 file_operations ，提供 open/read/write/ioctl/mmap/poll 等回调。

 注册流程通常是：实现 fops → alloc_chrdev_region 申请设备号 → cdev_ / → + 生成 节点。

# 地平线一面经历
 # 历时大概四十多分钟：
 
 
 1. 自我介绍
 2. 问项目，项目的意义是什么？你为什么这么做？有什么创新点？SDRAM存储器的乒乓操作是如何切换BANK空间的？选择外设的参数是基于什么考虑的？其中有一个协议是用状态机写的，定义了几个状态，状态名字叫什么，状态之间如何跳转，以及跳转之后做什么。你认为项目的难点是什么？如何解决的。
 3. 然后问了我参加了的两个比赛，FPGA创新设计竞赛和电子设计竞赛，其中比赛的一些细节，在比赛中负责哪个方面，遇到过什么问题，以及如何解决的
 4. 然后就开始问非技术问题了，你以后的职业规划，以后想学什么方向
 5. 你想留在哪个城市？
 6. 你有什么问题想问的？
 
 ---
 
 # 总结：主要以问项目和比赛为主，问的很深。

## 地平线芯片设计一面面经

来源：牛客网 ｜ 类型：面经 ｜ 发布：2020-08-14 ｜ [原文链接](https://www.nowcoder.com/discuss/353156758157860864)

约的今天一面视频面试，提前十分钟准备好，等待面试官。 

 
 

 面试官连上来后，让我开始自我介绍。我一开始看不到他人，以为网络或者腾讯会议出了问题，就提醒一下：“我这边好像有点问题，看不到您。” 

 
 

 面试官说：“不用看到我，公司没要求我一定要开视频。” 

 
 

 视频面试也经历了十来次，我开视频而面试官不开的第一次见到！我自己开视频看自己，是不是我也可以不用开的呀。 

 
 

 说重点，面经： 

 基本是基于项目来问问题。每介绍一个项目，他会提问直到他懂了这个项目是干嘛的。提的问题要么是项目里面的，要么针对项目技术扩展的一系列问题。 

 比如：IIC协议，先是用来干嘛，然后详细介绍一下IIC协议，然后你代码的思路是怎样的。 

 
 

 最后是描述一下你代码是怎么写的，我就是卡死在了这里，问我IIC协议定义了几个状态机，每个状态机的名字是什么（？？我懵圈了，就说S0,S1,S2），每个状态之间是怎么跳转的，每个状态跳转完之后具体干什么。 

 
 

 这个项目已经半年多了，复习的时候只复习了基本的思路和流程。代码之间怎样跳转早就忘了，而且也记不清楚每个状态是干嘛的了，跳转完之后是干嘛的。反正是IIC对一款芯片进行读写，只记得先初始化，再配置寄存器，最后读数据。具体的怎么初始化，配置哪些寄存器真的记不得了，也没有去复习。 

 
 

 最后还问了一个项目，问我你这个里面用的是什么接口，我说SPI,UART。 

 他说这是接口吗？然后我又懵圈了，原来这些都不是接口吗。 

 然后我问什么是接口，他说是总线接口呀，用了哪些总线。好吧。 

 总体感觉一般，应该过不了，问到最底层有点要口述代码的时候就罩不住了，感觉面试官不满意，可能复习项目的时候代码流程还要再背一背，芯片手册再看一遍。

 1.手写链表成环问题判断（快慢指针）
 

 
 2.c++11新特性的提问
 

 
 3.项目实现细节，多线程方面如何处理
 

 
 4.对opencv的了解程度，视觉方面的
 

 
 5.数据库事务
 

 
 6.linux的了解
 

 
 

 

 
 

 

 
 地平线校招（一面两次）：
 

 
 1.手写一个大数如何找到最大的3位数约数
 

 
 2.手写二维数组翻转90度
 

 
 3.设计模式使用经历
 

 
 4.介绍一下比赛用过的xgboost，和数据处理方面的方法，以及建模思路
 

 
 5.实习经历遇到的最大困难
 

 
 6.多进程，多线程联调遇到的困难
 

 
 7.做过的底层有关的问题
 

 
 8.opencv的了解，讲清楚用opencv做过的项目
