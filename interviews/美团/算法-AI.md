## 美团AI-Agent一面70分钟只问“怎么证明它行”，MiniMax大模型算法岗面试考什么

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-22 ｜ [原文链接](https://www.nowcoder.com/discuss/942861143775666176)

一、两场面试，两种“较真”

 最近听到两场大模型方向的面试经历，风格差别很大，但内核出奇一致：面试官都不满足于“我做过什么”，而是反复追问“你凭什么说它行”。

 第一场是美团AI-Agent开发岗，一面整整70分钟，几乎全程围绕一个主题打转——怎么证明这个Agent是有效的。不是问架构多花哨，也不是问用了哪个模型，而是把“证明”两个字拆开揉碎，一层层往下压。

 第二场是MiniMax的大模型算法岗，方向是后训练、SFT和RL。这家独角兽的面试节奏更偏技术纵深，问题沿着训练范式往下走，SFT的数据怎么构造、RL的奖励信号怎么设计、后训练阶段怎么判断模型真的变好了，问得很细。

 两场面试放在一起看，其实是当下大模型招聘的一个缩影：会调API、能跑通demo的人不少，但能说清楚“效果从哪来、怎么被验证”的人，才是面试官愿意花70分钟去聊的对象。

 二、美团AI-Agent岗：70分钟都在拆“证明”这件事

 1. 不是问“能不能跑”，而是问“凭什么信”

 Agent类项目最容易陷入的误区，是演示时很热闹，一问效果就含糊。面试官的追问路径大致是这样的：先让你讲一个做过的Agent项目，然后立刻转向“它的成功率是多少、这个成功率怎么统计的、统计口径是谁定的、有没有人工复核、复核的一致性怎么保证”。

 这一串问题下来，靠背项目介绍是撑不住的。它考察的其实是一种工程思维：Agent的输出天然带有不确定性，那么评估就必须是可复现、可追溯的。面试官关心的不是“它有时候挺好用”，而是“在什么条件下、多大比例、用什么标准判定它好用”。

 2. 评测集从哪来，比模型选哪个更致命

 70分钟里有一段追问特别典型：你这个Agent的评测集是怎么来的？是公开数据集，还是自己构造的？自己构造的话，样本怎么采样、标注规则是什么、有没有覆盖长尾场景、评测集和训练数据有没有重叠。

 这几个问题连在一起，指向的是评估的干净程度。很多Agent项目在演示阶段表现不错，一到规模化就露怯，根源往往在评测集本身就有偏。面试官显然见过太多“评测集即训练集”的案例，所以在这一环问得格外紧。

 3. “证明”的落脚点：可观测与可归因

 聊到后半段，话题转向了线上表现。Agent上线之后，怎么知道它哪一步出了问题？是规划错了、工具调用错了，还是最终回答的表述出了问题？这就要求项目具备可观测性——每一步的中间结果能留痕，失败案例能归因。

 面试官对“归因”的执着，其实是在筛选一种习惯：做Agent不能只做输入端和输出端，中间的决策链路要有日志、有指标、有回放能力。能把这套讲清楚的人，说明他真的在线上环境里磨过，而不是在 notebook 里跑通就收工。

 三、MiniMax算法岗：后训练、SFT与RL的纵深追问 hao.1905cq.com.cn 

 1. SFT不是“喂数据”，而是设计数据分布 

 MiniMax这场面试在SFT环节问得很实。面试官不太关心“用了多少条数据”，更关心“数据从哪来、怎么配比、质量怎么筛”。比如指令数据的多样性怎么保证、拒答样本怎么处理、多轮对话里上下文怎么组织、训练时loss masking的边界设在哪。

 这些问题背后是一个判断：SFT的效果上限，很大程度上由数据分布决定。能把这些细节讲明白，说明候选人真正参与过数据构建，而不是拿现成脚本跑了一遍。

 2. RL环节：奖励信号的设计比算法选择更见功力

 到了RL部分，追问重心落在奖励建模上。奖励信号怎么定义、稀疏奖励怎么缓解、奖励黑客现象怎么发现和抑制、KL约束加在哪个位置、离线评估和在线评估怎么配合。

 这类问题的特点是，没有标准答案，但能听出候选人有没有踩过坑。比如奖励黑客，没实际调过的人往往只会说“加个惩罚项”，而真正做过的人会讲具体现象：模型学会了在某个维度上刷分，导致其他维度悄悄退化，于是需要在评估体系里加入对抗性检查。

 3. 后训练的“证明”逻辑：消融与对照

 和美团那场呼应的是，MiniMax这边同样在意“怎么证明训练有效”。面试官会问：你怎么知道效果提升来自RL而不是SFT数据的变化？有没有做消融？基线怎么设？评估指标是单一指标还是多维度的？

 这其实是大模型后训练最容易被忽视的部分。训练跑起来不难，难的是把增益归因清楚。能设计对照实验、能解释每个阶段的边际收益，才是面试官眼里“靠谱”的信号。

 四、两场面试的共同底色：可验证性

 把两场面试并排看，会发现一个共同的关键词——可验证性。

 美团AI-Agent岗把它放在评估体系上：评测集干不干净、统计口径稳不稳、失败能不能归因。MiniMax算法岗把它放在训练范式上：数据分布怎么设计、奖励信号怎么定义、增益怎么归因。形式不同，本质一样：面试官都在判断候选人是否具备“用证据说话”的习惯。

 这也解释了一个现象：为什么有些候选人项目列表很长，面试却聊不深。因为项目数量不等于可验证性，能讲清楚一个项目的评估闭环，往往比罗列五个项目更有说服力。

 五、给准备大模型面试的读者几点观察

 第一，准备项目时，把“效果怎么证明”当成必答题。成功率、评测集来源、标注规则、失败归因，这四个问题提前想清楚，比堆技术名词管用。

 第二，Agent方向要重视可观测性。中间步骤留痕、失败案例回放、链路归因，这些工程细节在面试里的权重，比想象中高。

 第三，后训练方向要把数据讲透。SFT的数据配比、质量筛选、masking边界，RL的奖励设计、奖励黑客识别、消融对照，都是能拉开差距的地方。

 第四，别回避“不知道”。面试官追问70分钟，不是要听完美答案，而是看思路是否诚实、边界是否清楚。承认某个环节没做过，然后讲清楚会怎么设计验证方案，往往比硬编一个答案更得分。

 两场面试，一场偏工程验证，一场偏训练纵深，但都在问同一个问题：你说的“行”，证据在哪。想清楚这件事，大模型方向的面试准备就有了主线。

 不少朋友从传统前后端或数据岗往 AI 全栈、Agent 方向转，简历上会写"做过智能客服""搞过 LLM 应用"，真到面试时，面试官往深了一问，多轮对话怎么设计、幻觉怎么控、工具调用怎么落地，很容易卡壳。下面是一份美团 AI Agent 开发一面（智能客服方向，2026 年 2 月）的真实题目和参考答案思路，你可以先在心里答一遍，再对照看看自己差在哪一块。

 第一题 智能客服的多轮对话怎么设计

 面试官问：假设你需要开发美团智能客服 Agent，如何设计多轮对话流程？

 多轮对话要解决的是"用户说了上句，系统还能接住下句"。用户说"那改成明天""再帮我加一份"时，如果系统不知道当前在哪个环节、已经有哪些信息，就会答非所问。设计时可以抓住几条线。

 
 对话状态：当前处在哪个业务环节、已经填了哪些槽位（时间、门店、商品等），用结构化状态或状态机维护。

 每轮解析：对用户输入做意图识别和实体抽取，和当前状态拼在一起。

 决策与动作：根据"状态 + 本轮意图"决定是继续追问、调用接口、还是转人工，再生成回复。

 
 把"状态 → 解析 → 决策 → 回复"这条链路想清楚，再考虑超时、用户打断、多轮澄清等边界，就能讲出一套完整方案。

 追问一：你会使用哪些对话状态跟踪方法？

 常见有三种思路。一是基于槽位的状态机，每个意图对应一组必填槽，槽填满再执行动作，适合流程固定的场景。二是基于 DST （Dialogue State Tracking）的更新，用规则或小模型根据上一轮状态和本轮用户话术做状态更新。三是把多轮当成序列交给 LLM ，不显式维护槽位，靠上下文做"隐式"状态跟踪。实际项目里可以混用，例如关键槽用显式状态机保证可控，其余交给模型。

 追问二：如何处理用户意图模糊的情况？

 先对意图做置信度判断，置信度低时不要强行选一个意图执行，而是主动澄清。澄清方式可以是：给出几个最可能的意图让用户选、针对缺的关键信息单独追问、或用一句带选项的确认（例如"您是想查询订单，还是想申请退款？"）。可以单独做一个"澄清"子流程，在意图不清时一律走澄清，避免误触发下单、退款等敏感操作。

 第二题 用 LLM 做智能助手时遇到过哪些幻觉

 面试官问：描述一次使用 LLM 开发智能助手的经历，遇到过哪些幻觉问题？

 幻觉是面试高频题，最好提前准备一两个具体例子，按类型说清楚。

 
 无中生有：用户问"上周订单有没有优惠"，模型编造了一个不存在的活动或规则。

 张冠李戴：把 A 产品的价格、规则套到 B 产品上，或者把别的业务线的政策当成当前业务的。

 过度肯定：对不确定的问题也给出非常肯定的结论，用户信以为真后才发现是错的。

 
 应对思路可以分几层说：从数据源上限制模型只能基于检索到的文档或调用 API 的结果来答；对关键结论做二次校验或要求引用来源；在系统提示里明确写"不确定就说不知道，不要猜测"。有真实项目经历的话，可以顺带说一句你们当时是怎么发现、怎么修的就更有说服力。

 第三题 Agent 的规划能力与多任务协同

 面试官问：解释 AI Agent 的规划能力，如何实现多任务协同（如点餐、支付、售后）？

 规划能力指的是 Agent 能把一个复杂目标拆成多个子目标、排好顺序或依赖关系，再一步步执行。点餐、支付、售后就是一条链路上的多步，有先后和依赖：先点餐再支付，售后又依赖已有订单。

 实现上可以有两种说法。一是显式规划：用单独的规划模块（ Planner ）根据用户目标生成步骤列表，执行模块按步骤依次调工具。二是把规划交给主控 LLM ，每轮由模型决定"当前该做哪一步、调用哪个工具"，用 ReAct、LangGraph 等范式都能实现。多任务协同时要讲清楚三件事：步骤之间的数据怎么传（例如订单号从点餐传到支付再传到售后）、某一步失败时是重试还是降级、用户中途改主意时如何重新规划，这样才显得你真正做过或认真想过。

 第四题 Agent 工具调用的技术方案

 面试官问：在设计 Agent 的工具调用能力时，你的技术方案是什么？

 工具调用可以拆成三块来讲，逻辑清晰又不容易漏。

 
 工具描述：把每个工具的名称、参数、用途用 JSON Schema 或 OpenAPI 描述出来，和 LLM 的 function calling 格式对齐，让模型知道有哪些工具、该怎么选。

 解析与校验：用模型自带的 function calling 输出拿到"想调哪个工具、参数是什么"，再自己做一层校验（必填、类型、范围），避免脏参数直接打到业务接口。

 执行与治理：真实调用下游 API ，把结果塞回上下文。执行层要做超时、重试、熔断，对下单、支付等敏感工具可以做权限控制或二次确认。

 
 追问一：如何选择合适的工具 API？

 从"和当前意图是否匹配、参数能否从对话里补齐、当前是否有权限调用"几个维度筛。工具很多时，可以先做意图或语义检索，只把 Top-K 个相关工具暴露给当轮，减少干扰和 token 消耗。业务上要区分核心流程工具（下单、支付）和辅助工具（查门店、查天气），优先保证核心工具的稳定和可控。

 追问二：会使用哪些函数调用框架？

 可以分几类说：云厂商的 Agent 平台（如阿里百炼、腾讯混元助手）、开源编排如 LangChain 、 LangGraph 的 tool 能力、以及直接用 OpenAI 或国内大模型的 function calling API 自建。选型时看团队技术栈、要不要多模型切换、以及对编排和可观测性的要求。如果已有统一网关或 BFF ，可以在这一层做 tool 的注册与路由，再对接不同 LLM 的 function calling 格式，这样答会显得你有架构视角。

 第五题 通过用户反馈优化 Agent 的经历

 面试官问：分享一次通过用户反馈优化 Agent 能力的经历，关键改进是什么？

 这道题考的是你有没有闭环思维，最好用真实项目来答。可以按"现象 → 归因 → 动作 → 效果"来讲。

 例如：上线后发现某类问题用户常问但回答不准，通过收集 badcase 发现是意图被误判或检索不到对应文档。改进动作包括：补充、改写该意图下的 FAQ ，调整检索策略（关键词、向量、混合）或文档切分方式，在 prompt 里加该场景的 few-shot ，对高频问题单独做规则兜底。关键是要强调反馈闭环：从工单、日志、标注里筛出问题样本，归因到"意图、检索、生成、工具"中的某一环，再针对性迭代，用 A/B 或离线评估验证，而不是凭感觉改。

 小结

 五道题分别扣住多轮对话、幻觉控制、规划与多任务、工具调用、反馈优化，都是 Agent 和智能客服场景里实实在在会碰到的问题。想转 AI 全栈的朋友，可以拿这份题当自测：先不看答案在心里答一遍，再看自己哪一块说不清，针对性补一补理论和项目经历。祝大家面试顺利，早日拿到心仪 offer。

## 校招美团北京工作第7个月，经验分享

来源：牛客网 ｜ 类型：面经 ｜ 发布：2023-09-14 ｜ [原文链接](https://www.nowcoder.com/discuss/531847284577832960)

23年1月从北航硕士毕业，23年2月加入美团，到今天下班就满7个月了，如实分享一下这段经历。 

 1️⃣秋招 

 22年秋招正式批开始的时候进行的投递，去年是先投先笔试，投的早可以参加的笔试轮次多，但最多参加x次(具体忘了)。秋招我投的各家公司基本都是算法岗，美团的笔试相比来说，比hulu之类的简单，比英特尔之类的考察内容少（好多硬件型号题，做不了一点），比运营商国企的难（简单得令人发指，但只能通过80%，原题leetcode原答案都只能通过80%，至今想不通），有一些选择题和4个大题，我当时应该是ac了两道整＋剩下两道60%-70%的样子，具体要做出来多少不清楚。每次笔试难度不太平均，有的明显感觉更难一些，因为第一次就显示的应该是过了，所以我只做了两次笔试就懒得再参加了。后来过了好久(11月)才有人捞我面试，可能是因为我的技术背景跟大多数组不太匹配吧。一共三轮，两轮同事一轮leader，都考手写代码了，但都不是成品题，感觉题目是面试官个人爱好，我记得一道题是手写一个卷积过程，还有一道题是把一组数随机排列，后面还问了你怎么证明这是随机的，类似概率题吧，其他的就是聊聊项目，整体来说代码难度不大（应该算不了medium），比微软（考了topk、前缀树、动态规划等）、华为（换零钱）之流都简单，当然也可能有运气成分。最后一面当天就约了hr面，当天晚上聊完没过多久就下offer了。最终选择来美团主要是因为这个岗位比较有趣，是之前没做过的推理引擎研发，本着学海无涯的态度来进修了。 

 2️⃣工作环境氛围 

 之前在微软实习过（但离谱的是一个hc都没有，aa strong recommend硬是泡了3个月不给offer），别的公司不了解，美团与之相比的话，技术上更开放，应该不会干半年学到的都是一些内部的平台和流程。其他员工福利方面就被吊打了，只有开水，喝喝更健康，最近中秋节礼盒看着着实不错，别的也不指望了，给钱就行。工作时间官方的是早10晚7，我组是早9:30晚8:00，因为是大后方，不直接对接业务，所以我们组相对轻松愉快，不oncall，无紧急工作，下班从来不带电脑，自由快乐～有事的话只要打卡9小时就可以平稳撤退(所以我经常有事)。基研部门男的比较多，女生比较少，氛围还可以吧，互相帮助肯定没得说的。 

 3️⃣岗位 

 从一个py选手转型做cpp，甚至还要写汇编，上难度肯定是上了，不过项目循序渐进，目前适应的还是比较好，收获满满。在5个月的时候系统会推送转正自评，我组转正十分丝滑，没有答辩，我自己写了个小作文提交，然后两级领导通过一下就转正了。期待大家秋招投递，未来做同事～ 

 最后，礼品店的公仔周边真的很可爱，每次抽奖怎么就不能多我一个！

 int curWidth = j-k+ 1 ; 
 curHeight = Math.min(curHeight, dp[i][k]) ;
