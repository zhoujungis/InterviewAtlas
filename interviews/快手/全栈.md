## 快手可灵 AI全栈开发 一面

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-31 ｜ [原文链接](https://www.nowcoder.com/discuss/945980063550386176)

一、自我介绍 

 二、介绍一下你项目中 RAG 的完整链路。 

 三、Rerank 为什么通常能提升 RAG 效果？Cross-Encoder 和 Bi-Encoder 的本质区别是什么？ 

 Embedding 检索常用的是 Bi-Encoder。Query 和 Document 分别经过 Encoder 得到向量，然后计算余弦相似度或者内积。最大的优势是文档向量可以提前计算，在线只需要计算 Query Embedding，再通过 ANN 索引完成搜索，因此能够在百万甚至亿级语料上做低延迟召回。 

 它的问题也来自这种结构：Query 和 Document 在编码阶段没有发生 Token 级交互，模型只能把两段文本压缩到固定维度向量中。很多细粒度信息，例如否定关系、条件约束、数字差异或者业务缩写，很容易在向量压缩过程中损失。 

 Cross-Encoder 的输入更接近： 

 [CLS] query [SEP] document [SEP]
 
 Query 和 Document 会一起进入 Transformer，自注意力可以直接建模二者之间的 Token 级关系，因此相关性判断通常明显强于向量余弦相似度。 

 但 Cross-Encoder 无法提前为所有文档计算独立向量。如果知识库有一百万条文档，不可能让 Query 与一百万个 Document 分别跑一次 Transformer。 

 所以真实系统一般采用 两阶段检索 ： 

 ANN / BM25
 ↓
Top 50~200 candidates
 ↓
Cross-Encoder Reranker
 ↓
Top 5~10 contexts
 
 召回模型负责“尽量别漏”，Reranker 负责“把真正相关的内容排到前面”。RAG 中两者承担的是完全不同的职责。 

 四、怎么看出来优化真的有效果 

 不能靠挑几个 Case 看模型回答“好像更聪明了”。RAG 的链路比较长，需要把检索效果和最终生成效果拆开评估。 

 检索层我会重点观察 Recall@K、MRR 和 NDCG。比如一条 Query 对应一个标准相关 Chunk，如果它有没有进入 Top10，可以用 Recall@10 判断；如果进入了，但是长期出现在第八、第九名，那么 Recall 看不出问题，这时 MRR 更敏感；如果一条 Query 存在多个不同相关程度的文档，NDCG 更适合衡量排序质量。 

 生成层则看 Answer Correctness、Faithfulness 和 Citation Correctness。尤其 RAG 很容易出现“召回正确但模型没有使用证据”或者“答案正确但其实是模型参数知识猜出来的”，所以 Groundedness/Faithfulness 不能省。 

 线上还要观察 P95/P99 延迟、Token 消耗、无答案率、用户追问率等指标。因为一次优化即使把 Recall@10 从 88% 提到 91%，但让检索延迟从 80ms 变成 600ms，未必值得上线。 

 比较可靠的方法是固定同一套评测集，对 Baseline 和新版本分别跑完整链路，按照不同问题类型进行分桶比较，同时检查提升是不是集中在少量样本。上线之后再通过 A/B Test 验证真实用户场景，避免离线指标与业务体验脱节。 

 五、为什么很多 RAG 系统增加 TopK 以后，最终回答准确率反而会下降？ 

 TopK 增大通常能提高召回率，但 召回率提高不等于最终答案准确率提高 。 

 假设正确证据本来就在 Top3，TopK 从 5 增加到 30 以后，额外加入的大量内容可能只是弱相关文档。这些内容进入 Context 后会产生明显的噪声干扰。 

 Transformer 并不会天然知道哪段材料最可靠。如果上下文中存在多个相似但结论不同的版本，例如旧版接口文档和新版接口文档，模型很容易混合生成错误答案。 

 Context 过长还会出现 Lost in the Middle。相关证据位于长上下文中间位置时，模型对其利用能力可能下降。另外 TopK 增大会增加输入 Token 数量，延迟和推理成本也会同步上涨。 

 所以更合理的目标不是无限提高 K，而是让候选集合维持较高 Recall，再通过 Reranker、Metadata Filter、去重和动态阈值把真正有价值的 Context 留下来。 

 实际项目中我更倾向于： 

 较大的 Recall K
 ↓
Rerank
 ↓
较小的 Final K
 
 例如先召回 50 条，再让 Reranker 选 5～8 条，而不是直接把 50 条全部送入 LLM。 

 六、多模态怎么进行入库和检索了解吗 

 多模态 RAG 最难的地方不是“把图片也 Embedding 一下”，而是建立不同模态之间可对齐、可检索的语义表示。 

 例如处理带图片、表格的 PDF，我会先通过 Layout Parser 恢复文档结构，得到标题、正文、图片、表格以及它们之间的位置关系。文本可以直接进入文本 Embedding 模型，图片可以使用 CLIP、SigLIP 这类视觉文本对齐模型产生向量，也可以先通过视觉语言模型生成 Caption，再对 Caption 做文本 Embedding。 

 表格通常不能简单 OCR 成一串文本。比较可靠的方式是保留表头和行列结构，将表格转成 Markdown/HTML 或结构化 JSON，同时生成一份描述性文本用于语义检索。 

 索引层可以采用多个向量空间： 

 text_vector
image_vector
table_vector
 
 查询如果是纯文本，可以同时计算 Text Embedding 和跨模态 Embedding，对多个索引分别召回，然后进行融合排序。 

 另一种工程上更简单的方案是全部转成文本语义表示，例如图片通过 VLM 生成描述，表格生成摘要，再统一走文本 Embedding。它牺牲了一部分视觉细节，但检索链路更简单。 

 如果场景涉及“找出和这张图片相似的设计稿”这类视觉检索，仅靠 Caption 就不够，这时必须保留原始视觉 Embedding。 

 七、如果 RAG 在离线评测上效果很好，但上线后用户反馈大量“答非所问”，你会怎么定位问题？ 

 我不会直接认定是 LLM 能力不够，而是从线上 Query 分布和离线数据分布是否一致开始查。 

 很多离线评测集来自内部人员人工构造，问题往往语义完整，例如“订单退款接口的超时时间是多少”。真实用户可能只输入“退款超时”“这个多久”“上面那个接口呢”，甚至包含错别字、缩写和上下文指代。这属于明显的 Distribution Shift。 

 可以把线上失败请求完整记录成： 

 Query
→ Query Rewrite
→ Recall Documents
→ Rerank Scores
→ Final Context

## 分享｜5年Java面快手AI全栈，死磕虚拟线程底层，一面45分钟被当场问住

来源：牛客网 ｜ 类型：面经 ｜ 发布：2026-10-28 ｜ [原文链接](https://www.nowcoder.com/discuss/944996286334255104)

先交代背景：普通本科，5年经验，上家做电商中台。快手一面45分钟，没有手撕，全程围绕并发新特性与JVM深挖。我自认为对并发很熟，但遇到真正的底层连环追问，直接被按在地上摩擦。

 📌 一面被连环深挖的3个致命问题（45分钟） 

 1️⃣ ThreadLocal在虚拟线程里会有什么问题？底层怎么规避？ 

 💡 思路参考 ：我第一反应是背八股：“弱引用、内存泄漏、手动remove”。面试官直接打断：“我问的是 虚拟线程 。”我当时卡住了。正确逻辑是：平台线程数量有限（几百个），ThreadLocal副本顶多是几百份；但虚拟线程可以开到几十万甚至百万级，如果每个虚拟线程都持有一份ThreadLocalMap且不清理，内存会瞬间被撑爆。JDK的解法是引入 ScopedValue （作用域值）来替代ThreadLocal，它不可变、随作用域自动失效，天然适配虚拟线程。5年经验如果只知道怎么用ThreadLocal，不知道它在 新并发模型下的失效场景 ，在一线大厂的新特性考察环节直接出局。

 2️⃣ 追问：“虚拟线程一定比平台线程好吗？什么场景下用虚拟线程反而更慢？” 

 💡 思路参考 ：这是快手面试官最爱挖的坑。虚拟线程的收益只在 IO密集型 场景（如HTTP调用、数据库查询）——阻塞时自动让出载体线程。但在 CPU密集型 任务里，虚拟线程并不能加速计算，反而因为调度开销导致性能略差于平台线程。更致命的是 pin问题（钉住载体线程） ：早期JDK中，如果虚拟线程在 synchronized 块里阻塞，会直接钉住底层的载体线程（平台线程），导致载体线程无法去执行其他虚拟线程，并发度瞬间退化。解法是改用 ReentrantLock 。5年经验要能讲出这个 边界 。

 3️⃣ 追问：“线程池的几种拒绝策略，生产环境你用哪种？CallerRunsPolicy有什么致命副作用？” 

 💡 思路参考 ：四种拒绝策略（Abort、CallerRuns、Discard、DiscardOldest）。但我答“用CallerRunsPolicy不丢任务”时，面试官反问：“如果提交任务的是Tomcat的工作线程，或者Netty的IO线程呢？”——那这个工作线程就会被这个任务 阻塞 ，导致整个Web容器响应变慢甚至事件循环卡死。正确做法是：核心业务用CallerRuns保底，但必须评估提交线程池的上下文；或者用自定义拒绝策略，写入磁盘/DB做异步补偿。5年经验不能只会背“不丢任务”，要懂 背压传导 。

 📌 复盘： 

 一面挂得心服口服。快手考的根本不是“你背了多少并发八股”，而是 你有没有把并发模型放在真实业务场景里去推演边界 。

 📌 声明 

 以上思路参考来自 "面题鸭🦆" 各岗位专属考题的考点方向 

 🎯 后来怎么调整的？ 

 那天面完我极度挫败。因为虚拟线程、ScopedValue这些是2026年才真正大规模进面试的新东西，我刷的很多网盘资料和旧八股里根本就没有。

 还有一个意外收获——没想到在 "面题鸭🦆" 上刷了一遍快手方向的JD专属出题和大厂考题，里面不仅有“虚拟线程pin问题”、“ScopedValue替代ThreadLocal”的源码级解析，还有“CallerRunsPolicy在不同容器下的死锁场景”推演。我跟着这套题把并发新特性的边界全部补齐了，后来再面其他大厂，遇到新特性题我直接降维打击。 如果你也在准备跳槽，别拿着去年的旧八股去面今年的新大厂了。
